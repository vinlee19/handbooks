Chapter 09 · 并发模型与设计模式：为什么 moonlink 几乎没有锁

全仓 9 万行代码，核心表状态几乎不被互斥锁保护——靠的是「单线程 actor + 消息传递 + watch 广播 + 不可变快照」这套组合拳。本章把线程模型画清楚，并总结可迁移的设计模式。

9.4 可迁移的设计模式清单

模式moonlink 中的实现可迁移到的场景
单线程 actor + 结果回投TableHandler：事件串行、后台任务只回投 XxxResult任何「复杂可变状态」的并发封装（游戏状态机、会话管理）
水位窗口ongoing_flush_lsns BTreeMap：乱序完成按序生效分布式系统的乱序完成/顺序提交（复制协议、日志系统）
单一真源 + 最后写锚点metadata_wal.json 最后写；恢复时宁旧勿新任何「元数据 + 数据分离」的存储设计

9.6 全系列总结：一张图收束

读完九章，请用这句话向别人解释 moonlink：「它把 Iceberg 当成最终持久层，把本地内存+NVMe 当成可恢复的写缓冲：写入毫秒级可见（union read），落盘按 LSN 有序推进（flush 窗口 + 两级快照），删除只记位图（v3 DV），崩溃后从 WAL+Iceberg 对账恢复（单一真源 metadata），对查询引擎暴露的永远是『标准 Parquet + 位图』——所以实时与批式两条读路径共用一份物理数据。」

推荐的三条源码走读线路（每条约 1–2 天）：

  1. 写线路：rest_api.rs → moonlink_rest_sink.rs → table_notify.rs → table_handler.rs → mem_slice.rs → disk_slice.rs → snapshot.rs → iceberg_table_syncer.rs；
  2. 删线路：moonlink_sink.rs（upsert 展开）→ mem_index.rs → persisted_bucket_hash_map.rs → delete_vector.rs → iceberg/deletion_vector.rs → table_provider.rs（RowSelection）；
  3. 恢复线路：recovery_utils.rs → wal.rs（PersistentWalMetadata）→ iceberg_table_loader.rs → postgres_source.rs（skip_before_end_lsn）。
