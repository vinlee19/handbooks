Chapter 01 · 总体架构：Moonlink 是什么，为什么需要它

一句话：Moonlink 是一个「托管的 Apache Iceberg 摄取引擎」——它站在 PostgreSQL/Kafka/REST 与 Iceberg 湖仓之间，把高频流式写入变成对 Iceberg 友好的大文件 + v3 删除向量。

1.1 要解决的问题：Iceberg 不擅长「高频小写入」

Apache Iceberg 是为「大批量、低频次」的表格式与元数据管理设计的。一旦用传统 CDC 管线（如 Spark/Flink 作业）把高频更新直接打进 Iceberg，就会触发三个连锁问题：

  1. 小文件泛滥：每 1 分钟一个微批就要产生新 Parquet 文件，一天上千个小文件，对象存储 LIST/OPEN 请求暴增；
  2. 元数据爆炸：每次提交都重写 manifest list，equality-delete 文件还要在每次读取时与所有历史数据文件做关联，扫描代价持续上升；
  3. 合并成为日常运维：必须常驻 Spark compaction 作业，且合并窗口内写入/读取互相干扰。
图 1-1 · 传统摄取管线 vs Moonlink：把「合并」从日常运维变成内置后台任务
上：传统 CDC → Iceberg 管线。下：Moonlink 管线。核心差异在于中间多了一个「本地 NVMe 缓冲层」。

1.5 核心设计原则（读源码前先记住）

原则一：单写者 + 单线程事件循环。每张表一个 TableHandler actor 串行处理所有事件（写入/flush/快照/compaction 结果），重活 spawn 给后台任务再以事件形式回投。因此表内状态（Snapshot/MemSlice）几乎无锁。
原则二：一切靠 LSN 排序。commit LSN / flush LSN / iceberg snapshot LSN / replication LSN 构成一条单调时间线，写入可见性、恢复点、读一致性全部由「LSN 大小关系」推导（CH09）。
原则三：Iceberg 是唯一持久真相，WAL 是崩溃恢复补丁。已提交到 Iceberg 的数据永不丢；Iceberg 提交点之后、WAL 持久点之前的数据靠 WAL 重放补齐。
原则四：删除永不改写数据文件。所有删除都是「位图/日志」，读时过滤；数据文件只在 compaction 时才被重写——这是写放大与读放大之间的取舍，参数全部可配（CH06）。
