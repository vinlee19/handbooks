Chapter 05 · WAL 与崩溃恢复

Iceberg 之外的第二真相源。moonlink 的 WAL 极其「朴素」：每表一个 JSON 文件序列、一个 metadata_wal.json 单一真源，500ms 持久化一次、可截断。朴素，但闭环严谨。

5.1 WAL 的定位与文件组织

先明确：moonlink 的 WAL 不参与写路径延迟（Append 先进内存缓冲，500ms 才批量持久化），它的使命是崩溃恢复。真源链条是：Iceberg（已提交数据）+ WAL（Iceberg 提交点之后的增量）。WalManager（src/moonlink/src/storage/wal.rs，约 1300 行）每表一个实例、单线程使用。

5.5 六种 LSN 语义速查

LSN（table_handler.rs 头注释）含义谁维护
commit LSN一次（流式或非流式）提交的 LSN，可见性单位MooncakeTable::commit
flush LSN数据已 flush 成 data file 的水位（受图 3-3 窗口约束）apply_flush_result
iceberg snapshot LSN该 LSN 前的所有变更已持久化进 IcebergIcebergTableSyncer 提交后推进
table consistent view LSN最后处理的事件是 Commit 时点的 LSN —— 表处于一致视图，可安全 flush事件循环
replication LSNPG 复制流已到达的 LSNLsnState::mark（watch 广播）
persisted table LSN跨表概念：所有表都已持久化的最大公共 LSN（用于全局对账）backend 层
注意：replication LSN 与 commit LSN 之间没有数值序保证——表从干净状态恢复后，可能存在 iceberg snapshot LSN 但没有后续 replication LSN（源码头注释原话）。读侧（CH09）的可读判定为此专门做了分支。
