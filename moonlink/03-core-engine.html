Chapter 03 · 存储引擎：MooncakeTable

MooncakeTable 是整个项目的发动机：一个「磁盘表 + 内存切片」的混合结构，用 LSN 控制可见性。它不是 LSM-Tree，但借用了 LSM 的核心思想——分层、延迟物化、后台合并。

3.1 总体结构：一张表的三个世界

打开 src/moonlink/src/storage/mooncake_table.rs（约 1800 行），头注释一句话定调："MooncakeTable is a disk table + mem slice … LSN is used for visibility control"。一张表的完整状态分三个世界：可变内存（MemSlice，写正在发生）、快照内存（SnapshotTableState，已 commit 待 flush 的批与删除）、磁盘快照（Snapshot ↔ Iceberg snapshot 一一对应）。

图 3-1 · MooncakeTable 总体结构：数据从左到右单向流动
绿色 = 内存可变区；青色 = 快照内存区；橙色 = 磁盘/对象存储区。紫色管道是「LSN 可见性」。

3.2 MemSlice 内部：行流如何变成列批

摄入层送进来的是行（MoonlinkRow），落盘需要列（RecordBatch）。ColumnStoreBuffer 是这个转换器的核心：它把行流按 batch_size 切批，并为每个批分配 batch_id。

3.3 Flush：MemSlice 如何变成 Parquet

flush 是「内存态 → 磁盘态」的唯一通道。触发点在事件循环的 commit_and_attempt_flush()：每次 Commit 后检查水位；满足则走一条精心设计的异步流水线，actor 绝不等待磁盘。

// mooncake_table.rs（逻辑摘录）
fn should_flush(&self) -> bool {
    self.mem_slice.get_num_rows() >= self.config.mem_slice_size  // release: 131072 行
}
// table_handler.rs::commit_and_attempt_flush
if should_flush() || should_force_flush || force_flush_requested {
    let disk_slice = mooncake_table.prepare_disk_slice(lsn)?;      // ① actor 内：排空 MemSlice
    tokio::spawn(async move {                                      // ② 后台：写 Parquet
        let result = disk_slice.write().await;                     //    AsyncArrowWriter + 滚动切分
        event_tx.send(TableEvent::FlushResult{event_id, result});   // ③ 完成后回投事件
    });
}
图 3-3 · Flush 流水线全流程（含 flush LSN 顺序保证）
上半部是数据流，下半部是「ongoing flush LSN 窗口」——flush 完成顺序与 LSN 顺序解耦的关键。

3.4 两级快照：mooncake snapshot → iceberg snapshot

「快照」在 moonlink 里有两级，容易混淆，务必分清：mooncake snapshot 是内存态的整理与打包（500ms 周期），产出「待持久化 payload」；iceberg snapshot 才是真正向 Iceberg catalog 提交（异步、可攒批）。
