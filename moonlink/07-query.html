Chapter 07 · 查询路径：union read 与三个引擎生态

查询的本质是一道集合运算：磁盘文件 ∪ 内存数据 − 删除。moonlink 的聪明之处在于把「内存数据」现场物化成临时 Parquet，于是所有引擎看到的都是「纯 Parquet + 位图」这一种形态。

为什么把内存物化成临时文件，而不是让引擎读内存？① 免去跨语言/跨进程共享内存的复杂性；② 内存批生命周期短（随时 flush），物化后引用稳定；③ 引擎侧逻辑统一：只需要「parquet + 位图」一种抽象 —— pg_mooncake（C++）、duckdb 扩展、DataFusion（Rust）三种实现共享同一协议。临时文件的代价由 scan_table_end 时的 Drop 清理兜底。

7.2 可读判定：LSN 视角的读一致性

ReadStateManager::try_read(requested_lsn)（union_read/read_state_manager.rs）是读侧的「一致点等待器」。核心判定逻辑值得逐行读：

// read_state_manager.rs（摘录）
fn can_satisfy_read_from_snapshot(&self, requested_lsn, snapshot_lsn, replication_lsn, commit_lsn) -> bool {
    // 读侧不变式断言：iceberg snapshot LSN ≤ mooncake snapshot LSN ≤ commit LSN ≤ replication LSN
    if snapshot_lsn != NO_SNAPSHOT_LSN && commit_lsn != NO_COMMIT_LSN {
        assert_le!(snapshot_lsn, commit_lsn);
    }
    assert_le!(commit_lsn, replication_lsn);

    let is_snapshot_clean = Self::snapshot_is_clean(snapshot_lsn, commit_lsn);  // snapshot_lsn == commit_lsn
    match requested_lsn {
        None => true,                            // 读最新：总是可读
        Some(req) => {
            // 可读 ⇔ ① 快照已覆盖请求 LSN；或 ② 请求被复制流覆盖 且 快照干净（无未反映的提交）
            is_snapshot_initialized && req <= snapshot_lsn
                || (req <= replication_lsn && is_snapshot_clean)
        }
    }
}

条件②是点睛之笔：快照「干净」（snapshot LSN == commit LSN）意味着内存里没有未纳入快照的提交，此时磁盘快照 + 复制水位就足以保证读到 replication_lsn 的一致状态——不必等下一个 500ms 快照。缓存命中也用同一个 clean 判定（should_use_cache），所以重复读同一 LSN 几乎零成本。
