Chapter 02 · 数据摄入：REST 三格式 + PostgreSQL 逻辑复制

两条异构入口最终汇入同一条内部事件总线 TableEvent。本章拆开 moonlink_connectors 与 table_handler，看清数据怎么进来、怎么变成事件、怎么保证顺序。

2.1 总览：两条入口，一个总线

无论数据来自 PostgreSQL 的逻辑复制流，还是 REST 的 JSON/Avro/Protobuf 请求，最终都被翻译成统一的 TableEvent（src/moonlink/src/table_notify.rs），投递到每张表专属的 mpsc 队列。这是理解摄入层的第一个关键：入口异构，内核同构。

右侧三色的表各代表一张独立的表（每表一个 actor 与一套内存结构）。

2.2 TableHandler：每表单线程事件循环

TableHandler（src/moonlink/src/table_handler.rs）是整台机器的「心脏起搏器」：一个 tokio 任务跑 event_loop，另一个任务跑 tokio::select! 定时器。所有对表状态的修改都发生在这一个任务里。

// table_handler.rs（摘录）
const MAX_BUFFERED_TABLE_EVENTS: usize = 32_768;

let periodic_event_handle = tokio::spawn(async move {
    loop {
        tokio::select! {
            _ = table_handler_timer.wal_snapshot_timer.tick() => {
            // 每 500ms：请求把 WAL 缓冲持久化（CH05）
                event_sender.send(TableEvent::PeriodicalPersistenceUpdateWal(uuid)).await;
            }
            _ = table_handler_timer.mooncake_snapshot_timer.tick() => {
            // 每 500ms：尝试创建 mooncake 快照（CH03）
                event_sender.send(TableEvent::PeriodicalMooncakeTableSnapshot(uuid)).await;
            }
            _ = table_handler_timer.force_snapshot_timer.tick() => {
            // 每 300s：兜底强制快照，保证 Iceberg 不会长期不提交
                event_sender.send(TableEvent::ForceSnapshot { lsn: None }).await;
            }
        }
    }
});
图 2-2 · TableHandler 事件循环：输入、分派与结果回投
所有方框内动作都在同一 tokio 任务内串行执行；灰色箭头是后台任务的「结果事件」回流。阻塞态（initial copy / alter）期间普通事件进 initial_copy_buffered_events 缓冲。
为什么 WAL 先于内存写入？Append 事件处理顺序是「先 push_wal_event 再改 MemSlice」。这样即使进程在两者之间崩溃，恢复时重放 WAL 不会丢失任何已确认的写入——内存态可以随时重建，WAL 是源头。

2.5 REST 摄入：sync / async 双模式

REST 路径（src/moonlink_service/src/rest_api.rs + src/moonlink_connectors/src/rest_ingest/）把 HTTP body 转成 MoonlinkRow 后走同一事件总线。亮点是「sync 模式能拿回 LSN」：

// rest_api.rs：sync 模式 —— 建一条容量为 1 的 oneshot 式 mpsc，把 tx 塞进事件里
let (tx, rx) = mpsc::channel(1);
RowEventRequest { rows, table, tx, request_id, … }
// 事件流先「排队确认」再执行 —— 保证快照/flush 的 LSN 语义（先入队，后执行）
send_event_request(event_tx, request).await?;   // rx.recv() 确认已被表收到
backend.ingest_table_rows(…).await?;
let lsn = rx.recv().await;                     // 表事件循环处理完回传分配的 LSN
// 响应: IngestResponse { lsn }  —— 调用方可据此做「写到 LSN 为止」的一致性等待

2.6 数据模型：MoonlinkRow 与三种编码

摄入层的「货币」是行。moonlink 自定义了与 Arrow 解耦的行模型，三种入口编码最终都归一到它：

编码定义位置用途要点
MoonlinkRow { values: Vec<RowValue> }src/moonlink/src/row/moonlink_row.rs内存与 WAL 的行表示RowValue 是标量枚举（int32/int64/float/bool/bytes/decimal/array/struct/null…）；WAL 直接 serde_json 序列化它
Protobuf MoonlinkRowsrc/moonlink_proto/proto/row.proto/ingestpb · OTEL 自吞 · RPConeof kind 镜像 RowValue；decimal 用 16 字节大端补码 bytes

主键身份 IdentityProp（row/moonlink_row.rs）：SinglePrimitiveKey / Key / FullRow / None 四种形态决定建什么索引。get_lookup_key(&row) -> u64 计算哈希查找键；None = append-only 表，无索引、无删除，写入最快。

2.7 小结与自测

  • CDC 与 REST 两条入口在 MoonlinkSink / MoonlinkRestSink 处翻译成统一的 TableEvent，之后的世界完全同构。
  • 每个事务的边界与 LSN 直接继承自 PG 的 Commit.end_lsn；UPDATE 在 sink 层展开为 Delete+Append。
  • Initial copy 用 pg_export_snapshot + CTID 分片做到「并行但不乱序」：actor 阻塞态 + 事件缓冲是关键。
  • REST sync 模式的 LSN 回传与「先入队后执行」是一致性语义的核心技巧。

自测：为什么 send_status_update 的 flush_lsn 不能用 replication LSN 而要用 WAL 持久化 LSN？（提示：ACK 过早 → PG 清理 WAL → 崩溃后 moonlink 却还没持久化 → 数据丢失。答案在 CH05 的 WAL 持久化闭环里。）
