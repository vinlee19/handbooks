Postgres 扩展层：940 行代码如何撬动整个湖仓

src/ 是整个项目最薄、也最“反直觉”的部分——表访问方法几乎是空的，数据一条都不经过它。本章逐文件拆解它到底做了什么、为什么敢这么设计。

2.2 扩展入口：_PG_init 做的两件事

src/lib.rs 
pg_module_magic!();                          // Postgres 动态库入口约定
extension_sql_file!("./sql/bootstrap.sql");  // CREATE EXTENSION 时执行

#[pg_guard]
pub extern "C-unwind" fn _PG_init() {
    bgworker::init();   // ① 注册 moonlink 后台工作进程（仅 postmaster 阶段生效）
    table::init();      // ② 把 MOONCAKE_AM 注册进 pg_duckdb 的表 AM 注册表
}
🔑 关键理解 _PG_init 在每个加载本库的 Postgres 进程里都会执行一次：postmaster 里注册 bgworker；每个 backend 里把 MOONCAKE_AM 指针登记进 pg_duckdb 的进程内注册表 duckdb_table_ams（pg_duckdb/src/pgduckdb_table_am.cpp:502）。之后 planner 钩子只要看到某关系的 rd_tableam 命中该注册表，就知道“这表归 DuckDB 管”。

2.3 空壳表访问方法：全项目的点睛之笔

src/table.rs 定义了一个完整的 TableAmRoutine 静态结构 MOONCAKE_AM。Postgres 要求 AM 的每个槽位都有值，但它把所有涉及行数据的回调都填成了 unimplemented!()（一旦被调用即 panic），只保留少数“结构性”回调给出无害实现：

图 2-2 · 空壳表 AM 剖析：注册进 pg_duckdb 才是它的唯一使命，行数据回调 panic 是特性不是缺陷
💡 为什么要费这个劲 用真表 AM 而不是 FDW/视图，换来的是：① pg_dump/\d/权限/依赖等目录管理全部原生；② pg_duckdb 的 ruleutils 能把表定义反解析成 USING mooncake；③ planner 钩子有稳定的识别锚点（rd_tableam 指针）。代价是必须“装作”一张表——这就是那些空实现回调的由来。

2.4 mooncake.create_table：一次“借道自己”的 DDL

创建镜像表的过程堪称精巧：过程先用一条独立的 SQL 连接（rust-postgres + native-tls，而非 SPI）读取源表列定义，然后执行 CREATE TABLE … USING mooncake，最后才通过 RPC 通知 moonlink 开始复制。这样设计让“源库”与“目标库”可以是两个不同的 Postgres 实例（src_uri 参数）。

src/functions.rs（节选，行号为对应源码位置） 
// L24-43：存储过程入口
#[pg_extern(sql = "...")]
fn create_table(dst: &str, src: &str, src_uri: Option<&str>,
                table_config: Option<pgrx::JsonB>) -> TableResult<()> {
    let dst_table = parse_table(dst)?;                 // L146：正则解析 schema.table（支持引号标识符）
    let src_table = parse_table(src)?;
    let dst_uri = get_loopback_uri()?;                 // L165：postgresql:///db?host=<unix_socket_dir>&port=…&user=…
    let src_uri = src_uri.unwrap_or(&dst_uri);         // 默认源 = 本实例（环回）
    create_mooncake_table(&dst_table, &dst_uri, &src_table, src_uri)?;  // ① 先建空壳表
    let mut stream = get_stream();                     // ② 再通知 moonlink（阻塞式 RPC）
    block_on(moonlink_rpc::create_table(&mut stream, DATABASE.to_owned(),
        dst_table.to_string(), src_table.to_string(),
        src_uri.to_owned(), config_str))
}

// L198-232：用 rust-postgres 直连内省 pg_attribute，拼出列定义并执行 DDL
fn create_mooncake_table(…) -> Result<()> {
    let query = "SELECT string_agg(
        format_type(a.atttypid, a.atttypmod) ||
        CASE WHEN a.attnotnull THEN ' NOT NULL' ELSE '' END, ', ')
        FROM pg_attribute a WHERE a.attrelid = $1
          AND a.attnum > 0 AND NOT a.attisdropped";
    // ...对 src 连接执行，拿到 "col1 type NOT NULL, col2 type, …"
    dst_client.execute("CREATE TABLE … USING mooncake", &[])?;
}

2.5 DROP 的两阶段同步：事件触发器 + 事务回调

删除镜像表必须解决一个经典难题：DDL 可能回滚。如果 sql_drop 事件触发时立刻通知 moonlink 删表，而随后事务 ROLLBACK，引擎状态就丢了。解法是把 RPC 推迟到事务预提交回调里：

src/functions.rs:45-82（节选） 
#[pg_extern(sql = "...")]
fn mooncake_drop_trigger(trigger: &pgrx::PgTrigger) -> Result<()> {
    // SPI 查询本次 DROP 的对象，过滤 object_type = 'table'
    let dropped_tables: Vec<String> = /* pg_event_trigger_dropped_objects */;
    for table in dropped_tables {
        let tbl = table.clone();
        pgrx::register_xact_callback(PgXactCallbackEvent::PreCommit, move || {
            // 只在事务真正提交时才通知引擎删表
            block_on(moonlink_rpc::drop_table(&mut stream, DATABASE…, tbl))
        });
        // 并行 worker 提交路径（ParallelPreCommit）同样注册
    }
}
图 2-4 · DROP 同步：把破坏性 RPC 延迟到 PreCommit，天然获得“回滚安全”

2.6 后台工作进程与每后端状态

src/bgworker.rs 
pub(crate) fn init() {
    BackgroundWorkerBuilder::new("moonlink")
        .set_library("pg_mooncake")        // 从本 .so 找入口
        .set_function("moonlink_main")
        .enable_shmem_access(None)          // 需要共享内存访问权限
        .set_start_time(BgWorkerStartTime::ConsistentState)
        .set_restart_time(Some(Duration::from_secs(15)))  // 崩溃 15s 后重启
        .load();
}

#[tokio::main]
pub async fn start() {
    let config = ServiceConfig {
        base_path: "pg_mooncake".to_owned(),  // 相对 cwd = $PGDATA
        data_server_uri: None, rest_api_port: None,
        otel_ingestion_api_port: None, tcp_port: None,   // 内嵌模式全部关闭
        log_directory: None, otel_export_target: None,
    };
    start_with_config(config).await.unwrap();
}

每个 backend 里则维持着极简的“每进程一份”状态（src/utils.rs）：

静态量 / 函数内容为什么这样
DATABASE: LazyLock<String>当前数据库名（get_database_name(MyDatabaseId)）RPC 都带 database 参数；backend 生命周期内不变，缓存一次即可
block_on()懒初始化的 current-thread tokio runtime在 Postgres 进程内嵌异步调用但不能抢主线程；单线程运行时零竞争
get_stream()Mutex<UnixStream>，首次连接 pg_mooncake/moonlink.sock每 backend 只建一条 RPC 长连接，Mutex 串行化避免帧交错
⚠️ 串行化的代价：Mutex 意味着同一 backend 内的 RPC 是串行的，但对典型负载（一个事务里几次控制面调用）完全够用；真正并行的扫描流量走的是 DuckDB→moonlink_ffi 的独立连接池（第 06 章）。

2.7 三个导出符号：跨语言回头的桥

src/duckdb_mooncake.rs 导出三个 #[no_mangle] C 符号。它们的存在前提是：pg_mooncake.so 与 DuckDB（含 mooncake 扩展）已经加载在同一个进程地址空间，所以 C++ 扩展可以直接 dlsym(RTLD_DEFAULT, …) 找到它们——这是两种语言、两个扩展之间零胶水代码的通信方式：

src/duckdb_mooncake.rs 
#[no_mangle]
extern "C" fn pgmooncake_get_init_query() -> *mut c_char {
    // 取当前数据库名 → 拼出 DuckDB ATTACH 语句
    let init_query = format!("ATTACH DATABASE 'mooncake' (TYPE mooncake, \
        URI 'pg_mooncake/moonlink.sock', DATABASE '{database}')");
    CString::new(init_query).unwrap().into_raw()   // 所有权移交 C++ 侧（用 pgmooncake_drop_cstring 释放）
}

#[no_mangle]
extern "C" fn pgmooncake_get_lsn() -> u64 {
    unsafe { pgrx::pg_sys::XactLastCommitEnd }   // 本 backend 最近一次提交记录的结束 LSN
}
  • pgmooncake_get_init_query：把“如何接入本实例的湖仓”编码成一条 DuckDB SQL，由扩展加载时执行（详见第 06 章）。
  • pgmooncake_get_lsn：DuckDB 每开一个事务用它取快照 LSN——这是读写一致性的锚点（第 07 章 LSN 不变式）。
  • pgmooncake_drop_cstring：让 C++ 侧把 CString 的内存还回 Rust 分配器，避免跨分配器 free。
🔑 小结：扩展层的全部职责 ① 登记 AM 路标；② 提供建/删/维护表的 SQL 入口；③ 拉起并守护 moonlink 引擎；④ 向 DuckDB 泄漏两条信息（接入方式 + 快照 LSN）。它不碰数据、不做路由、不管理事务——把这些全部让渡给 pg_duckdb 与 moonlink。
