第 01 章

架构总览：四大组件、一条 RPC、一份磁盘契约

本章回答三个问题：仓库里有哪些东西、它们如何被构建成三个 .so、运行时它们靠什么协议与什么磁盘布局协作。

1.1 项目定位

README 的原话是：“为你的 Postgres 表在 Iceberg 中创建列存镜像（columnstore mirror），并保持亚秒级新鲜度”。拆开来看是三种能力的组合：

能力实现者机制
实时摄取moonlink 引擎订阅源表 WAL 逻辑复制，行进来先入内存列存（Arrow），攒批落 Parquet
开放存储格式moonlink + apache/iceberg-rust每次快照以 Iceberg 表格式提交（manifest/snapshot），删除向量与文件索引写入 Puffin 附件
分析查询pg_duckdb + duckdb_mooncakeplanner 钩子强制 SQL 走内嵌 DuckDB；mooncake_scan 表函数读 Parquet 并应用删除过滤
使用方式（README Quick Start） 
-- 安装扩展（CASCADE 会连带装好依赖的 pg_duckdb）
CREATE EXTENSION pg_mooncake CASCADE;

-- 为已有行存表 trades 创建列存镜像 trades_iceberg
CALL mooncake.create_table('trades_iceberg', 'trades');

-- 像普通表一样查询，实际由 DuckDB 扫描 Parquet 执行
SELECT avg(price) FROM trades_iceberg WHERE ts > now() - interval '1 day';

1.2 构建体系：三条流水线拼出一个可运行系统

三个组件各自独立构建，靠“版本对齐”协同：duckdb_mooncake 必须与 pg_duckdb 内嵌的 DuckDB v1.4.1 完全同版（Makefile 里用 OVERRIDE_GIT_DESCRIBE=v1.4.1 硬编码）。根 Makefile 把三条流水线串起来：

Makefile（根目录） 
install:        ## 一键安装扩展本体（自动生成 SQL 并装进 pgrx 管理的 PG）
	cargo pgrx install --release
pg_duckdb:      ## 先装依赖扩展 pg_duckdb
	$(MAKE) -C pg_duckdb install
duckdb_mooncake: ## 构建 DuckDB 社区扩展（Corrosion 会顺带编译 Rust FFI 静态库）
	$(MAKE) -C duckdb_mooncake GEN=ninja OVERRIDE_GIT_DESCRIBE=v1.4.1
test:
	cargo pgrx regress --resetdb
图 1-2 · 三条构建流水线与运行时组装
⚠️ 版本对齐陷阱 duckdb_mooncake 的静态扩展版本必须等于 pg_duckdb 内嵌的 DuckDB 版本，否则加载即崩。这也是 Docker 镜像直接从社区扩展仓库下载预编译版而不是本地构建的原因：CI（duckdb_mooncake/.github/workflows/MainDistributionPipeline.yml）保证发布的二进制与 DuckDB 版本矩阵对齐。

1.3 通信协议：4 字节长度 + bincode 的极简 RPC

扩展层（每个 Postgres backend）与 moonlink 引擎（bgworker）之间的全部通信，都走一个 Unix Domain Socket：$PGDATA/pg_mooncake/moonlink.sock。协议定义在 moonlink/src/moonlink_rpc/src/lib.rs，总共不到 70 行：

moonlink/src/moonlink_rpc/src/lib.rs（节选） 
// 10 个 RPC 用宏一次性生成：Request 枚举 + 客户端 async fn
rpcs! {
    create_snapshot(database: String, table: String, lsn: u64) -> ();
    create_table(database: String, table: String, src: String,
                 src_uri: String, table_config: String) -> ();
    drop_table(database: String, table: String) -> ();
    get_parquet_metadatas(data_files: Vec<String>) -> Vec<Vec<u8>>;
    get_table_schema(database: String, table: String) -> Vec<u8>;   // Arrow IPC 流
    list_tables() -> Vec<Table>;
    load_files(database: String, table: String, files: Vec<String>) -> ();
    optimize_table(database: String, table: String, mode: String) -> ();
    scan_table_begin(database: String, table: String, lsn: u64) -> Vec<u8>;
    scan_table_end(database: String, table: String) -> ();
}

// 帧格式：4 字节本机序长度 + bincode(standard) 载荷
pub async fn write<W: AsyncWrite, S: Serialize>(writer: &mut W, data: &S) -> Result<()> {
    let bytes = bincode::serde::encode_to_vec(data, BINCODE_CONFIG)?;
    writer.write_all(&(bytes.len() as u32).to_ne_bytes()).await?;
    writer.write_all(&bytes).await
}
图 1-3 · bincode-over-Unix-Socket RPC 帧格式：控制面信使，载荷只有指令与元数据，永远不传行数据
🔑 协议设计要点 ① schema 用 Arrow IPC（get_table_schema 返回 StreamWriter 字节流），C++ 侧用 nanoarrow 直接解码；② 扫描返回的不是数据而是文件清单——bincode 编码的 MooncakeTableMetadata（见第 06 章），DuckDB 拿到路径自己去读文件；③ 帧头用本机字节序（to_ne_bytes），因为通信两端永远在同一台机器上。

1.4 磁盘布局：$PGDATA/pg_mooncake/

bgworker 启动时的工作目录是数据目录 $PGDATA（postmaster 会 chdir 到这里），所以 base_path = "pg_mooncake"（src/bgworker.rs:29）解析为 $PGDATA/pg_mooncake。所有状态都集中在这一个目录：

1.5 SQL 对象清单（扩展装了什么）

扩展安装后，Postgres 侧多出的对象非常少——这正是刻意为之的“薄扩展层”。除了 mooncake schema 里几个过程外，核心是一个表访问方法和一个事件触发器：

SQL 对象定义位置作用
ACCESS METHOD mooncake TYPE TABLE + handler mooncake_am_handlersrc/table.rs:69-75让 CREATE TABLE … USING mooncake 可用；AM 例程表是空壳，真正的目的是把 AM 指针注册进 pg_duckdb
PROCEDURE mooncake.create_table(dst, src, src_uri?, table_config?)src/functions.rs:24-43建镜像：环回连接复制列定义 → CREATE TABLE … USING mooncake → RPC 通知 moonlink 启动复制
PROCEDURE mooncake.create_snapshot(dst)src/functions.rs:9-22以当前 XactLastCommitEnd 为 LSN 强制做一次 Iceberg 快照
FUNCTION mooncake.list_tables()src/functions.rs:84-116列出镜像表及 commit_lsn / flush_lsn / warehouse 位置
PROCEDURE mooncake.load_files / optimize_tablesrc/functions.rs:118-144批量导入 parquet 文件；手动触发压缩（mode: data/index/full）
EVENT TRIGGER mooncake_drop_trigger ON sql_dropsrc/functions.rs:45-82镜像表被 DROP 时，在事务预提交回调里 RPC drop_table（保证只在 DDL 真正提交后删除引擎状态）
SCHEMA mooncake + duckdb.install_extension('mooncake','community')src/sql/bootstrap.sql在 duckdb.extensions 表登记社区扩展，之后 DuckDB 实例启动时自动 LOAD
⚠️ 注意：本版本（0.2.0）没有 mooncake_database / mooncake_table 这类目录表——表注册表在 moonlink 的 SQLite 元数据存储里；也没有任何 GUC 定义（旧版 CHANGELOG 提到的内存/线程 GUC 已移除）。

1.6 启动时序：从 postmaster 到可查询

图 1-5 · 启动时序：postmaster 预载 → bgworker 独立就绪 → CREATE EXTENSION 登记 DuckDB 扩展 → 首次查询触发完整链路
💡 为什么这样分层 扩展层薄（~940 行）意味着 Postgres 侧几乎零维护成本；引擎厚（moonlink 数万行）意味着所有复杂度被隔离在 bgworker 进程内——即使 moonlink panic，也只是 bgworker 退出并在 15 秒后重启，Postgres 本体不受影响。这是本项目最重要的工程决策之一。
