第 04 章

CDC 复制引擎：把 WAL 变成列存的流水线

moonlink_connectors 负责数据从哪来：Postgres 逻辑复制（pgoutput）为主通道，REST/Avro/Kafka 为辅通道；配套解决初始拷贝、超大事务流式摄取、复制槽水位回传三大工程难题。

4.1 复制拓扑与每表组件装配

ReplicationManager（moonlink/src/moonlink_connectors/src/replication_manager.rs:22）维护两张映射：src_uri → ReplicationConnection（每个源实例一条复制连接）和 mooncake_table_id → (uri, src_table_id)。同一源实例上的多张镜像表共用一条复制流，在 Sink 层按表分发。特殊 URI rest://api 代表 REST 摄取通道。

图 4-1 · 复制拓扑：连接级（每源实例）与表级（每镜像表）两层组件的职责划分

4.2 初始拷贝：先复制存量，再衔接增量

新镜像表建立时，源表可能已有海量数据。moonlink 的做法是经典的“拷贝点 + 追平”：先建复制槽拿到一致性点，再分片并发 COPY 存量，最后从一致性点开始消费 CDC，直到追平后进入常规增量模式。

图 4-2 · 初始拷贝四阶段：复制槽保一致性点 → 分片 COPY 并发拉存量 → CDC 追平 → 常态增量

4.3 大事务流式摄取：高位 LSN 空间的技巧

逻辑复制的开销主要来自“提交前不知道事务有多大”。pgoutput 支持 streaming 模式：未提交事务的变更可以边产生边推送。moonlink 用一个精巧的 LSN 地址空间划分来管理这些“还没有最终 LSN”的行：流式事务的行被赋予 0xFFFFFFFF_00000000 以上的虚拟 LSN，与正常 LSN 空间完全隔离。

图 4-3 · 流式大事务：高位虚拟 LSN 隔离未提交数据，提交时整体“落地”到真实 LSN

4.4 复制槽水位回传：谁说了算“WAL 可以删了”

复制槽不推进，源库 WAL 就会无限膨胀——这是所有 CDC 系统的生死线。moonlink 的答案：只有数据“持久到 Iceberg”之后，才允许源库删除对应 WAL。

图 4-4 · 复制槽水位回路：取所有表最慢一路的“持久化水位”作为确认点，把存储故障转化为源库 WAL 背压

4.5 其他摄取通道：REST / Avro / Kafka / 文件

moonlink_service 在独立部署（或启用 REST 端口）时暴露一组 HTTP API（moonlink/src/moonlink_service/src/rest_api.rs:390-423），经 EventRequest 通道进入与 CDC 相同的 actor 队列，后端处理路径完全一致：

端点 / 入口载荷去向
POST /ingest/{table}JSON 行RestSource 转换为 MoonlinkRow → TableEvent::Append
POST /ingestpb/{table}protobuf（moonlink_proto 的 RowValue）同上，零拷贝友好
POST /kafka/{table}/ingestAvro 记录Avro → MoonlinkRow
POST /upload/{table}Parquet 文件load_files RPC / FileRequest：整文件注册进快照（跳过行转换）
…/optimize | snapshot | flush—触发压缩 / 强制快照 / 强制 flush

pg_mooncake 的内嵌模式没有打开 REST 端口（src/bgworker.rs 全部为 None），但 mooncake.load_files 过程仍可经 RPC 批量导入 Parquet 文件。此外 load_files 还支持把外部 parquet 直接挂进表——这就是 README 中 “load_files” 特性的实现。

🔑 本章心法 无论 CDC、REST 还是文件导入，最终都收敛为同一件事：带 LSN 的 TableEvent 进 actor 队列。上游千变万化，下游（第 03/05 章）完全不知情——这是 moonlink 架构上最重要的解耦。
