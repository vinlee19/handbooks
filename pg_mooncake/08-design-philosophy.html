设计精髓：八个决策、一份权衡清单、一条调试路线

把全部源码读完后回望：这个项目真正的创新不是某个算法，而是一组互相成就的架构决策。本章逐一复盘它们，并给出诚实的局限清单与动手调试路线。

8.1 八个关键设计决策

  1. 空壳表 AM 作为“路标”——不实现数据路径，只把 rd_tableam 当作查询路由的稳定锚点（src/table.rs）。换来原生目录管理/权限/工具链兼容，代价是“看起来像表但不是表”的认知成本。
  2. 引擎内嵌为 bgworker——moonlink 与 Postgres 同进程同生共死，Unix socket 通信零网络开销；崩溃隔离靠 Postgres 的 worker 重启机制（15s），不需要任何看门狗代码。
  3. 控制面 RPC、数据面文件——RPC 只传指令与元数据（最长载荷是文件清单），数据永远以文件路径共享。带宽占用与数据规模彻底解耦。
  4. LSN 作为唯一时钟——Postgres 的 XactLastCommitEnd 贯穿写入（复制位点）与读取（扫描快照）两条链路，一个标量同时回答“读哪、等到哪、恢复到哪”。
  5. 每表 actor + 结果回流——单写者消除一切数据竞争；重活 spawn 出去、结果作为事件回流队列，串行核心保持极薄。
  6. Union Read 物化内存数据——查询不必等 flush：已提交未落盘的行物化成临时 Parquet 参与扫描。新鲜度与落盘节奏解耦，这是“亚秒级”的直接来源。
  7. 开放格式优先——数据文件是标准 Iceberg（任何引擎可读），删除向量/索引放 Puffin 附件；moonlink 死机也不损坏数据，第三方引擎最多读到旧快照。
  8. 复用而不重造——路由用 pg_duckdb、扫描用 parquet_scan 克隆、Iceberg 提交用 apache/iceberg-rust、统计裁剪用 DuckDB 原生过滤框架。自研代码只出现在“胶水”与“增量语义”上。

8.4 诚实的局限清单（读源码才能看见的）

局限源码证据影响 / 缓解
镜像表只读duckdb_mooncake PlanInsert/Delete/Update 抛 NotImplementedException；表 AM 写回调全是 unimplemented!()写入必须经源表（或 load_files）。这是刻意取舍：单写入口让 CDC 语义永远简单
VACUUM/CLUSTER 会 panicAM 的 relation_vacuum / relation_copy_for_cluster 未实现对空壳表执行这些命令没有意义，panic 即“误用报警”
复制模式仅 NOT NULLcreate_table 的 pg_attribute 查询只拼类型 + NOT NULLPK/唯一约束/默认值不复制——镜像表是分析副本，不是热备
WAL 保留依赖引擎健康confirmed_flush_lsn = min(所有表持久化水位)moonlink 长期停滞 → 源库 WAL 膨胀。监控复制槽 restart_lsn 是运维必配
引擎全局单点一个实例只有一个 moonlink bgworker，所有库的表都在其中bgworker 崩溃 → 全部表复制中断 ~15s（重启后自动追平）
DuckDB 版本强绑定OVERRIDE_GIT_DESCRIBE=v1.4.1 必须与 pg_duckdb 内嵌版本一致升级三件套要同步；社区预编译扩展由 CI 保证兼容矩阵
无 ALTER TABLE 支持src/ 无任何 ALTER 拦截；引擎有 AlterTable 事件但 SQL 侧未暴露源表加列后需重建镜像（或未来版本补齐 alter_table RPC 通路）
ANALYZE 对镜像表无效scan_analyze_next_block 返回 false；estimate_size 全 0无影响：触及镜像表的查询整体交给 DuckDB，由其 Parquet 统计做计划

8.5 动手调试路线（debug-learning 分支指南）

🛠 快速上手 
make pg_duckdb && make duckdb_mooncake && make install   # 构建三件套
make test                                                  # pg_regress: sanity / partitioned_table
cd moonlink && cargo test -p moonlink                      # 引擎单测（~600 个）
psql -c "CALL mooncake.create_table('c','r')"              # 复现链路
psql -c "EXPLAIN SELECT * FROM c"                          # 应显示 DuckDB 计划
ls $PGDATA/pg_mooncake/                                    # 观察 socket/parquet/wal 的诞生
psql -c "SELECT * FROM mooncake.list_tables()"             # commit_lsn / flush_lsn 水位
  • 看写入进度：mooncake.list_tables() 的 commit_lsn 与 flush_lsn 差值 = 内存中未落盘的数据量；复制槽 pg_replication_slots 的 confirmed_flush_lsn 停滞 = 引擎持久化卡住。
  • 看查询路径：EXPLAIN 输出若不是 DuckDB 计划，先查 duckdb.extensions 是否有 autoload 的 mooncake、duckdb.allow_community_extensions 是否开启。
  • 读状态断点（Rust 侧）：`moonlink/src/moonlink/src/table_handler.rs` 的 event_loop、`union_read/read_state_manager.rs` 的 try_read 是两条链路的咽喉。
  • 读状态断点（C++ 侧）：`duckdb_mooncake/src/storage/mooncake_scan.cpp` 的 MooncakeMultiFileList::LazyInitialize 观察文件裁剪；`mooncake_table_metadata.cpp` 的 GetDeleteFilter 观察位图合并。
  • chaos 测试：moonlink 内置 chaos-test feature（故障注入重放框架），是理解崩溃语义的最佳教材。
🎓 结语 pg_mooncake 用约 940 行扩展代码 + 一个独立引擎，把“实时 CDC → Arrow 内存列存 → Parquet/Iceberg → DuckDB 向量查询”整条流水线装进了 Postgres 进程。它对“扩展边界”“一致性时钟”“开放格式”三个问题的回答，比任何单个组件的实现都更值得借鉴——这也是把它作为湖仓/HTAP 架构教学样本的价值。
