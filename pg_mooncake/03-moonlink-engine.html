moonlink 引擎核心：每表一个 actor 的流式列存引擎

moonlink 是整个系统真正的“发动机”：12 个 crate 组成的独立 Cargo 工作区，负责把变更流变成 Parquet 文件、把快照变成 Iceberg 提交、把任意 LSN 变成一致的读视图。

3.3 TableHandler：每表一个 actor

moonlink 最核心的并发决策：每张表一个单线程 actor。所有对该表状态的变更（追加、删除、提交、flush、快照……）都被封装成 TableEvent 投进一个容量 32768 的 mpsc 队列；一个专职任务串行消费。耗时操作（写 Parquet、Iceberg 提交、压缩）不占队列——spawn 出去，做完把结果再作为事件投回队列。

图 3-2 · TableHandler actor 模型：队列进 → 串行处理 → spawn 慢活 → 结果事件回流，全流程无锁

3.4 TableEvent：一张表的“指令集”

moonlink/src/moonlink/src/table_notify.rs:69 定义了约 20 种事件，可归为四类——理解它们等于理解引擎的全部行为：

类别事件语义
数据流Append / Delete / Commit / CommitFlush
StreamAbort / StreamFlush、StartInitialCopy / FinishInitialCopy、AlterTable / LoadFiles		来自 CDC/REST/初始拷贝的行级变更与事务边界；流式大事务使用独立的 Stream* 事件族

3.7 Union Read：引擎如何“给出一个可扫描的文件清单”

扫描请求（scan_table_begin(db, table, lsn)）最终落到 ReadStateManager::try_read。它做三件事（union_read/read_state_manager.rs:90）：

  1. 等水位：在 watch 通道上等待，直到四个 LSN 水位覆盖请求的 lsn（不变式成立）。
  2. 算差异：快照里的磁盘 Parquet 文件 + 已提交但仍在内存的数据物化成临时 Parquet（temp/inmemory_<table>_<tid>_<version>.parquet，无压缩、用完即删）+ 删除向量（Puffin 引用 + 内存 position deletes）。
  3. 出契约：打包成 ReadState——bincode 的 MooncakeTableMetadata { data_files, puffin_files, deletion_vectors, position_deletes }，同时钉住对象存储缓存句柄（引用计数），返回给调用方；scan_table_end / Drop 时释放并清理临时文件。
🔑 为什么叫 Union Read 读视图 = 磁盘文件 ∪ 内存物化文件 − 删除。牺牲一次小小的临时文件写，换来“任何已提交 LSN 都能立即给出一致的列存视图”，这是亚秒级新鲜度的关键——查询不必等 flush。
