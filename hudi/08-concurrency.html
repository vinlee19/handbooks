并发控制与 ACID：锁、冲突校验与时间线原子性

Hudi 的 ACID 建立在三件事上：timeline 文件的原子重命名、可插拔的 LockProvider、以及提交前的 OCC 冲突校验。默认 Snapshot Isolation 允许不同 fileGroup 并行写，冲突只在文件集相交时发生。

01提交协议

图图 8-1 · 提交协议：锁 + 冲突校验 + timeline 原子推进

每个写客户端在提交前通过 TransactionManager 获取锁（LockProvider 实现：Zookeeper / DynamoDB / FileSystem / 存储 SQL 等），随后 ConflictChecker 拿自己的写入文件集与「并发未完成 instant」的文件集比对，相交即失败。

02冲突的粒度

默认 Snapshot Isolation：两个写者只要不写同一个 fileGroup 就能同时提交；这使多管道（流批）写同一张表的不同分区成为常态。需要更严格时开启 hoodie.write.concurrency.mode 与早期冲突检测（写入过程中周期性比对，尽早失败省算力）。

元数据表自身也是 Hudi 表，其提交复用同一套协议；对 HBase / Record Index 这类外部索引，rollback 时会回写撤销记录，保证索引与数据最终一致。

03与 Timeline 的配合

锁只保护「校验 + 提交」的临界区；真正的原子性来自 timeline 文件的重命名。锁丢失或进程崩溃时，inflight instant 由后续写者按 CH02 的恢复语义处理（rollback 或续跑）。
