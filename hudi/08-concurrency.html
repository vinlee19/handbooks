并发控制与 ACID：锁、冲突校验与时间线原子性

Hudi 的 ACID 建立在三件事上：timeline 文件的原子重命名（真相）、可插拔的 LockProvider（互斥）、提交前的 OCC 冲突校验（正确性）。默认 Snapshot Isolation 允许不同 fileGroup 并行写，冲突只在文件集相交时发生。

01提交协议的临界区

图图 8-1 · 提交协议时序：取锁 → 校验 → 提交 的临界区，以及两种失败路径

临界区很短：取锁 → ConflictChecker.hasConflict() → 写 completed instant → 放锁。数据写入本身在临界区之外——这正是乐观并发的意义：锁的争用只发生在提交瞬间。

校验逻辑（SimpleConcurrentFileWritesConflictResolutionStrategy）：拿自己成功的文件集，与 timeline 上所有「并发未完成/已完成」instant 的文件集求交集；相交 → HoodieWriteConflictException。metadata 变更（schema）与表服务 instant 有专门的比对规则。

02隔离级别

默认 Snapshot Isolation：只校验写写文件集冲突，允许「A 读的文件被 B 改写」这类可串行化理论上的异常（对湖仓场景通常无害）。开 hoodie.write.concurrency.mode=optimistic_transaction_control 后可选 Repeatable Read / Serializable：提交时会检查「本事务读过的文件是否被并发提交修改」。

早期冲突检测（early conflict detection）让写客户端在写入过程中周期性比对并发 timeline，尽早失败、节省算力——长任务对撞时收益明显。

03锁提供者与恢复

LockProvider 接口的实现：ZookeeperBasedLockProvider、DynamoDBBasedLockProvider（AWS 官方推荐，含条件写自旋）、FileSystemBasedLockProvider（HDFS 原子 rename）、存储 SQL 锁。锁配置（路径/表/重试）全部在 HoodieLockConfig。

锁过期后的正确性由 timeline 兜底：即使锁服务失灵导致两个写者同时进入临界区，completed 文件的重命名仍只允许一个成功（存储层原子性），另一个会发现目标 instant 已存在而失败。

04元数据表与外部索引的并发

MDT 自身是一张 Hudi 表：主表提交时同步提交 MDT（文件清单、bloom、record index 的更新），复用同一套锁与冲突校验。HBase / Record Index 等索引在 rollback 时回写撤销记录——因此「索引与数据最终一致」由协议保证，而非碰运气。
