APACHE HUDI SOURCE STUDY · CH 01

Hudi 总体架构：为湖上增量处理而生

传统数据湖的目录里只有一堆不可变的 Parquet：追加一条记录要重写整个分区，更新一条记录无从谈起，并发写互相覆盖。Hudi（Hadoop Upserts Deletes and Incrementals）用三个正交机制破解这三个问题，并把它们统一在一条时间线协议之下。本章建立全局心智模型并给出完整的模块地图与版本演进脉络。

01三个问题与三个机制

问题一：更新与删除。对象存储上的 Parquet 文件不可变，改一条记录唯一的办法是重写整个文件。Hudi 的答案是 FileGroup + FileSlice：把「记录住在哪里」稳定下来（fileId 永不变名），更新时只重写该文件组对应的文件，其他文件毫发无损。更新因此在物理上退化为「追加新版本」，代价与命中文件数成正比而不是与表大小成正比。

问题二：更新的定位。要改一条记录，得先知道它在哪个文件里。全表扫描定位太贵，Hudi 引入 Index：把 record key 映射到 fileGroup 的映射关系持久化下来——Bloom filter（随 base file 内嵌）、Bucket（哈希预分区）、外部 KV（HBase）、元数据表（Record Index）。写入前用 index.tagLocation() 一次性打标。

问题三：并发与一致性。多个写客户端同时提交，谁赢？Hudi 引入 Timeline：每次提交是时间线上的一个 instant，文件以「重命名」原子可见，提交前用 OCC 冲突校验——文件集不相交即可并行。时间线还顺带解决了崩溃恢复（inflight 残留可判定）与增量消费（instant 区间即变更集）。

一句话心智模型：Timeline 记录「何时发生了什么」，FileGroup 回答「数据住在哪里」，Index 回答「怎么找到它」。三者正交，其余一切都是实现细节。

02总体架构图

图图 1-1 · Hudi 总体架构：七个参与方围绕 Timeline 协作（所有交互都以 instant 为协议单位）

图中七个参与方的每一次交互，最终都会落到 timeline 上的某个 instant：写入客户端产生 commit/deltacommit；表服务产生 compaction/clustering/clean；rollback 产生回滚 instant。查询引擎是唯一的「只读者」，它通过 FileSystemView 消费 completed instant 之后的稳定视图。

注意架构的对称性：写入客户端与表服务是对等的 timeline 参与者——compaction 调度出的 plan 本身就是一个 requested instant，它和数据写入的提交走完全相同的协议。这使 Hudi 的所有组件天然可审计（timeline 上的每个 instant 都有内容）、可重放（inflight 幂等）、可并发控制（同一套冲突校验）。

03COW 与 MOR：一条分界线贯穿全库

Hudi 支持两种表类型，由 HoodieTableType 枚举定义。下表是它们在源码层的完整对照：

维度COW（Copy-On-Write）MOR（Merge-On-Read）
提交 action.commit.deltacommit
update 物理路径重写整个 base file（MergeHandle）追加 log block（HoodieAppendHandle）
写延迟高（写放大 = 重写整文件）低（只追加增量）
读路径纯 Parquetbase + log 实时合并（或退化为 ReadOptimized）
compaction无此概念必须（否则 log 无限增长）
典型场景批处理 ETL、OLAP 直查CDC 秒级同步、高频 upsert
小文件问题写入即合并（partitioner 处理）靠 compaction/clustering 收敛

这条分界线在源码里随处可见：HoodieTable 的实现类分叉为 HoodieSparkCopyOnWriteTable / HoodieSparkMergeOnReadTable；写入 handle 分叉为 HoodieMergeHandle（COW 更新）/ HoodieAppendHandle（MOR 追加）；甚至查询侧也有专门的 Read Optimized 视图（只看完成 compaction 的纯 base）。读任何一段 Hudi 代码，先问「这是 COW 还是 MOR 分支」。

04仓库模块地图（逐目录）

hudi-common 是地基，不依赖任何计算引擎：common/table/timeline/（instant 与存储 IO）、common/table/（HoodieTableMetaClient、HoodieTableConfig、TableFormat 版本）、common/table/view/（FileSystemView 视图层）、common/table/log/（日志块读写）、common/model/（HoodieRecord/HoodieKey/payload）、metadata/（元数据表 MDT 客户端）、common/fs/（HoodieStorage 存储抽象）。

hudi-client 是写侧引擎：BaseHoodieWriteClient / BaseHoodieTableServiceClient 骨架、index/ 各索引实现、transaction/（TransactionManager、ConflictChecker、lock/ 各 LockProvider）、marker/（防部分写）、action/ 各 action 具体执行器（commit/compaction/clustering/clean/rollback）。

hudi-spark-datasource 是 Spark 绑定（DefaultSource、HoodieSparkTableFactory、Spark 合并执行器）；hudi-flink-datasource 是 Flink 绑定（含 ContinuousFileStoreSource 与 compaction 算子）；hudi-hadoop-mr 提供 Hive/Presto/Trino 的 InputFormat；hudi-aws（DynamoDB 锁、S3 事件通知器）、hudi-gcp（BigQuery 同步）提供云上实现；hudi-cli 是运维工具；hudi-timeline-service 承载集中式视图与 marker 服务。

还有一个横切模块值得单独记住：Metadata Table（MDT）（org.apache.hudi.metadata.HoodieBackedTableMetadata）。它本身是一张 MOR 小 Hudi 表，托管四类信息：文件列表（免对象存储 List）、column stats（免读 footer 做裁剪）、bloom filter（免读文件 footer）、record index（key→位置）。对象存储时代它几乎是必开项（hoodie.metadata.enable=true）。

05Table Format 版本演进

Hudi 用 HoodieTableVersion 管理表格式版本（1-8），版本号写在 hoodie.properties，升级通过 upgrade 命令（hudi-cli）单向推进：

版本关键变化
1-4早期格式：timeline v1、bloom 内嵌 base
5timeline v2（归档优化）、六字节 log magic
6扁平化文件布局（timed layout）：文件不再按 fileGroup 建子目录，文件名自带时间戳；marker 语义收紧
7Transaction Timestamp 精度提升；log 块序号全局化
8Record Index 稳定化、二级索引支持（secondary index）

读源码时版本分叉集中在 HoodieTableVersion.currentVersion() 的判断处——很多「为什么这里有个 if」的疑问都源于此。

06贯穿全库的四个设计决策

① 一切皆 instant。数据写入与表服务共用一套提交协议，这让 compaction 可以独立部署在异构引擎上，也让运维操作（clean/rollback）天然可审计可重放。

② 物理不可变。base file 写出后不再修改，更新 = 新文件 + timeline 记录。这把一致性难题转化为「重命名 + 引用切换」，完美适配对象存储。

③ 视图层解耦。查询和表服务都不直接碰文件系统，而是问 FileSystemView 要「某个 fileGroup 在某个 instant 的切片」。物理布局因此可以自由演进（v6 的扁平化等）。

④ 增量一等公民。任何消费者都可以按 instant 区间拉取变更（incremental query / CDC），不需要额外构建变更管道——写入时留下的元数据已经足够。

07读码路线建议

第一遍沿「写入主干」：BaseHoodieWriteClient.upsert() → index.tagLocation → UpsertPartitioner → HoodieMergeHandle → commit（对应 CH04）。第二遍沿「元数据」：HoodieTableMetaClient → HoodieActiveTimeline → FileSystemView（CH02/03）。第三遍再读表服务与并发（CH05/08）。每章末尾的交互图可在 interactive/ 查看动态版。

表类型在 DDL 与配置层的体现

建表时 hoodie.datasource.write.table.type（或 Flink 的 table.type）决定 COW/MOR，写入 hoodie.properties 的 hoodie.table.type 字段，此后不可更改（只能重建表）。 preorder 字段还有 hoodie.table.name、hoodie.table.version、hoodie.timeline.layout.version、hoodie.table.base.file.format（PARQUET/ORC）等。MetaClient 初始化时严格校验这些字段——读 HoodieTableConfig 就是读一张表的身份证。

HoodieWriteConfig：全库参数的收口

所有写侧行为都由 HoodieWriteConfig（构建器模式）承载：索引选择、并行度、小文件阈值、compaction/clustering/clean 触发、marker 模式、schema 演进策略、锁配置……参数超过 400 个，按 hoodie.xxx.yyy 命名。源码里每个引擎的 ConfigClass 会把 SQLConf/FlinkConfig 的键映射过来。读参数文档不如直接读 HoodieWriteConfig.Builder 的 setter——每个 setter 的 javadoc 就是语义说明。

Timeline Server：集中式架构

默认架构下每个 Spark executor 都要建 FileSystemView、查索引、写 marker——写放大与重复扫描随并行度线性增长。Timeline Server 模式把这三件事集中到一个常驻服务：executor 通过 RPC 请求视图分片与 marker 代写。相关配置 hoodie.embed.timeline.server（Driver 内嵌）或独立进程部署。这是大集群 + 对象存储场景的推荐形态，也是理解 Hudi「服务化演进」的关键。

三大表格式对比中的 Hudi 定位

与 Iceberg（纯快照 + 隐藏分区，无内置更新索引）、Delta（日志即表，写路径绑定 Spark/Databricks 生态）相比，Hudi 的差异化在：内置更新索引（upsert 的一等公民）、记录级增量语义（incremental/CDC 不需要额外 diff 计算）、表服务一体机（compaction/clustering/clean/rollback 全内置）。代价是概念复杂度最高——这也是本手册存在的原因。

一次 INSERT 的端到端旅程（快速预览）

以 COW 表的 spark.write.format("hudi").mode("append") 为例：① DefaultSource 构建 HoodieInternalV2Table → ② WriteIntoHoodieTable 命令 → ③ HoodieSparkSession.createHoodieWriteClient（含 MetaClient 加载、索引初始化、锁管理器）→ ④ tagLocation 打标 → ⑤ WorkloadProfile + UpsertPartitioner → ⑥ 各分区任务写 parquet（marker 先行）→ ⑦ WriteStatus 收集 → ⑧ 提交协议。后续章节就是这条链的逐站放大。

多模态写入：precombined validator

输入流可能自带重复 key（CDC 上下游重试），hoodie.combine.before.upsert=true 时 Hudi 在写入前按 key 做 preCombine（用 payload 的 combineVal 比较保留最新）。preCombine 的比较函数由 payload 决定（DefaultHoodieRecordPayload 按 ordering field 比较）——这也是「ordering field 设错导致数据回退」事故的根源。

Hudi 的失败模式总览

写失败的三类：① 提交前失败（数据写了一半）→ marker 检测 + rollback 清理；② 提交临界区失败（锁丢失/冲突）→ inflight 残留由后续写者 rollback；③ 提交后失败（post-commit hook 如 MDT 同步失败）→ 表数据正确但索引滞后，MDT 按需重建。三类失败都不需要人工介入数据修复——这是「timeline 即真相」的直接收益。
