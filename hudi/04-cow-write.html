COW 写路径：从 upsert 到一次原子提交的八步

BaseHoodieTableServiceClient.upsert() 是 Hudi 写侧的主干道：索引打标 → 工作负载画像 → 分区器派发 → 写新 base → marker 防泄漏 → 冲突校验 → 提交。本章沿这条链逐站拆解，每一站的类名、决策点与调优参数都标出来。

01主流程总览

图图 4-1 · COW upsert 全流程：八个阶段与两处保护（marker + OCC）

入口 upsert(javadDRecordRDD, instantTime)：先 index.tagLocation()，把每条记录标注为「update（已有 fileId）」或「insert（新 key）」；随后构造 WorkloadProfile（按分区的 update/insert 工作量画像），交给 UpsertPartitioner 生成 Spark 任务；执行后汇总 WriteStatus，最后走提交协议。

02Index 阶段：决定记录去哪

tagLocation 输出带 HoodieRecordLocation（instantTime + fileId）的记录流：命中旧 fileGroup 的标 update（位置 = 该组当前 slice），未命中的标 insert。这一步的代价就是索引实现的代价（CH06）：Bloom 索引要读候选文件的 bloom，Bucket 索引是纯计算，Record Index 查 MDT。

索引还有第二个职责：提交成功后 updateLocation() 把新 key 的位置回写进索引（Bloom 无需回写——它随 base file 自带；Record Index/HBase 需要）。

03Partitioner：update 与 insert 的不同命运

update 记录：按 fileId 分组——同组记录合并为一个任务，交给 HoodieMergeHandle：读旧 slice 的 parquet 逐行与更新记录按 key 合并（payload.merge），写出全新 base file。insert 记录：先尝试填充小文件（SmallFileAssignPolicy），填不下的开新 fileGroup 交给 HoodieCreateHandle。

任务并行度由 hoodie.upsert.shuffle.parallelism 控制；WorkloadProfile 还会为每个分区的写入量估算，用于全局小文件平衡（SmallFileCompare）。

04Marker：对象存储上的防部分写

S3/OSS 没有原子重命名，「写一半的文件」会被 List 看到。Hudi 的解法：写数据文件之前先写一个 marker 文件，提交前由 MarkerFiles（MarkerType.DIRECT 或 timeline-server 聚合模式）核对「marker 数 = 成功数据文件数」。不等则本次写失败：触发 rollback 清理半成品。频繁失败的场景可开 hoodie.write.markers.timeline_server_based.enabled 把 marker 写放大降一个量级。

05提交：OCC 与索引回写

WriteStatus 汇总为 HoodieCommitMetadata 后进入 CH08 的提交协议：取锁 → 冲突校验 → 写 timeline。成功后回调 index.updateLocation() 维护外部索引，并触发 inline 表服务（compaction/clustering/clean 的调度钩子）。

Bulk Insert 是同一骨架的轻量分支：跳过 index（不查旧位置，直接新建），适合首次装载。HoodieBulkInsertDataInternalWriter 在 Spark 3 上走 vectorized 路径。
