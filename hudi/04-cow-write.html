COW 写路径：从 upsert 到一次原子提交

COW 的写路径是一条经典的「索引打标 → 工作负载画像 → 分区器派发 → 写新文件 → 打点防泄漏 → 提交」流水线。BaseHoodieTableServiceClient 是它的骨架，理解这条链就理解了 Hudi 写侧 80% 的代码。

01主流程

图图 4-1 · COW 写入流水线：index 打标 → 分区分组 → 执行替换 → 提交

BaseHoodieTableServiceClient.upsert() 首先调 index.tagLocation()：对每条 HoodieRecord 查它属于哪个 fileId（不存在则标为 insert）。随后 WorkloadProfile 按「是否命中已有 fileGroup」把工作分成 update 与 insert 两组，交给 UpsertPartitioner 生成 Spark 任务。

02写文件与防部分写

COW 的更新 = 重写整个 base file：HoodieMergeHandle 读旧 slice、与新记录合并、由 HoodieCreateHandle 写出新 parquet。insert 走 HoodieCreateHandle 直接新建 fileGroup（受小文件策略 SmallFileAssignPolicy 影响可能填进旧组）。

对象存储没有原子重命名，Hudi 用 marker 机制防部分写：写每个文件前先落 marker（marker/marker-type/），提交前 MarkerFiles 校验「所有 marker 都有对应数据文件」，否则判定失败并清理，杜绝读到半成品。

03提交与冲突

全部 WriteStatus 汇总成 HoodieCommitMetadata；提交前经 TransactionManager 取锁、ConflictChecker 与并发 instant 比对（CH08），通过后 transitionState 到 completed。

Bulk Insert 与 Delete 复用同一骨架，只是 partitioner 与 handle 不同；replacecommit 用于 clustering 与整分区替换（HoodieReplaceCommitMetadata）。
