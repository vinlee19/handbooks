Timeline：把每一次变更变成时间线上的一个点

Timeline 是 Hudi 的心跳：所有写入、表服务、运维操作都表现为时间线上的一个 instant（HoodieInstant）。它的文件形态简单到极致——.hoodie/ 目录下的一批小文件——却支撑起了 ACID、崩溃恢复、增量消费与表服务调度。本章从三要素、状态机、文件形态到源码走读完整拆解。

01Instant 的三要素

HoodieInstant 由三部分组成：timestamp（形如 20240115103000000 的字符串，由 HoodieActiveTimeline.createNewInstantTime() 生成，保证单调）、action（做什么）、state（做到哪）。三者的组合唯一确定一次表变更，也是文件命名的全部依据。

图图 2-1 · instant 三要素与状态机：文件名 = 时间戳 + action + 状态后缀

注意文件命名细节：completed 状态的文件没有状态后缀（{ts}.{action}），requested/inflight 有显式后缀。文件按文件名排序即时间序——Hudi 从不依赖文件 mtime（对象存储 mtime 不可靠）。

02状态机：两个迁移方法就是全部

状态迁移只有两个入口：HoodieActiveTimeline.transitionState(instant, newState)（重命名）与 saveAsComplete(metadata)（写内容 + 重命名）。所有 action 执行器都遵守「先 requested（需要计划时）→ 再 inflight → 最后 completed」的纪律。

requested 阶段对数据写入是可选的（直接 inflight），但对 compaction / clustering 是必须的：计划（哪些 fileGroup、怎么合并）先持久化为 requested instant，执行器崩溃后计划不丢，任何引擎都能接手执行——这是「表服务可独立部署」的基石。

03commit 文件里有什么

completed 的 commit 文件内容是 HoodieCommitMetadata（avro 序列化，兼容 json 视图）：顶层是 partitionToWriteStats——每个分区下每个 fileGroup 的写入统计（文件路径、新增行数、更新行数、总行数、文件大小）；replacecommit 额外带 partitionToReplaceFileIds（被整组替换的文件）。

查询路径几乎不读 commit 的业务内容，只读它的 文件清单 部分（经由 FileSystemView 缓存）；而 Incremental Query 与 CDC 则会深入解析它，输出 instant 区间内的变更。

04HoodieActiveTimeline 源码走读

getActiveTimeline() 时 MetaClient 会扫描 .hoodie/ 目录，把文件名解析成 instant 列表缓存。filterCompletedInstants() / filterInflights() / filter(f) 是流式过滤器；lastInstant()、nthInstant(n)、findInstantsBeforeOrEquals(ts)、findInstantsAfter(ts,n) 服务于增量查询与 Time Travel 定位。

写入 IO 只有两条：saveToPending(action, content) 写 requested/inflight 内容，saveAsComplete(action, content) 完成提交。二者都以 HoodieActiveTimeline 持有的 HoodieStorage（封装 FileSystem / object store）为底座——这也是云存储适配的单一收口点。

05Archival：时间线的垃圾回收

高频写入会让 active timeline 无限增长，扫描变慢。HoodieArchivedTimeline（配合元数据表）把老 instant 归档到 .hoodie/archived/ 的列存文件里。归档按「保留窗口 + 最老活跃 instant」划线，归档后 active timeline 恢复小文件状态。

读源码注意：HoodieTableMetaClient.reloadActiveTimeline() 在任何可能的外部变更（多写者场景）之后必须显式调用，否则拿到的是缓存的旧时间线——这是并发调试时最常见的坑。

06崩溃恢复的完整语义

结合状态机与文件形态，崩溃恢复不需要任何分布式协调：残留 inflight 说明执行中断——数据写入类 action（commit/deltacommit）由 rollback instant 撤销（删除半成品文件、回写索引撤销记录）；表服务类（compaction）则可以直接删除 requested/inflight 重试，因为计划是幂等的。

rollback 本身也是 instant（action=rollback），其元数据记录被回滚的目标 instant 及删除的文件清单——所以回滚同样可审计、可追溯。
