索引体系：record key 如何找到自己的文件组

索引是 Hudi 更新效率的命门：HoodieIndex.tagLocation() 把每条待写记录映射到它所属的 fileGroup，这个映射的实现决定了写入的延迟与扩展性。六个实现各有清晰的适用边界，两个开关（canIndexLogFiles / isGlobal）决定行为分叉。

01接口契约

图图 6-1 · 索引家族全景：tagLocation 的六种实现与两种关键开关

HoodieIndex 抽象类只有两个核心方法：tagLocation(HoodieRecordRDD) 给每条记录打上 HoodieRecordLocation（instantTime + fileId，update 语义）；updateLocation(WriteStatus) 在提交成功后回写新增 key。两个配置 canIndexLogFiles（MOR 日志是否索引）与 isGlobal（key 跨分区唯一性）在每个实现里有不同答案。

02Bloom Index：为对象存储而生

默认实现。四步：① bucketRecords 用 interval tree 按 key 范围把记录与候选文件配对（依赖 keyGenerator 生成可比对的 key）；② 并行读每个候选文件的 bloom filter（base file footer 内嵌，或 MDT 托管版本——后者避免为查索引而随机读数据文件）；③ bloom 可能误报，命中的文件再读实际 key 列精确比对（KeyLookupHandle 批处理）；④ 比对命中 → update，未命中 → insert。

代价模型：一次 upsert 的索引成本 ≈ 候选文件数 × bloom 读取。数据按 key 聚得越紧（排序/聚簇），候选越少越快——这就是「写入前排序」对 Hudi 特别重要的原因。

bloom 参数：hoodie.bloom.index.filter.type（DYNAMIC 按文件大小动态调大小 / SIZED 固定）、hoodie.bloom.index.expected.insertion.rate（预期装入率，默认 0.05）、hoodie.bloom.index.parallelism（bloom 读取的并行度）。误报率越高精确比对越贵——动态 bloom 会按文件记录数自动扩容位数组。

03Bucket Index：用布局换查找

HoodieBucketIndex 彻底跳过「查找」：hash(record key) 决定 bucket（BucketIdentifier.bucketId），bucket 即 fileGroup——写入 O(1)，且天然把同 key 数据聚在一起。代价：bucket 数量建表时固定（hoodie.bucket.index.num.buckets）。ConsistentBucketIndex 用一致性哈希环支持扩缩容，代价是需要额外的迁移元数据。

Bucket Index 与 keyGenerator 的关系：bucket 只按 key 哈希，不感知分区——同 key 永远落同一 bucket，分区由写入时的 partition path 决定，因此它天然要求 isGlobal=false 语义下的本地唯一。

04Record Index：元数据表托管

0.14+ 的演进方向：key→location 存进 Metadata Table 的 record index 分区，由 Hudi 自管（随表 commit 自愈、随 rollback 撤销）。读取 O(1)（哈希分片 + 执行器本地缓存），无外部依赖，天然支持 MOR 的 log 索引与二级索引（secondary index）构建。开启方式 hoodie.metadata.record.index.enable=true + 一次性 bootstrap。

05选型决策树

外部 KV 可接受 + 超低延迟 → HBase；key 分布稳定 → Bucket（性能最稳）；要跨分区更新 → GlobalBloom/Record Index(globally)；其余 → Bloom 或 Record Index。所有索引都要回答一个问题：rollback 之后索引如何自愈——Bloom 随文件消失自动正确，HBase/Record Index 靠回写撤销记录。
