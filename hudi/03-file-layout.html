文件布局：FileGroup、FileSlice 与 Log File 的字节级细节

Hudi 的目录布局刻意保持「分区 / 文件组 / 切片」三层结构：fileId 是记录的身份（永不变名），commit 是切片的版本（时间线驱动），base 不可变、MOR 追加日志。本章从目录树一路讲到 log block 的字节级格式。

01三层布局全景

图图 3-1 · 三层布局全景：分区目录 → FileGroup → FileSlice → Base/Log

与 Parquet 目录的最大差异在于：Hudi 的文件名携带 fileId + 写入时间（如 fg-id-v1.parquet），从而「文件的身份」与「文件的版本」都可从文件名推断——文件系统视图的重建因此不需要任何额外元数据。

02Base File：比 Parquet 多一个 footer

base file 是标准 Parquet，外加 Hudi 自己的 footer 块（HoodieFooter）：写入 commit instant、schema、以及 bloom filter（若启用）。bloom filter 按 hoodie.bloom.index.filter.type 选择 DYNAMIC/SIZED，写入时 HoodieCreateHandle 按 key 构造。

记录级元数据还有 record key 与分区路径列（MetaColumns）：_hoodie_commit_time、_hoodie_commit_seqno、_hoodie_record_key、_hoodie_partition_path、_hoodie_file_name 五列前缀由 HoodieRecordPayload 写入，是 merge 与审计的物理依据。

03Log File：字节级格式

log file 由 HoodieLogFormatWriter 追加，结构为「块序列」：每块以 6 字节 HOODIE_MAGIC（#HUDF#）开头，随后是块长度、HoodieLogBlockHeader（instantTime、blockType、schema、owner class）、块体、以及 HoodieLogBlockFooter（总长度用于完整性校验）。

五种块类型：AVRO_DATA_BLOCK（upsert/insert 的记录序列）、DELETE_BLOCK（整行删除的 keys）、COMMAND_BLOCK（rollback 命令，让 reader 跳过被回滚块）、CORRUPT_BLOCK（写坏后的占位，reader 跳到下一 MAGIC）、HFILE_DATA_BLOCK（HFile 格式变体）。块达到 hoodie.logfile.data.block.max.size（默认 256MB，常调小）就滚动新文件。

读取端 HoodieLogFormatReader 逐块读：校验 MAGIC → 读 header → 按 schema 反序列化 → footer 校验长度。CORRUPT_BLOCK 的存在使「写一半崩溃」的日志仍可安全地读到已完整写入的块。

04v6 格式与布局演进

传统布局把同一 fileGroup 的版本放子目录；table format v6（HoodieTableVersion.SIX）起支持扁平化（timed layout）：文件名携带版本时间戳，直接放分区前缀下。这减少了小目录数量，对对象存储的 List/事务更友好。视图层通过 HoodieTableMetaClient.getTableFormatVersion() 分叉处理。

05FileSystemView：把物理组装成逻辑

FileSystemViewManager 按表创建 HoodieTableFileSystemView：扫描分区 → 按 fileId 聚成 FileGroup → 每个 group 内按 instant 排出 FileSlice → 缓存。提供 getLatestFileSlice(partition)、getLatestBaseFile()、getAllFileSlices()、getLatestMergedFileSliceBeforeOrOn()（Read Optimized 用）等 API。

多写者场景下视图可能过期，sync() 增量刷新；服务端化形态（Timeline Server）把视图集中缓存，避免每个 executor 重复扫描——这是 0.13+ 的默认推荐架构。
