CHAPTER 03 · TRANSFER ENGINE

Transfer Engine 架构：统一数据传输层

Transfer Engine（TE）是 Mooncake 的"网卡之上的操作系统"：对上暴露一个 submitTransfer(TransferRequest) 的统一接口，对下适配 19 种硬件传输后端，中间完成拓扑发现、选路、建链、流控与故障切换。本章拆解它的三层类结构、初始化流程、元数据服务与握手协议。

3.1三层类结构：外观 → 实现 → 调度

TE 采用经典的外观模式，源码分三层：TransferEngine（include/transfer_engine.h）是用户唯一接触的类，几乎所有方法都是转发；真正的实现在 TransferEngineImpl（include/transfer_engine_impl.h）；底下的执行调度由 MultiTransport（transport 注册表）与 TransferMetadata（元数据/握手）分担。外观类同时持有 V1 与 TENT 两个后端指针，通过环境变量 MC_USE_TENT / MC_USE_TEV1 切换（src/transfer_engine.cpp:394 附近），为新一代引擎的灰度替换留了通道。

3.2初始化流程：init() 的七步

TransferEngineImpl::init()（src/transfer_engine_impl.cpp）是理解 TE 的地图。它完成端口规划、元数据接入与 transport 自动安装：

  1. 资源上限：setFilesLimit() 把 RLIMIT_NOFILE 拉满（RDMA QP/大内存映射都吃 fd）；
  2. 身份解析：解析 local_server_name（昇腾下格式特殊 ip:port:npu_x）；
  3. RPC 端口：三种模式 —— 旧版指定端口 / P2PHANDSHAKE（随机端口 + 无元数据中心）/ 默认随机端口（15000–17000，可 MC_TCP_BIND_ADDRESS 绑定），端口信息注册进元数据中心；
  4. 元数据接入：按 conn string 的协议头（etcd://、redis://、http://、p2p://）创建 TransferMetadata；
  5. 拓扑发现：MC_CUSTOM_TOPO_JSON 优先，否则 Topology::discover()；
  6. 自动装 transport：有可用 HCA → 装 rdma；无 HCA 或 MC_FORCE_TCP → 装 tcp；再按编译宏叠加 GPU 直通类 transport（nvlink/hip/ascend/maca/cxl…）；
  7. 发布自身：updateLocalSegmentDesc() 把 segment 描述符（含每个 buffer 的 lkey/rkey 数组）写入元数据中心，等待被发现。
图 3-2init() 七步流程与 transport 自动装配决策树（源码：transfer_engine_impl.cpp init() / multi_transport.cpp installTransport()）

3.3元数据服务与 TCP 握手协议

TE 的一切"发现"都围绕 SegmentDesc（节点描述符）展开：每个节点把自己的名字、协议、网卡设备列表、拓扑矩阵、已注册内存（buffer 地址 + 每张网卡的 lkey/rkey）打包成 JSON，写进元数据中心。对端 openSegment("hostA") 时拉取并缓存。数据真正传输前还要一次 TCP 握手：发起方通过 SocketHandShakePlugin 与对端交换 gid/lid/qp_num，双方各自把 QP 状态机推进到 RTR/RTS，RDMA 链路才建立。

图 3-3一次跨节点传输前的完整协调时序：注册 → 发现 → TCP 握手 → RDMA 数据

3.4核心数据结构：SegmentDesc 与 TransferRequest

TE 的公开 API 极小，全部围绕两个结构：SegmentDesc 描述"网络上有什么"（静态拓扑与内存布局），TransferRequest 描述"搬什么"（动态请求）。理解这两个结构，TE 的其他代码都能自行看懂。

SegmentDesc（transfer_metadata.h）

name 节点名 · protocol 协议（决定选哪个 transport）
devices[] 每张网卡的 name/lid/gid
topology 位置→HCA 优先矩阵（cpu:N / cuda:N / *）
buffers[] 已注册内存：addr/length + lkey[]/rkey[]（每 HCA 一个）
nvmeof_buffers[] / cxl_* / rank_info(昇腾)

TransferRequest（transport/transport.h）

opcode READ / WRITE
source 本地地址（必须已注册）
target_id 对端 SegmentID · target_offset 对端偏移
length 字节数 · advise_retry_cnt
结果经 getTransferStatus(batch_id, task_id) 轮询：
WAITING→PENDING→COMPLETED/FAILED/TIMEOUT

BatchID 的取巧设计：allocateBatchID(n) 直接 new BatchDesc 并把指针值当作 ID 返回（multi_transport.cpp）。热路径上省掉一次 ID→对象查表；代价是调用方必须保证 batch 在传输完成前不释放（freeBatchID 会拒绝释放未完成的 batch）。
V1 与 TENT 并存：仓库同时孵化着新一代引擎 tent/（支持 tcp/rdma/shm/nvlink/mnnvl/gds/io_uring/ascend 等后端，自带独立运行时与 Python 绑定），通过 MC_USE_TENT=1 即可在同一外观 API 下切换。日常读 V1 源码即可，两者接口语义一致。
