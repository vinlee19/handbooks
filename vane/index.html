Vane 是一个多模态原生的分布式 AI 数据引擎：把 vendored DuckDB（v1.5.5 fork）改造成可跑在 Ray 集群上的分布式引擎，并把 AI 调用（embedding / prompt / 推理）做成 SQL 计划里的一等算子。全链路 Arrow，Python + SQL 双接口。

C++ ~5.0 万行Python ~9.7 万行vendored DuckDB ~50 万行Apache-2.0

二、三层物理结构

Vane 的代码分三层，每层职责清晰、边界干净：

层位置规模职责
Python 包vane/~202 文件公开 API（vane.sql / connect / ai.embed）、Runner 编排（local / ray / fte）、AI Provider、DataSource/DataSink、ADBC DBAPI
pybind11 绑定层src/vane_py/~140 文件唯一原生模块 vane._native：DuckDBPyConnection / Relation / Expression、UDF 与 VLLM 执行器、Ray 绑定（ray_cxx）、FILE 读取器

构建链：pyproject.toml（PEP 517）→ build_backend.py（注入 DuckDB 源标识）→ scikit-build-core → CMake（cmake/duckdb_loader.cmake 静态编 DuckDB + httpfs）→ 单一 _native.so，只导出 PyInit__native 与 vane_adbc_init 两个符号——原生 ADBC 驱动就是这同一个 so。

三、核心原理（六条主线）

1. 惰性 Relation 代数 + 上游 DuckDB 规划管线

vane.sql() 对无参 SELECT 只解析并包成 QueryRelation，不执行；.filter()/.project()/.aggregate() 每次返回新的不可变 Relation 子类节点（external/duckdb/src/include/duckdb/main/relation/*.hpp）。真正执行发生在 fetch/execute：ClientContext → Binder → Planner → Optimizer → PhysicalPlanGenerator，这条规划管线原封不动复用上游 DuckDB。

2. AI 调用是一等公民算子，而不是 UDF 外挂

这是 Vane 对引擎最深的定制。SQL 宏 ai_prompt(...) / ai_embed(...) 背后是隐藏标量函数 __vane_ai_*（src/vane_py/ai_sql_functions.cpp），其 bind 阶段回调 Python（vane.ai._sql）构建执行规格；优化器里挂入 UDFProjectRewriter / VLLMProjectRewriter（external/duckdb/src/optimizer/optimizer.cpp:231），把它们改写成新增逻辑算子 LOGICAL_UDF_PROJECT / LOGICAL_VLLM_PROJECT，最终由 PhysicalUdfInOut（流式 Python 批执行）或 PhysicalVLLM（原生推理算子，C++ 侧 prefix 分桶）执行。Python 的 rel.map_batches(fn)、rel.embed()、rel.prompt() 全部收敛到这同一条算子路径。

3. Runner 抽象：一份计划，三种执行

VANE_RUNNER 环境变量在 C++ 侧分叉（pyrelation.cpp:1000）：未设置 → 本地向量化执行；local-fast → LocalRunner 在单机按 FTE 语义跑同一份分布式计划；ray → RayRunner 导出 PyLogicalPlan 交 Ray 集群。Runner 按 DatabaseInstance 缓存，连接关闭时通知清理（PR #187 的连接所有权模型：每个 Relation 持有 connection_owner 防 GC 提前回收）。

4. 分布式执行：碎片（Fragment）+ FTE + Flight

引擎内新增 src/execution/distributed/：DistributedPhysicalPlan 把 DuckDB 物理计划翻译成 DistributedPipelineNode 树（Scan/HashJoin/BroadcastJoin/AsOfJoin/CrossProduct/Repartition…，见 translator_join.cpp 的策略选择：≤10MiB 自动广播、等值键哈希重分区、非等值/ASOF/cross 先收拢）。每个节点 produce_tasks()（C++20 generator）产出携带碎片物理计划的 WorkerTask 流。容错由 FTE 层承担：任务 attempt 状态机（PLANNED→QUEUED→RUNNING→FINISHED/FAILED/…）、split 队列重放、投机执行与撤销、租约/准入泵/压力记账——没有 checkpoint，恢复 = split 重放 + attempt 重试。数据面：sink 先写节点本地磁盘 IPC 文件（ShuffleCache），消费方经进程本地 Flight 服务 DoGet 拉取（无 DoPut/DoExchange），server_epoch 围栏陈旧 ticket。

5. 连接快照：Worker 环境的可重建性

驱动不搬运工件，而是把"环境描述"序列化成连接快照（logical_plan_bindings.cpp:1244：duckdb_source_id、静态扩展及版本、动态扩展描述符（SHA-256 钉住 + 信任链）、契约身份、非默认设置、attached 数据库声明）。每个 Worker 准入前重建出逐字节一致的 DatabaseInstance；CREATE SECRET 永不传输，凭据走显式通道。

6. 多模态 = 类型系统 + 流式 DataSource

不新增 IMAGE/VIDEO 逻辑类型，而是：文件引用是 FILE 结构体（URL/CONTENT_TYPE/POSITION/SIZE/CHECKSUM，五字段免凭证），张量是 TENSOR(child, shape) 原生类型；视频经 VideoFrameSource（decord，~10MiB 分区，内存水位背压）变成 TENSOR 列流，由核心 datasource_scan 表函数以纯 C 的 ArrowArrayStream 回调扫入引擎——Python 对象不进引擎，只见函数指针。

四、设计理念

🎵 Fork 而非重写

  • 上游 Binder/Planner/Optimizer/向量化执行全保留，subtree 方式跟版
  • 定制点集中：新算子、新类型、分布式层、扩展契约，均可按文件溯源（SPDX 标注 Vane contributors）

🔀 双语言分工

  • C++ 拥有计划与执行；Python 拥有生态与模型
  • 边界只有两种通道：bind 期回调构 spec、执行期 Arrow 批交换

🏹 Arrow 唯一数据面

  • 跨语言、跨进程、跨节点全是 RecordBatch（C 数据接口 / IPC / Flight DoGet / Plasma）

🛡️ 显式信任边界

  • 动态扩展：SHA-256 钉住 + 描述符 v1 + 提供方 entry point，无 autoload/下载
  • Flight 明文无鉴权，明确限定可信集群网络

🧩 扩展即可分布式

  • scan 契约：TableFunctionDistributedScanCallbacks（split 规划/worker bind），Vane 不解释 split 载荷
  • write 契约：DistributedWriteOperatorExtension（FILE_ARTIFACT / CALLBACK 两模式 + Prepare/Finalize 生命周期）

📦 单一原生制品

  • 引擎、httpfs、ADBC 全静态链进一个 so，符号 lockdown + 私有 pybind ABI 标记，防外部扩展误交换 C++ 对象

六、创新点

1️⃣ AI 进计划

LLM/embedding 调用被优化器重写为物理算子，享受计划优化、断点容错与分布式调度——而不是黑盒 UDF。

2️⃣ 嵌入式引擎的分布式化

DuckDB 进程内引擎被拆成可调度碎片，跑在 Ray actor 上；同一份代码在笔记本与集群间无改动迁移（local-fast 与 ray 共用定位计划）。

3️⃣ 连接快照协议

用"环境描述 + worker 重建"替代"环境搬运"，配合 SHA-256 钉住的受信任扩展描述符，兼顾可复现与供应链安全。

4️⃣ 分布式扩展契约

第三方 DuckDB 扩展声明 scan/write 能力即可参与分布式执行；协调者不解释 split 载荷，写路径有严格 Prepare/Finalize/Abort 状态机（含 outcome unknown 语义）。

5️⃣ 磁盘优先的 shuffle

shuffle 落本地 IPC 文件、Flight 只做 DoGet 拉取——push 的可靠性问题变成 pull 的重试问题，天然适配 FTE 重放。

6️⃣ FILE/TENSOR 作为 SQL 类型

多模态以"引用 + 张量"进列存，凭证不进数据；video→tensor→embedding→向量库一条 SQL/Relation 流水线直达。
