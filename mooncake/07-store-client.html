CHAPTER 07 · CLIENT SIDE

Client 深度剖析：内存池、零拷贝与读写全链路

客户端是数据面唯一的执行者：它管理本地内存 segment、对接 Transfer Engine 搬运数据、维护本机热缓存与 SSD offload。本章拆解 RealClient / DummyClient 双客户端设计、内存分配器家族，以及一次 Put 与一次 Get 的完整跨文件调用链。

7.1客户端三层结构与双客户端设计

对外门面是 RealClient（src/real_client.cpp，5400+ 行），内部干活的是 Client（include/client_service.h:72），持有四个关键成员：master_client_（RPC）、transfer_submitter_（数据搬运）、storage_backend_（SSD）、hot_cache_（本机热缓存）。DummyClient 是与 RealClient 配对的"影子客户端"：它自己不管理数据，只通过共享内存把推理进程的 buffer 映射进 RealClient 所在进程——用于"推理进程与存储代理进程分离"的部署（见 7.3）。

7.2内存分配器家族

客户端所有 KV 数据都要落在"已注册 RDMA 的 segment"里。分配器的职责是在大块 mmap 内存上做快速子分配，且分配结果天然携带 RDMA 地址：

分配器位置用途
ClientBufferAllocatorclient_buffer.cpp客户端主分配器：hugepage mmap 大池 + 内嵌两级 bin 的 OffsetAllocator；BufferHandle RAII 归还；支持"视图模式"包装外部指针
OffsetBufferAllocator / CachelibBufferAllocatorallocator.h · cachelib_memory_allocator/Master 段内分配器（二选一，--memory_allocator），默认 offset
ShmHelpershm_helper.cppmemfd_create+mmap 创建跨进程共享段，fd 经 Unix socket 传递（见 7.3）

7.3DummyClient：跨进程零拷贝

推理引擎（vLLM/SGLang）进程与存储代理进程分离部署时，KVCache 在推理进程的显存/内存里，而 RDMA 注册与传输逻辑在代理进程。DummyClient 的解法是把 RealClient 的 segment 以 memfd 共享内存的方式映射进推理进程：RealClient memfd_create 建段 → Unix socket SCM_RIGHTS 把 fd 发给 DummyClient → 双方 mmap 同一物理内存 → 推理引擎写入的地址经 map_dummy_buffer_to_real 换算成 RealClient 侧地址，直接用于 Put。整条链路没有任何一次 memcpy。

7.4一次 Put 的完整调用链

Put 全链路 · 从 Python 到 RDMA
# Python 侧（mooncake.store / pybind）
store.put(key, tensor_bytes, config)             # → RealClient::put

// ① real_client.cpp put_internal：本地 buffer 分配 + 数据拷入 + 切片
auto handle = buffer_allocator_->allocate(size); // ClientBufferAllocator
memcpy(handle.ptr, data, size);
split_into_slices(handle, slices);                // 按 kMaxSliceSize(≈2MB) 切

// ② client_service.cpp Client::Put：三段式写
master_client_.PutStart(key, slice_lengths, cfg)  // → Master 分配副本，返回 Descriptor[]
for (desc : descriptors) {
  if (desc.is_disk())  storage_backend_.StoreObject(...);   // SSD 副本：写盘后异步 PutEnd(DISK)
  if (desc.is_mem())   transfer_submitter_.submit(...);     // → TE 批量 RDMA WRITE 到对端 segment
}
master_client_.PutEnd(key);                       // 全部成功 → 提交；任一失败 → PutRevoke 回滚

TransferSubmitter（include/transfer_task.h）按副本位置自动选择四种策略之一：LOCAL_MEMCPY（副本在本机 segment，直接 memcpy）、TRANSFER_ENGINE（远端，openSegment 后提交 RDMA 请求）、FILE_READ（DISK 副本走文件接口）、EMPTY。传输结果封装为 TransferFuture，内部轮询 TE 的 batch 状态。

7.5一次 Get 的读路径决策

图 7-3Get 读路径：副本择优 → 热缓存短路 → 传输 → CMS 准入 → 租约复核
LocalHotCache 为什么需要 CountMinSketch：热缓存容量有限，若按"读过就缓存"会把缓存打满成噪声。CMS（带时间衰减的 4096×4 计数器）以 O(1) 空间估计 key 频率，只有多次被读的 key 才值得占用热缓存——这是"频率 + 新近度"的近似 LRU 实现。
