CHAPTER 02 · PHYSICAL ARCHITECTURE

物理架构：硬件、网络与部署形态

软件架构再优雅，最终都要落到物理设备上。本章回答：一个 Mooncake 集群由哪些物理角色组成？一个节点内部 GPU、网卡、内存、SSD 如何连接？哪些流量走 RDMA 数据面、哪些走 TCP 控制面？最后给出一套可落地的 XpYd 部署实例。

2.1集群物理部署总图

一个完整的 Mooncake 集群包含四类物理角色：推理节点（Prefill / Decode，内嵌 mooncake client 与 Transfer Engine）、KVCache 池节点（可以就是推理节点自身挂载的内存 segment，也可以是独立的内存/存储节点）、Master（元数据服务，可热备）与 etcd（segment 注册、HA 选主、OpLog 通道）。所有节点通过两张物理网络互联：RDMA 数据面网络（RoCEv2 / InfiniBand，承担 KVCache 搬运）与以太网管理面（TCP，承担握手、RPC、etcd、指标）。

图 2-1集群物理部署总图：两张物理网络 + 四类角色。KVCache 池节点与推理节点复用同一 RDMA fabric

2.2节点内部：GPU、NIC、NUMA 与存储的物理连接

单节点内部是理解性能的关键。典型 GPU 服务器（以 8 卡 H100/H20 + 4 张 CX-6 为例）的物理拓扑如下：GPU 之间走 NVLink/NVSwitch（节点内 P2P），GPU 与网卡之间走 PCIe Switch，每张网卡物理上属于某个 NUMA 域。Transfer Engine 的拓扑发现（mooncake-transfer-engine/src/topology.cpp 的 Topology::discover）会读取 /sys/class/infiniband 与 /sys/devices/system/node，把"与 CPU 同 NUMA、与 GPU PCI 距离最近"的网卡标为 preferred HCA——这是后续传输选路的物理依据。

图 2-2节点内部物理拓扑：GPU↔NVLink、GPU↔NIC 走 PCIe、DRAM segment 按 NUMA 挂载、SSD 承接 offload

2.4XpYd 部署实例

把以上角色拼成一个可直接落地的 2P4D 部署（2 个 prefill 实例、4 个 decode 实例）。路由代理（benchmarks/xypd_benchmarks/proxy_demo.py 或 vllm_v1_proxy_server.py）按缓存亲和性把请求派发给 prefill 实例；prefill 算完 KVCache 后通过 TE 直写 decode 节点显存或写入 KVCache 池。

图 2-4XpYd 部署实例：prefill 与 decode 完全解耦，KVCache 是两者唯一的耦合点
部署实践要点：① 客户端需要 ulimit -l unlimited（memlock）注册 RDMA 内存；② 用 MC_MS_FILTERS 限制挂载的网卡白名单；③ 大容量 segment 建议开启 hugepage；④ 无 etcd 的最小部署可用 mooncake_http_metadata_server 或 P2PHANDSHAKE 模式（两节点直连，无元数据中心）。
