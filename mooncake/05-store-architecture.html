CHAPTER 05 · MOONCAKE STORE OVERVIEW

Mooncake Store 总体架构：控制面与数据面分离的 KV 池

如果说 Transfer Engine 解决"怎么搬"，Mooncake Store 解决"搬什么、搬到哪、何时淘汰"。它的答案是一条贯穿始终的设计纪律：Master 只管理元数据，数据永远在节点间点对点直传。本章建立 Store 的全景认知，第 06/07 章再分别深入 Master 与 Client。

5.1全景：一张图看懂 Mooncake Store

Mooncake Store 是面向 LLM KVCache 的分布式分层 KV 存储。它最重要的架构决策是控制面 / 数据面彻底分离：Master（元数据服务）从不见数据，只维护"哪个 key 的副本在哪台机器的哪段内存里"；真正搬运数据时，客户端拿到副本描述符（内含对端内存地址 + 网络端点），直接通过 Transfer Engine 发起 RDMA 读写。这个决策带来三个直接收益：Master 无带宽瓶颈、Master 故障切换不影响数据面、容量随节点线性扩展。

图 5-1Mooncake Store 全景：Master 只发"地址簿"，数据沿青色路径点对点直传

5.2对象模型：ObjectMetadata 与 Replica

Master 里最核心的两个数据结构：ObjectMetadata（key 级元数据）与 Replica（副本级状态）。每个 key 对应一个 ObjectMetadata（含副本数组、租约、软/硬 pin 标记）；每个副本有自己的类型与状态机。

图 5-2对象模型：ObjectMetadata 聚合多副本，副本类型决定读路径，状态机保证写入原子可见

5.3核心 RPC 接口一览

WrappedMasterService 经 coro_rpc 对外暴露约 50 个方法，最常用的不到 15 个：

接口语义备注
MountSegment客户端注册一段本地内存进全局池幂等；为段创建 BufferAllocator
PutStart / PutEnd / PutRevoke三段式写：预分配 → 数据就位 → 提交 / 回滚PutStart 返回全部副本描述符
GetReplicaList读路径：返回 COMPLETE 副本 + 隐式读租约客户端按"本机内存 > 远端内存 > 本地 SSD > 盘"择优
UpsertStart/End/Revoke存在即原地更新（同尺寸复用 buffer）否则删旧建新
CopyStart/End · MoveStart/End副本复制 / 迁移原语支撑再均衡与 Drain 腾空
Remove / RemoveByRegex / BatchRemove删除（force 可越过租约）REMOVE 同步写入 OpLog（强持久）
EvictDiskReplica客户端淘汰本地 SSD 副本后回报master 删对应 DISK/LOCAL_DISK 元数据
Ping客户端心跳无心跳超时 → 清理其加工中的残留副本
CreateCopyTask/CreateMoveTask/FetchTasks异步任务系统客户端拉取任务并执行
为什么是三段式写：两段式（先分配后确认）让 Master 在数据落地前就能锁定空间与副本位置，避免"写一半发现没空间"的尴尬；processing_keys 让并发写同一 key 时后到者直接失败；PutRevoke 保证失败不留孤儿空间。这是存储系统经典的两阶段提交在内存池上的轻量实现。
与 Redis 的本质区别：Redis 数据流经过服务器，容量与带宽受单机限制；Mooncake Store 的 Master 只是"地址簿 + 裁判"，数据流在客户端之间以 RDMA 直达，容量 = 所有 segment 之和，带宽 = 所有网卡之和。
