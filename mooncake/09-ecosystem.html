CHAPTER 09 · ECOSYSTEM

生态集成：从推理引擎到 MoE、RL 与权重重分片

Mooncake 的价值要靠生态兑现。本章梳理五类集成：推理引擎接入（vLLM 双路径 / SGLang / TRT-LLM）、P2P checkpoint 分发、MoE 专家并行（容错 DeepEP + 自研 IBGDA）、容错集合通信（ProcessGroup），以及新成员——权重重分片规划器 mooncake-reshard。

9.1vLLM 集成的两条路径

Mooncake 接入 vLLM 有两条互补的路，选哪条取决于场景：路径 A（TE 直传）面向 PD 分离——prefill 实例算完 KVCache 后通过 TransferEngine 直接 RDMA 写进 decode 实例的显存，实现是 mooncake-wheel/mooncake/mooncake_connector_v1.py（vLLM KV Connector V1 接口）；路径 B（Store 池化）面向跨请求前缀复用——KVCache 存进 Mooncake Store，任何实例都能按 block 命中读取，vLLM 侧使用内置的 MooncakeStoreConnector，服务端用 mooncake_store_service.py（把 Store 封装成 REST 服务）。

图 9-1vLLM 双路径：A 点对点低延迟（PD 分离），B 池化高复用（前缀缓存）；两者可叠加部署

9.2P2P Store：BitTorrent 式 checkpoint 分发

mooncake-p2p-store（纯 Go，cgo 调 transfer_engine_c.h）解决另一个场景：训练结束的 checkpoint 要分发到上千个推理节点。传统"中心仓库 + 全员拉取"会打满源站出口带宽；P2P Store 把每个节点变成潜在数据源：Register 只登记元数据（etcd key 前缀 mooncake/checkpoint/）不传数据；GetReplica 自动找源边拉边成为新源，拉的人越多总带宽越大。

图 9-2P2P Store：Register 做种 → GetReplica 边拉边种，分发带宽随受众增长

9.3mooncake-ep：容错的 DeepEP（MoE 专家并行）

mooncake-ep 是 DeepSeek DeepEP 的改造版，用于 MoE 推理的 dispatch/combine（token 按专家分发与结果聚合）。两处关键改造：

  • 容错：API 给 dispatch/combine 增加 active_ranks 张量——故障 rank 被剔除出通信集合，token 自动重路由到健康专家（配合 EPLB 专家负载均衡）；
  • 自研 IBGDA 协议栈：src/mooncake_ibgda/mlx5gda.cpp 直接操作 Mellanox mlx5 网卡的 doorbell 与 JIT，实现 GPU 侧发起的低延迟 RDMA 发送（GPU-Initiated 通信，绕过 CPU proxy）。

mooncake-pg：容错 ProcessGroup

MooncakeBackend : c10d::ProcessGroup——替代 NCCL/Gloo 的集合通信后端（all_reduce/broadcast/all_gather），基于 TE 实现，rank 故障后 recover_ranks 恢复、支持弹性扩组（extend_group_size_to）。Python 绑定 pg_py.cpp，自带 nccl-tests 风格 pgbench。

mooncake-rl 与 mooncake-reshard

mooncake-rl：RLHF 场景示例——rollout 引擎与训练引擎之间用 MooncakeDistributedStore 传样本（推理-训练解耦的数据总线）。mooncake-reshard（纯 Python 新模块）：框架无关的模型权重重分片规划器——N-D 逻辑规划 plan_placement_transfer 产出后端无关的 LogicalTransferPlan，再 bind_logical_transfer_plan 绑定运行时地址；KVCache manifest 已预留接口位。
