§1.1设计哲学：SQL 目录 + Parquet

Iceberg 和 Delta 把元数据存成对象存储上的文件树（manifest / JSON commit log），任何元数据操作都要"读一堆文件 + 乐观写文件 + 外部协调"。DuckLake 的回答是：元数据本来就是关系数据，为什么不直接用数据库管？

🗂️ 控制面 = SQL 数据库

28 张元数据表放在一个支持 ACID 的 SQL 数据库里。快照提交 = 一个数据库事务，天然获得原子性、隔离性与崩溃恢复，无需 Time.sleep 式的乐观文件重试协议。

📦 数据面 = 裸 Parquet

数据文件就是普通 Parquet，放在 S3/本地 FS 上，文件里不携带任何格式元数据。任何能读 Parquet 的引擎（Spark/Trino/Pandas）都能直接读数据面。

🔌 引擎面 = DuckDB 扩展

对 DuckDB 来说 DuckLake 是 ATTACH 型 Storage Extension：协议头 ducklake: 触发 attach，之后 schema/table/事务/扫描全部接管，SQL 体验与本地库无异。

💡 源码定位
扩展入口 src/ducklake_extension.cpp:20（LoadInternal）注册 StorageExtension("ducklake")（ducklake_extension.cpp:27），attach 回调在 src/storage/ducklake_storage.cpp:73（DuckLakeAttach）。

§1.7DuckLake vs Iceberg vs Delta

维度DuckLakeIcebergDelta Lake
元数据存储SQL 数据库表（28 张）对象存储 manifest/JSON 文件树对象存储 JSON commit log
提交协议一个 ACID 事务（主键约束兜底）乐观文件 swap + 外部 catalog 协调乐观 JSON 追加 + atomic rename
冲突检测数据库约束 + changes_made 比对重读全部并发 commit 文件重读 log segment
Time TravelAT (VERSION ⇒ n) 查 snapshot 表snapshot 引用链版本跳转
Schema Evolutionfield_id + name_mapping 表field_id（v2）列映射（较晚支持）
小表性能数据可内联进元数据库（零文件IO）每 commit ≥1 文件每 commit ≥1 文件
元数据操作延迟毫秒级 SQL需多轮对象存储往返需 JSON 读写
数据面兼容纯 Parquet，任何引擎可读Parquet + manifest 绑定Parquet + log 绑定
✅ 取舍总结
DuckLake 用"必须有一个 SQL 数据库"换取了控制面的全部优势。代价是数据面与控制面分离后，第三方引擎只能读数据、不能提交——这是有意的架构决策：写路径统一收口到 ducklake 扩展（或 quack 服务器），保证协议简单可靠。
