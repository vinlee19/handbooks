§2.3核心表逐个剖析

◆ducklake_metadata —— 一切从 KV 开始

四列结构 (key, value, scope, scope_id)，scope 决定配置的作用域（全局 / schema / table）。存储：version（格式版本号，迁移链的判断依据）、data_path、encrypted，以及被 schema/table 级覆盖的所有可调参数。

◆ducklake_snapshot —— 每次提交一行

四个递增游标

  • snapshot_id：主键，提交号
  • schema_version：仅 DDL 时递增
  • next_catalog_id：下一个可用的 schema/table/column id
  • next_file_id：下一个 data/delete file id

为什么存"游标"而不是全量状态？

所有目录实体都带 begin_snapshot/end_snapshot 区间，所以"某个快照的世界" = 对每张表做一次区间过滤查询。快照行本身极小（几十字节），提交成本就是一条 INSERT —— 这是毫秒级 DDL 的来源。

◆ducklake_data_file —— 数据面账本

每写一个 Parquet 文件 commit 时插入一行（ducklake_metadata_manager.cpp:259）。除 path/size/row_count 外，四个高价值列：

  • row_id_start：该文件首行的全局 rowid 基址，配合 file_row_number 支撑 DELETE 的定位与 rowid 虚拟列；
  • partition_id + ducklake_file_partition_value：分区剪枝的依据；
  • mapping_id：指向 ducklake_name_mapping，schema 改名后老文件如何读；
  • partial_max：排序键前缀最大值，供 Top-N / 动态过滤器裁剪（读路径 ducklake_metadata_manager.cpp:1354-1403 一带会拼进 WHERE）。

◆时态区间——一行多版本

📐 万能可见性谓词
读任何实体都套用同一模板（见 ducklake_metadata_manager.cpp:1430 附近的 GetFilesForTable）：
WHERE {SNAPSHOT_ID} >= x.begin_snapshot AND ({SNAPSHOT_ID} < x.end_snapshot OR x.end_snapshot IS NULL)
删除 = 闭合 end_snapshot；新建 = 新行 begin_snapshot=提交号。历史版本查询因此永远不需要"恢复"任何状态。
