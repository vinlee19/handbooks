§6.5冲突检测矩阵

细粒度比对在 ducklake_transaction_state.cpp:142-286：把本事务 changes 与快照以来其他事务的 changes_made 逐类对照，命中即抛 TransactionException：

本事务操作 ↓ 遇并发提交 →对方 INSERT（同表）对方 DELETE（同表）对方 DDL（同对象）对方 Compact / Flush
INSERT✅ 允许（纯追加，重试后换新快照基）⚠️ 检查删除的文件集是否与我写的文件重叠表被改/删则冲突视文件集重叠判定
DELETE⚠️ 对方新文件不在我删除范围 → 允许⚠️ 双方都删同一文件 → 允许（rowid 集合并）；文件被重写 → 冲突冲突❌ 与 compaction 互斥
DDL（create/drop/alter schema·table·view·macro）——❌ 同名即冲突（ConflictCheck 模板 :77-138）—
Compaction / Flush 内联视文件集对方删除与我重写的文件重叠 → 冲突—❌ 互斥
⚔️ 关键洞察：约束即锁
快照表主键（snapshot_id 自增）是唯一的全局串行化点。两个事务同时提交 → 数据库层主键冲突立刻暴露，无需应用层锁。此后才轮到 changes_made 语义比对精细裁决。数据库约束承担了分布式锁的角色——这就是"SQL 目录"架构红利的最佳注脚。

§6.6Staged Commit 与服务端提交 ★

17 类暂存表

DuckLakeStagedTableType（hpp:36-54）：COMMIT_HEADER、DATA_FILE、DATA_FILE_COLUMN_STATS、DELETE_FILE、INLINED_DATA/ROW/COLUMN_STATS/DELETE/FILE_DELETE、DROPPED_FILE、FLUSHED_INLINED、COMPACTION(+SOURCE)、NAME_MAP(+ENTRY)、TABLES_DELETED_FROM。

为什么快

普通提交每轮重试都要"重新读最新快照 + 重发整批 SQL"（跨网络）；服务端提交把循环内化，网络成本 O(1)。高并发写入者 + 远程元数据库时收益最大。

能力探测

ProbeServerCapabilities（quack_metadata_manager.cpp:74-86）查 duckdb_functions() 里是否有 ducklake_commit——老服务器自动退回客户端路径，前后向兼容零配置。

§6.7changes_made 协议

每个提交把"我动了什么"序列化进 ducklake_snapshot_changes.changes_made blob（ducklake_transaction_changes.cpp 的 TransactionChangeInformation/SnapshotChangeInformation）。后续事务提交时，用 ParseChangesMade 反序列化所有前序提交，逐一过 §6.5 矩阵。

📦 changes_made 里有什么
涉及的 schema/table/view/macro 集合（drop/create/rename 各自列出）、被删文件集合、被整表清空的表、compaction/flush 记录、新内联表等。它是一份"提交指纹"——足够细以支撑冲突判断，又远小于完整变更内容。
