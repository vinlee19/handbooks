§3.1快照：一条记录、四个游标

结构定义在 src/include/common/ducklake_snapshot.hpp:18，仅 4 个整数——却是全库版本状态的唯一真源：

snapshot_id
主键·提交号·时间旅行坐标
schema_version
仅 DDL 提交时递增
next_catalog_id
下一个目录对象 id
next_file_id
下一个数据/删除文件 id
🔑 为什么是"游标"而不是"状态"？
快照不复制任何数据。查询快照 N 时，用区间谓词 begin_snapshot ≤ N < end_snapshot (或 NULL) 对每张元数据表做过滤，直接"投影"出该时刻的目录世界。插入快照行是提交的最后一个动作，也是唯一需要全局串行化的动作（CH 06 的乐观重试就是抢这个自增主键）。

§3.5Schema Evolution 与 field_id

Parquet 文件一旦写成就不可变。改名、加列之后，老文件怎么读？DuckLake 的答案：逻辑列 id（field_id）作为稳定锚点，物理列名只是投影。

图 3-4 · 改名 + 加列后，老文件与新 schema 的对接
field_id 让"改名"零成本——不重写任何 Parquet；读侧 DuckLakeMultiFileReader::MapColumns（multi_file_reader.cpp:458-519）完成物理名→逻辑名翻译

类型提升（Type Promotion）

int→bigint 等安全提升直接改 ducklake_column.column_type；读老文件时由 reader 按目标类型 cast。跨语义提升（如积分与 decimal 的边界保持）在近期提交中有专门修复。

嵌套类型演化

ducklake_column.parent_column_id 构成列树（struct/list/map），ducklake_field_data.hpp 的 DuckLakeFieldData 在内存中镜像该树，AddField/RemoveField/RenameField 精确到叶子。

compaction 边界

ducklake_schema_versions 记录每张表的 schema 版本号，merge/rewrite 时保证"不同 schema 版本的文件"不会被错误合并（compaction 函数里 can_merge_into_latest 判定）。

CDC 不是事件日志，而是"账本做差"：insertions = 快照区间内新增的文件行；deletions = 删除文件覆盖的行集
💡 与 changes_made 的关系
ducklake_snapshot_changes.changes_made blob 是提交协议的一部分（记录本提交动了哪些表，供并发事务冲突比对，CH 06）；而 ducklake_table_changes() 是面向用户的行级数据 diff。两者共享"区间可见性"思想但层次不同。
