03 · Action 体系：Function/Reducer 二分与流式协议

源码：burr/core/action.py（2021 行）。这一篇讲透：动作的二分模型、装饰器的低.magic 实现、绑定参数 bind、四个条件构造器、safe_expr 的安全 AST 解释器，以及流式动作的生成器协议。

3.1 二分模型：Function（算）+ Reducer（写）

Burr 把一个图节点拆成两个正交职责（这正是 reducer 模式）：

接口职责核心成员源码
Function计算：从 state 读 → 产出结果reads / run(state,**kw)→dict / inputs / is_async()action.py:184
Reducer写入：结果 + 旧 state → 新 statewrites / update(result,state)→Stateaction.py:262
Action二者合一 + 图节点身份name/with_name/single_step/streaming/tags/schema/get_source()action.py:306

Action 的几个细节值得注意：

  • 命名后置：动作实例创建时没有名字，with_name() 通过 copy.copy 返回带名副本（action.py:313-333）——这样同一个动作对象可以在不同应用里挂不同名字，也解释了为什么 with_actions(counter=counter) 用 kwargs 传名。
  • 两个能力开关：single_step（计算与写入合一）和 streaming（可流式）两个 bool 属性（action.py:341-347），引擎据此选择四条执行路径之一（04 篇）。
  • get_source()：用 inspect.getsource 抓取类源码（action.py:353），这就是遥测 UI 能直接显示动作源码的原因。
  • tags：动作别名，halt_after=["@tag:iteration"] 可以按 tag 停（action.py:374-380）。

3.3 @action 装饰器的「零魔法」实现

装饰器没有用任何黑科技：它只是把一个 FunctionBasedAction 实例作为属性挂在函数对象上，再补一个 bind 方法（action.py:1905-1912）：

def __call__(self, fn):
    setattr(fn, FunctionBasedAction.ACTION_FUNCTION,   # 属性名 = "action_function"
            FunctionBasedAction(fn, self.reads, self.writes, tags=self.tags))
    setattr(fn, "bind", types.MethodType(bind, fn))     # 注入 bind 方法
    return fn                                          # 原函数原样返回，仍可正常调用

被装饰的函数依然是一个普通函数——可以单测、可以不带框架直接调用。Builder 侧的 create_action（action.py:2007）负责把属性取出来并 with_name。

参数如何变 inputs

FunctionBasedAction 用 derive_inputs_from_fn（action.py:1184）读取函数签名：

  • 无默认值的参数 → required inputs（运行时必须传）
  • 有默认值的参数 → optional inputs（可用 bind 预绑定）
  • state 与 __ 开头的参数被识别为特殊注入位

bind：部分应用

chat_response = (chat_response
  .bind(prepend_prompt="Context: "))
# bind = copy_func + with_params(**kw)
# action.py:1828-1847

绑定后参数不再出现在 inputs 里，Runner 调用时解包 _bound_params。这是构建「同一动作多角色」的惯用法（12 篇 chatbot 实例）。

3.5 Conditions：边的判断逻辑

条件转移的本质是一个只读函数：Condition(Function)（action.py:697）持有键列表和一个 resolver(state)→bool，run() 返回 {"PROCEED": bool}（KEY 常量，action.py:698）。图遍历时按声明顺序取第一个为真的边（05 篇）。

expr() 的安全边界（源码 docstring 原文强调，action.py:737-753）：expr 内部是 eval(compile(tree,...), None, state.get_all())。传给 eval 的 globals=None 不是沙箱——CPython 会自动注入 __builtins__，攻击者可控的表达式字符串等价于任意代码执行（如 __import__("os").system(...)）。接收用户/外部来源的表达式必须用 safe_expr。

3.7 流式动作与 StreamingResultContainer

流式的核心是一个极简的生成器协议：中间产物 yield (dict, None)，最终产物带状态更新 yield (dict, State)。引擎收到 state is None 就继续流出；收到非 None 就认为该步结束并提交状态。

@streaming_action 的目标形态

@streaming_action(reads=["prompt"], writes=["response"])
def streaming_response(state, **kw):
    resp = client.chat.completions.create(..., stream=True)
    buffer = []
    for chunk in resp:
        delta = chunk.choices[0].delta.content
        buffer.append(delta)
        yield {"response": delta}   # 中间：裸 dict 会被
                                       # 规范化为 (dict, None)
    full = "".join(buffer)
    return {"response": full}, \
           state.update(response=full) # 终态：带 State

若生成器直到结束都没有产出带 State 的终态，引擎会报错（application.py:323-460 的校验逻辑）。

容器的两个职责

StreamingResultContainer（action.py:1420）：

  1. 迭代：__next__ 转发内部生成器；一旦某个 item 的 state 非 None，立即用 process_result（引擎注入的闭包：盖 __PRIOR_STEP 时间戳、提交 _set_state）缓存终值并 StopIteration。
  2. 保证回调恰好一次：__iter__ 的 finally（action.py:1506-1512）无论正常耗尽、提前 break 还是中途异常，都保证执行一次 callback——它负责触发 post_run_step、post_end_stream 钩子。这就是「流式中断也不丢状态、不漏钩子」的机制保证。

.get() = 排空迭代器后返回缓存的 (result, state)。

本篇要点：① Action = Function（reads/run）+ Reducer（writes/update）；② 装饰器零魔法——动作属性挂在原函数上，bind 做部分应用；③ 条件是只读 Function，返回 PROCEED 布尔，expr 有任意执行风险、不可信输入用 safe_expr；④ 流式协议 = 「(dict, None)…(dict, State)」生成器，容器保证状态提交与钩子的恰好一次。
