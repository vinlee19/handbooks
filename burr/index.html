Burr 是什么

Apache Burr（孵化中，前身是 DagWorks 的 Hamilton 状态管理框架）是一个用于构建会做决策的应用的 Python 框架：聊天机器人、Agent、模拟器、多 Agent 协作、RAG 管道，甚至非 LLM 的传统工作流。它的核心思想是——

把应用表达为一张状态机（有向图）：节点是 Action，边是带条件的 Transition，贯穿全局的是一份不可变的 State。

它由三部分组成（对应 README.md:113-117）：

  1. 一个低抽象、零依赖的状态机库（burr/core/）—— 只有 Action / State / Application / ApplicationBuilder 四个核心概念，没有隐藏的 Prompt 模板魔法；
  2. 一套开源的实时遥测 UI（telemetry/ui/ + burr/tracking/）—— 执行的每一步、每个 LLM 调用的 span、每次状态变更都落盘并在浏览器中可视化、可注释、可回放；
  3. 持久化与集成生态（burr/core/persistence.py、burr/integrations/）—— 断点恢复、fork/spawn、SQLite/PostgreSQL/MongoDB/Redis 持久化，OpenTelemetry/Langfuse/Bedrock/Hamilton/Haystack 等集成。
为什么值得精读源码？ Burr 用不到 2 万行 Python 实现了 LangGraph 级别的能力，代码分层极其清晰：核心引擎不依赖任何第三方库；流式执行用纯生成器协议实现；观测系统完全构建在「生命周期钩子」这一个扩展点上。它是学习「如何设计一个可观测的执行引擎」的最佳范本之一。

全局物理架构总图

下图是 Burr 运行时的物理架构：左侧是用户编写的 Python 应用进程，中间是落盘在 ~/.burr 的 JSON 数据层，右侧是独立进程的 FastAPI 追踪服务与浏览器中的 React UI。这套「同机文件共享」的设计让追踪系统对应用零侵入（异步写 JSONL），同时让 UI 能实时刷新。

两个内置「游标」

Application 的当前位置不在内存里，而在 State 的两个双下划线键中（application.py:85-86）：

  • __PRIOR_STEP —— 上一步执行的 action 名，决定下一步走哪条边；
  • __SEQUENCE_ID —— 步数计数器，每步自增，是持久化与追踪的对账主键。

因为游标在 State 里，「断点恢复」就等价于「载入一份 State」—— 这是 Burr 持久化设计最优雅的一点。

执行 API 的四个层级

API粒度返回
run / arun跑到 halt 条件最终 (action, result, state)
iterate / aiterate每步 yield生成器（可逐步观察状态）
step / astep单步(action, result, state)
stream_result / astream_result流式单步StreamingResultContainer

一个扩展点统治观测

追踪、持久化、tracing、并行级联……全部通过 Lifecycle Hook（lifecycle/base.py）挂进引擎，核心代码对它们一无所知：

  • post_application_create → 追踪器写 graph.json
  • pre_run_step / post_run_step → 追踪事件、状态存档
  • pre_start_stream / post_stream_item → 流式观测
