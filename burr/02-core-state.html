02 · State 深度剖析：不可变状态的全部真相

源码：burr/core/state.py（491 行）+ burr/core/serde.py（124 行）+ burr/core/typing.py（147 行）。State 是整个框架的「数据库」——不可变、delta 驱动、可序列化、可类型化。

2.1 State 的本质：包着 dict 的不可变 Mapping

State（state.py:273）继承 typing.Mapping，内部只持有两样东西：

class State(Mapping, Generic[StateType]):
    """An immutable state object. This is the only way to interact with state in Burr."""
    def __init__(self, initial_values=None, typing_system=None):
        self._typing_system = typing_system or DictBasedTypingSystem()
        self._state = initial_values        # 一个普通 dict
  • 读取走 Mapping 协议：__getitem__/__len__/__iter__（state.py:455-469）。取不存在的键时抛出带引导信息的 KeyError（提示你检查上游 action 是否写出该键、是否声明 reads）。
  • 写入只有一条通道：apply_operation(delta)（state.py:302），所有便捷方法（update/append/extend/increment/wipe）都是它的语法糖。
  • 私有键：以 __ 开头的键（如 __PRIOR_STEP）是框架内部游标，action 对它们的修改会在归并时被剥离（04 篇 _state_update）。
为什么不可变？① 引擎可在任意时刻快照/回滚/比较状态；② fork 一份新应用时无需深拷贝防御；③ hooks（追踪器）拿到的 state 永远是稳定快照，不会因后续执行而「变脸」。

2.3 StateDelta：把变更建模成「事务」

每种变更不是「直接改 dict」，而是一个可校验、可序列化的事务对象（state.py:71-266）。抽象类 StateDelta 要求实现四个方法：reads()、writes()、validate()、apply_mutate()——正好构成「读什么、写什么、合法性、怎么改」的完整契约。

2.5 TypingSystem：给 State 装上「类型外壳」

设计

TypingSystem[StateType]（typing.py:35）把「KV 字典」和「你心里的类型化模型」解耦：

  • construct_data(state) —— 把 State 物化成类型化视图（如一个 pydantic 模型），State.data 用 cached_property 惰性缓存（state.py:298-300）；
  • construct_state(data) —— 反向包装；
  • validate_state / state_pre_action_run_type ... —— 校验与类型推导钩子。

默认实现 DictBasedTypingSystem 是个恒等透传（typing.py:130）；PydanticTypingSystem（11 篇）则让整个应用以 pydantic 模型为第一视角。

与 ActionSchema 的配合

ActionSchema（typing.py:94）描述单个 action 的输入/输出/中间结果类型：state_input_type / state_output_type / intermediate_result_type。执行引擎在 _validate_result（application.py:92-100）用它校验 action 返回值必须是声明的类型（默认 dict）。

双层类型体系的意义：TypingSystem 管「全局状态的类型外观」，ActionSchema 管「单个动作的输入输出契约」。两者叠加即可实现「用 pydantic 模型编程、运行时全链路校验」的 guardrails 模式。

2.6 一次真实的调用链

# State 构造与变更（等价展开）
s0 = State({"counter": 5})
s1 = s0.update(counter=6)          # → apply_operation(SetFields({"counter": 6}))
s2 = s1.append(history="hi")      # → apply_operation(AppendFields({"history": "hi"}))
assert s1["counter"] == 6 and s0["counter"] == 5  # 旧状态不变

# 执行期被引擎调用（04 篇展开）
state.subset(*action.reads)        # 只把声明的 reads 交给 action（最小权限）
new_state = reducer.update(result, state)   # action 的写入
_state_update(old, new)            # 归并：剥离 __ 私有键 + 保留删除语义

# 边界处被追踪/持久化调用
payload = state.serialize(serde_kwargs=...) # → log.jsonl 里的一行 JSON
restored = State.deserialize(payload)       # 断点恢复时还原
本篇要点：① State = 不可变 Mapping，唯一写通道是 apply_operation；② 变更是「事务对象」StateDelta，自带校验与序列化；③ 序列化只在追踪/持久化边界发生，两级分发 + 类型标记；④ TypingSystem 提供可插拔的类型外壳。掌握这些，04 篇的引擎逻辑就只剩「调度」没有「魔法」了。
