06 · 生命周期钩子与 Tracing：一个扩展点统治观测

源码：burr/lifecycle/base.py（518 行）+ internal.py（214 行）+ default.py + burr/visibility/tracing.py（490 行）。追踪、持久化、并行级联全部构建在这套钩子协议上。

6.1 Hook 协议：11 个事件 × 同步/异步双版本

每个钩子是一个 ABC，用 @lifecycle.base_hook("<事件名>") 装饰注册（internal.py:80）。装饰器同时做签名校验 validate_hook_fn（internal.py:42）：钩子方法必须 kwarg-only 且带 **future_kwargs——这保证了协议可以向前演进而不破坏旧钩子。

阶段钩子（Sync/Async 成对）触发时机
应用级PostApplicationCreateHookApplication 构造完成（写 graph.json/metadata）
Pre/PostApplicationExecuteCallHook每个公共入口（run/step/...）前后，恰好一次
步骤级PreRunStepHook / PostRunStepHook每步前后；post 带 exception、result、新 state
DoLogAttributeHookaction 内 tracer.log_attributes(...) 时
Span 级PreStartSpanHook / PostEndSpanHook子 span 开/关（LLM 调用等细粒度）
（span 由 TracerFactory 经 contextvar 触达，见 6.4）

另有流式三件套：PreStartStreamHook / PostStreamItemHook / PostEndStreamHook（base.py:382-462）。全部定义见 lifecycle/base.py，LifecycleAdapter 是这 11 个类的 Union 别名（:497）。

6.3 LifecycleAdapterSet：MRO 爬取式派发

注册：爬 MRO 而非显式声明

适配器加入集合时，LifecycleAdapterSet（internal.py:109）遍历它的 MRO（:132-150），发现它实现了哪些钩子 ABC，就把它登记进对应事件的桶：

# 伪代码（internal.py:132-150）
for klass in type(adapter).__mro__:
    if hasattr(klass, "hooks"):      # 装饰器打的标签
        event = klass.hooks
        if issubclass(适配器, AsyncXxx):
            async_buckets[event].append(...)
        else:
            sync_buckets[event].append(...)

效果：实现即注册。你写一个只实现 PostRunStepHook 的类，传给 with_hooks() 就自动只收步骤结束事件。

派发：三个入口

  • call_all_lifecycle_hooks_sync(event, **kw)（:174）—— 同步引擎用；
  • ..._async（:185）—— asyncio.gather 并发跑全部 async 钩子；
  • ..._sync_and_async（:200）—— 同步+异步钩子都要发时（如 astep 遇混合适配器）。
为什么 async 用 gather？钩子之间无序（观测不该有顺序依赖），并发派发让慢的追踪器不拖慢执行关键路径。钩子抛异常会向上传播——追踪器自身应当吞掉并记录自己的错误。

6.4 visibility/tracing：进程内的 span 树

钩子解决「步骤级」观测；span 解决「动作内部」观测（LLM 调用、检索、工具执行…）。实现三件套（visibility/tracing.py）：

类职责源码
ActionSpan一个 span：唯一 id（create_span_id 时间戳+熵）、begin/end 时间、属性字典、子 span 列表:34
ActionSpanTracer上下文管理器工厂：with tracer("openai", span_type="llm"): 开子 span；结束时自动回填:98
TracerFactory每步一个，生产 ActionSpanTracer；持有 lifecycle_adapters 以便把 span 事件发给钩子:283

传递链路：TracerFactoryContextHook（04 篇）在 pre_run_step 把工厂放进 contextvar → 业务代码任意深度 trace(...) 或声明 __tracer 参数拿到工厂 → 开子 span → post_run_step 复位。span 数据最终经钩子流入 LocalTrackingClient 的 pre_start_span/post_end_span/do_log_attributes，写进 log.jsonl。

6.5 写一个自己的钩子

from burr.lifecycle import PostRunStepHook, LifecycleAdapter

class MetricsHook(PostRunStepHook):
    """每个动作结束后打点 —— 实现即注册"""
    def post_run_step(self, *, app_id, partition_key, action,
                      state, result, sequence_id, exception, **future_kwargs):
        status = "failed" if exception else "completed"
        statsd.increment("burr.step", tags=[f"action:{action.name}", status])

app = (ApplicationBuilder()
    ...
    .with_hooks(MetricsHook())      # 可叠加任意多个钩子
    .build())
签名纪律：钩子方法必须全部 kwarg-only 并以 **future_kwargs 结尾——validate_hook_fn 会在注册时强制检查（internal.py:42-64），否则直接报错。这是框架「协议可演进」的代价与保障。
本篇要点：① 11 个钩子事件覆盖 应用/入口/步骤/span/属性/流式 六个层级，sync/async 成对；② 实现即注册（MRO 爬取），派发支持 gather 并发；③ execute-call 与流式的结束钩子都有「恰好一次」的兜底机制；④ span 树是步骤内的细粒度观测，经 contextvar 触达业务代码，最终以扁平事件流落盘。
