1. 解决了什么问题

Daft 想跑在 Ray 上,但又坚决不像 Spark 一样写一个独立的物理 Stage IR。两个原则:

  1. 算子语义是统一的:Filter、Aggregate、Join 不该有"local 版"和"distributed 版"两份实现。
  2. shuffle 落地策略要可换:Spark 风格的"sort & spill"不一定最优,Daft 选磁盘 IPC 缓存 + Arrow Flight pull。

2.2 关键决策:DistributedPhysicalPlan 不是物理树

src/daft-distributed/src/plan/mod.rs:35:

pub(crate) struct DistributedPhysicalPlan {
    query_idx: QueryIdx,
    query_id: QueryID,
    logical_plan: Arc<LogicalPlan>,   // ← 仍然是 LogicalPlan!
    config: Arc<DaftExecutionConfig>,
}

注意它持有的是 Arc<LogicalPlan>,而不是某种 DistributedOp 树。"distributed plan" 其实只是一个惰性描述符,真正的物理化(切 pipeline、决定 shuffle 边界)发生在 pipeline_node::translate 这一步,按 PipelineNode 流式产生 SwordfishTask。

这一设计避免了"一份 logical + 一份 local physical + 一份 distributed physical"三份 IR 的同步成本。

4.2 Runner::run_iter_tables

src/daft-runners/src/runners.rs:102-132:

pub fn run_iter_tables<'py>(&self, py: Python<'py>, lp: LogicalPlanBuilder,
                            results_buffer_size: Option<usize>)
    -> DaftResult<impl Iterator<Item = DaftResult<MicroPartitionRef>> + 'py>
{
    let pyobj = self.get_runner_ref();
    let py_lp = PyLogicalPlanBuilder::new(lp);
    let builder = py.import(intern!(py, "daft.logical.builder"))?;
    let builder = builder.getattr(intern!(py, "LogicalPlanBuilder"))?;
    let builder = builder.call((py_lp,), None)?;
    let result = pyobj.call_method(py,
        intern!(py, "run_iter_tables"), (builder, results_buffer_size), None)?;

    let iter = PyIterator::from_object(result.bind(py))?;
    let iter = iter.map(move |item| {
        let item = item?;
        let partition = item.getattr(intern!(py, "_micropartition"))?;
        let partition = partition.extract::<PyMicroPartition>()?;
        Ok::<_, DaftError>(partition.inner)
    });
    Ok(iter)
}

4.4 Shuffle 数据落盘 + Flight Pull

sequenceDiagram participant MapWorker as Map Worker (Swordfish) participant Cache as InProgressShuffleCache participant Disk as 本地磁盘 IPC participant Server as ShuffleFlightServer participant Client as ShuffleFlightClient participant ReduceWorker as Reduce Worker MapWorker->>Cache: 给 partition_ref_id 写 morsel Cache->>Disk: AsyncFileWriter.write_ipc MapWorker->>Cache: Flush Cache->>Cache: writer_task.await → 收集 file_paths Cache-->>MapWorker: 完成 MapWorker->>SchedulerActor: report partition_ref_id 就绪 SchedulerActor->>ReduceWorker: 派发 task,附 partition_ref_id 列表 ReduceWorker->>Client: pull(partition_ref_id × N) Client->>Server: Flight DoGet (ticket = partition_ref_id) Server->>Disk: 读取本地 IPC 文件 Server-->>Client: stream Arrow batches Client-->>ReduceWorker: MicroPartition ReduceWorker->>ReduceWorker: merge / probe / 继续 pipeline

为什么不直接 Ray object store? Ray 的 in-memory object store 在大 shuffle 量下要 spill 到磁盘,但暴露给程序的接口仍是 "object_ref"。Daft 选择显式管理磁盘 + Flight 协议,好处: - 直接复用现成的 Arrow Flight server / client(行话说叫 zero-copy IPC) - 失败重试时只需重读磁盘,不需要重算 map 阶段 - 避免 Ray object store 的 LRU 淘汰把 shuffle 数据回收掉

5.1 PipelineNode 镜像 Swordfish 算子

src/daft-distributed/src/pipeline_node/ 下每个文件镜像 daft-local-execution 的同名算子,但不在本地执行——而是产生 SwordfishTask(scheduling/task.rs)给 SchedulerActor 派发。

每个 DistributedPipelineNode 的 produce_tasks(&mut plan_context) 方法返回一个 TaskBuilderStream,惰性产生子任务——这就是为什么 DistributedPhysicalPlan 不需要"提前切 stage"。
