1. 解决了什么问题

1.1 三种用户入口需要走同一条优化通道

flowchart LR subgraph User P["Python<br/>col('a') + 1"] S["SQL<br/>SELECT a+1"] U["UDF<br/>@daft.udf"] end subgraph DSL E["同一棵 Expr 树<br/>(Arc&lt;Expr&gt;)"] end subgraph PlanLayer LP["LogicalPlan / 优化器<br/>下推、化简、CBO"] end subgraph ExecLayer EX["RecordBatch.eval_expression<br/>(daft-recordbatch:1267)"] end P --> E S --> E U --> E E --> LP --> EX

关键设计:DSL 层既要好写(用户 Python 端 col() + col() 之类的算子重载)、又要好优化(优化器要做 transform_down / 模式匹配)、还要好执行(eval_expression 一棵树扫到底)。这三件事的"公共子集"就是 Expr 这个大枚举 + Arc 共享的设计。

1.2 一个长期问题:Column 名字、序号、Scope 怎么管?

SELECT a, b FROM t WHERE EXISTS (SELECT 1 FROM s WHERE s.x = t.a)
                                                             ↑↑↑
                                          外层 t 的 a,在子查询里怎么解析?

朴素方案是"全部用 string 名字 + 运行时查 schema",但在以下场景会爆: - Join 重排后列源自 left 还是 right - 子查询里引用外层列(OuterRef) - Bound 阶段算子要快速取列(O(1) by index)

Daft 的答案是显式三态 Column 枚举(下文 §3.2)。

所有变体的 children 都是 ExprRef = Arc<Expr> —— 这意味着相同子树天然共享、clone() 是 O(1) 的引用计数。

2.3 解析三阶段

stateDiagram-v2 [*] --> Unresolved: col("a") / 用户写 Unresolved --> Resolved: LogicalPlanBuilder.<br/>resolve_columns Resolved --> Bound: BoundExpr::try_new(schema) Bound --> [*]: RecordBatch.eval_expression state Resolved { [*] --> Basic [*] --> JoinSide [*] --> OuterRef Basic: Resolved::Basic(name) JoinSide: Resolved::JoinSide(field, side) OuterRef: Resolved::OuterRef(field, plan_ref) }

看图要点:三阶段不是装饰,是强制类型规约 —— BoundExpr 是个 newtype:pub struct BoundExpr(ExprRef)。try_new(schema) 会遍历整棵树,任一列不是 Bound 都直接 DaftResult::Err。这把"列没解析完就被执行"这个 bug 类别在编译器之外又卡了一道。

注意三个细节:

  1. #[allow(clippy::large_enum_variant)](line 221)—— Daft 知道 VLLMExpr 这种大变体会让整个枚举每个实例都按最大变体分配,但因为 几乎总是 Arc<Expr> 共享,所以可以接受。
  2. BinaryOp / IfElse 等结构体变体 = 命名字段,可读性强。
  3. Function { func, inputs } 与 ScalarFn(ScalarFn) 共存 —— 这是历史包袱:旧式内置函数走 FunctionExpr 枚举(functions/mod.rs:36),新式 trait-based UDF 走 ScalarFn(functions/scalar.rs:21)。优化器要同时识别两种(详见 03 篇)。

AggFnMap / AggFnReduce 是 partial+final 两阶段聚合的核心数据结构 —— PushDownAggregation 优化规则会把 Sum(x) 拆成 "scan 侧 AggFnMap(Sum)" + "shuffle 后 AggFnReduce(Sum)",后者聚合前者输出的部分结果。这是分布式聚合"map-side combine"的内部表示。

4.5 Python UDF 如何套到这个体系

@daft.udf(return_dtype=daft.DataType.int64())
def my_double(x):
    return [v * 2 for v in x]

走的不是 ScalarFn 这条路,而是 Expr::Function { func: FunctionExpr::Python(...) }(FunctionExpr 在 functions/mod.rs:36)。理由:Python UDF 需要 GIL、需要序列化、行为不确定,优化器要识别它来做 SplitUDFs 规则(见 03 篇)把 UDF 节点单独切出来调度。

5. 怎么优化的

5.1 优化点速查

# 优化点 不优化会怎样 Daft 怎么做 源码
1 ExprRef = Arc<Expr> 共享 树克隆代价 O(节点数) Arc 引用计数,clone O(1) expr/mod.rs:218
2 BoundExpr newtype 强制约束 列没解析就执行 → 错误延迟 类型系统在编译期/构造期截断 bound_expr.rs:21,25
3 Column 三态显式建模 字符串拼 + 运行时查表 枚举 + 两次显式转换 expr/mod.rs:115
4 AggFnMap / AggFnReduce 拆 必须 shuffle 完整数据 partial+final 两阶段 expr/mod.rs AggExpr
5 FunctionRegistry LazyLock+RwLock 启动时无并发安全 / 频繁加锁 一次写多次读,RwLock 适配 functions/mod.rs:191
6 is_deterministic() 扁平标记 无法做公共子表达式消除 trait 默认 true,UDF 可改 false scalar.rs:76
7 IfElse 短路求值 两边都算 对 mask 分别取分支再合并 expr/mod.rs:283(eval 分发)
8 谓词 IsIn / Between 单独建模 都展开为 OR/AND 单变体让规则识别成 set / range expr/mod.rs:271-275

5.2 is_deterministic 之于公共子表达式消除(CSE)

flowchart LR E1["expr1: f(a)+1"] -->|hash| H["semantic_id"] E2["expr2: f(a)+1"] -->|hash| H H -->|相等| Q{"f.is_deterministic()?"} Q -->|true| CSE["复用一次计算"] Q -->|false| TWICE["分别计算两次<br/>(eg. random())"]

Expr::semantic_id (line 629) 把整棵树折叠成 FieldID,但仅当所有节点的函数都是 is_deterministic 时,优化器才能放心合并。这是个经典但容易写错的细节。

6.2 表达式结构(初始)

  Expr::Agg(
    AggExpr::Sum(
      Expr::Column(Column::Unresolved(UnresolvedColumn{ name: "amount" }))

6.3 6 个阶段的形态

flowchart TB S0["Stage 0: 用户构造<br/>Unresolved column 'amount'"] --> S1 S1["Stage 1: LogicalPlanBuilder.agg(...)<br/>resolve → Resolved::Basic('amount')"] --> S2 S2["Stage 2: Optimizer 跑<br/>PushDownAggregation"] --> S3 S3["Stage 3: AggExpr::Sum 拆<br/>scan 侧 AggFnMap, 全局侧 AggFnReduce"] --> S4 S4["Stage 4: BoundExpr::try_new<br/>amount → Column::Bound{idx=1}"] --> S5 S5["Stage 5: RecordBatch.eval_expression"] --> S6 S6["Stage 6: Series 'total' 输出"]

6.4 Stage 3 拆分前后对比

拆分前 (单机):
  Aggregate
   └── Sum(amount)

拆分后 (分布式):
  Aggregate (final)
   └── AggFnReduce(Sum, partial_sum)
        ↑
     [shuffle by user]
        ↑
  Aggregate (partial, in scan stage)
   └── AggFnMap(Sum, amount)

看出:PushDownAggregation 不仅"挪了位置",还把 AggExpr::Sum 在 DSL 层就拆成了两份不同的 AggExpr 变体。下游执行算子直接吃这两种,不需要再判断"我是不是 partial 阶段"。

8. 未解之谜

  1. Expr::Function 与 Expr::ScalarFn 何时统一? —— 源码里两者并存,ScalarFn 是新派(trait-based),Function 是旧派(FunctionExpr 枚举)。优化器需要同时匹配两套,长期看应该收敛。
  2. #[deprecated] 的 BoundColumn::field —— 源码注释说"name-referenced columns",意味着未来某天 BoundColumn 可能只剩 index: usize(纯位置索引),对优化器影响多大?
  3. semantic_id 的 hash 冲突概率 —— FieldID 是 sanitized 字符串,公共子表达式消除完全靠它。深层嵌套表达式的字符串可能很长,有没有压缩?
  4. Python UDF 跨进程序列化 —— Ray runner 下 UDF 必须用 cloudpickle 跨节点,这部分代码在 Python 端而不在 daft-dsl 里。
  5. Expr 大枚举与 large_enum_variant lint —— 当前 #[allow] 掉了,VLLMExpr 一个变体就比基础变体大很多。在 Arc 共享下问题不大,但深度优化时这件事可能值得 revisit。
