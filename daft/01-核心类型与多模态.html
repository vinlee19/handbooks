1. 解决了什么问题

1.1 多模态 DataFrame 面临的核心矛盾

同一个 DataFrame 里,结构化的 int64 和 变长的 image bytes 怎么共存,还能保住 Arrow 列存的"零拷贝、向量化、可下推"三大美德?

下表展示如果"不用 Daft"的两种朴素做法的代价:

方案 int64 列 image 列 后果
全部 Object (pandas) ✅ 但慢 ✅ 但 GC 压力大 失去向量化
全部 PyArrow ✅ ❌ image 没有原生类型 业务侧自己处理嵌套 struct
Daft ✅ Arrow 原生 ✅ Logical Type 包装 Struct 列存 + 类型语义都保住

3.1 Series —— 类型擦除的多态外壳

// src/daft-core/src/series/mod.rs:32

    pub inner: Arc<dyn SeriesLike>,

简洁到只有一个字段。内部多态通过 trait object dyn SeriesLike 实现:

classDiagram class Series { +inner: Arc&lt;dyn SeriesLike&gt; +data_type() DataType +to_arrow() ArrayRef +from_arrow() Self +cast() Series +equal() BooleanArray +hash() UInt64Array +build_probe_table_without_nulls() } class SeriesLike { <<trait, sealed>> +data_type() +len() +to_arrow() +cast() } class ArrayWrapper~T~ { +0: T } Series *-- SeriesLike : Arc&lt;dyn&gt; SeriesLike <|.. 从图看出:Series 自己几乎没字段,所有类型差异都被吸收进 dyn SeriesLike。下游只要 hold Series,就能用一套 API 处理所有类型 —— 这种风格在 Rust 列存里很少见(polars 用枚举 Chunked<T>),Daft 选择 trait object 是为了插入新数组类型不用改 Series 本身。

3.2 DataArray<T> —— 原生类型数组

// src/daft-core/src/array/mod.rs:40
pub struct DataArray<T> {
    pub field: Arc<Field>,
    data: ArrayRef,           // Arrow 原生数组
    nulls: Option<NullBuffer>,
    marker_: PhantomData<T>,
}

注意一个有意思的设计:data 是 arrow::array::ArrayRef(动态类型),但泛型参数 T 只是 PhantomData。原因是:

  • 在 Rust 这一层用 T 提供编译期类型安全(DataArray<Int32Type> 不能传给 DataArray<Float64Type>)
  • 在内存这一层直接复用 Arrow buffer,避免重复实现一套类型分发

as_slice() 还做了一个编译期布局断言(line 66-81):

const fn native_layout_assert() {
    assert!(std::mem::size_of::<T::Native>() == ...arrow size_of...);
    assert!(std::mem::align_of::<T::Native>() == ...arrow align_of...);
}

这意味着 DataArray<Int32Type>::as_slice() 是真·零拷贝 —— 直接把 Arrow buffer 当作 &[i32] 返回,而 unsafe cast 的合法性由编译期 assert! 担保。

3.5 MicroPartition —— 执行层"标准盒子"

// src/daft-micropartition/src/micropartition.rs:32
pub struct MicroPartition {
    pub(crate) schema:     SchemaRef,
    pub(crate) chunks:     Arc<Vec<RecordBatch>>,
    pub(crate) metadata:   TableMetadata,           // { length }
    pub(crate) statistics: Option<TableStatistics>, // 列级 min/max

构造时强不变量(new_loaded line 59):

  1. 每个 RecordBatch.schema 必须等于外层 schema(assert!)
  2. 若 statistics 存在,其 schema 必须等于外层 schema(assert_eq!)
  3. metadata.length = sum(batch.len())

4. 关键源码走读

4.1 Series::from_arrow:从外部 Arrow 进入 Daft

// src/daft-core/src/series/mod.rs:111
pub fn from_arrow<F: Into<FieldRef>>(field: F, arrow_arr: ArrayRef) -> DaftResult<Self> {
    let field = field.into();
    with_match_daft_types!(field.dtype, |$T| {
        Ok(<<$T as DaftDataType>::ArrayType as FromArrow>::from_arrow(field, arrow_arr)?
            .into_series())
    })
}

with_match_daft_types! 是个类型分发宏:它根据运行时 DataType 值,在编译期展开成对每个 dtype 调用对应的 FromArrow::from_arrow。这避开了 trait object 的虚函数开销。

4.2 Series::build_probe_table_without_nulls:group-by 加速

src/daft-core/src/series/mod.rs:65 是 join / group-by / distinct 的共享底座:

let mut probe_table =
    IndexMap::<IndexHash, (), IdentityBuildHasher>::with_capacity_and_hasher(
        DEFAULT_SIZE, Default::default());

for (idx, hash) in hashed_series.into_iter().enumerate() {
    // 用 raw_entry_v1 + from_hash 显式跳过 hash-of-hash
    let entry = probe_table.raw_entry_v1().from_hash(hash, |other| {
        (hash == other.hash) && self.get_lit(idx).eq(&self.get_lit(other.idx as _))
    });
    if entry.is_none() {
        probe_table.insert(IndexHash { idx: idx as u64, hash }, ());
    }
}

为什么不能直接用 HashMap<u64, _>?

flowchart LR subgraph Naive["朴素方案"] H1["row → hash(row) = u64"] H1 -->|HashMap key=u64| H2["RandomState::hash(u64) 再算一次"] H2 -.过载.-> H3["内层 hasher 又 hash 一次"] end subgraph Daft["Daft 方案"] D1["row → hash(row) = u64"] D1 -->|raw_entry from_hash| D2["IdentityBuildHasher<br/>把 u64 直接当 hash"] D2 --> D3["O(1) 命中"] end

看图要点:Daft 用 IdentityBuildHasher 短路了内层 BuildHasher,直接把外层算好的 hash 拿来用。配合 IndexHash { idx, hash } 同时记录原行号,后续 take(idx) 就能拿回原始数据。这是个很多列存查询引擎都不写出来的实现细节。

4.3 MicroPartition 与 IPC 序列化(分布式 shuffle 用)

src/daft-micropartition/src/micropartition.rs:191 提供了:

  • write_to_ipc_stream() -> DaftResult<Vec<u8>>(序列化到 Arrow IPC 字节流)
  • read_from_ipc_stream(buffer) -> DaftResult<Self>(反序列化)

这是分布式 shuffle 的物理边界:Arrow Flight server(daft-shuffles)拿到的就是这一段字节;接收端反序列化后立即能拿到 MicroPartition,无需重建索引。

6.3 ImageArray 物理布局(stage 3 后)

列 "img" : DataType::Image(Some(RGB))
内部: ImageArray = LogicalArray<ImageType>
  └── physical: StructArray { fields: [
        data:     ListArray<UInt8>      ← 像素 bytes flatten
        channels: UInt16Array            ← 通道数 (RGB=3)
        heights:  UInt32Array
        widths:   UInt32Array
        modes:    UInt8Array             ← ImageMode 枚举
      ]}

每行一张图,变长,但所有元数据列都是定长 → 谓词下推可作用于元数据列

6.4 为何 where(img.height > 256) 不需要解码即可裁

注意 stage 4 的 where:谓词作用在 img.height,而 height 是一个 UInt32 sidecar 列,不需要触碰 data 这个 ListArray。这意味着:

  • 读 sidecar 只是读一段定长 buffer
  • 整张图的 raw bytes 只有在最终 stage 5 才被 Python 拿到

这就是 docs/architecture/index.md 里说的"多模态感知 —— 贵算子尽量延后"在数据层的对应。

8. 未解之谜

  1. SeriesLike trait 是 pub(crate),外部 crate 怎么实现自己的 Array?目前看是不行的 —— 多模态新类型必须落在 daft-core 内部。这是一种"封闭多态"设计,可能是为了避免 ABI 风险。
  2. MicroPartition.statistics 真的能在 shuffle 间隔保留吗? —— write_to_ipc_stream 写的是 chunks,statistics 的传播路径还需要看 daft-shuffles 与 daft-distributed 的 IPC 边界(留给 05-分布式执行.md 解答)。
  3. with_match_daft_types! 宏展开后到底是 match 语句还是 if-else? —— 留个 TODO,需要 cargo expand 验证。
  4. UnionArray 为什么没出现在 Series 主用 API 中? —— 类型推断 Union(Vec<Field>, ...) 是冷门类型,可能仅在 Iceberg 兼容路径出现。
  5. Probeable trait 在 Explore 报告中被提到但本篇没找到主导文件,可能在 daft-recordbatch/src/probeable/ 或 daft-core/src/array/ops/probe.rs,留待 04 篇专门讲 join 时解开。
