04 · Swordfish 本地执行

基准 commit: fa0d066204eae630962af7b22a5ab559ecd454fb (v0.7.10-13) 文档版本: v0.3.0-dev0 / Rust 2024 阅读前置: 03 逻辑计划与优化器 · 06 IO 与扫描下推

1. 解决了什么问题

Swordfish 是 Daft 的本地执行器代号(crate daft-local-execution)。它要解决:

  1. morsel-driven 并行:把单个查询拆成大量 ~10万行 的小 chunk(MicroPartition),让 N 个 CPU worker 同时干活,不要被一个慢算子卡住整个 pipeline。
  2. 背压:慢 sink(写文件)不能让 fast source(顺序扫 Parquet)爆内存。
  3. 算子异质性:UDF、HashJoin build、Sort、Limit 各自有不同的并发上限和 morsel 大小偏好——执行器要配合。
  4. 任务/通道混合模型:既不是 pure push(Volcano-style 倒拉),也不是 pure pull(Snowflake-style 推送)。Daft 用「tokio::select! 事件循环 + bounded channel + JoinSet」的混合模型,由每个算子节点自管 worker 池。
模型 优点 缺点 代表
Pull (Volcano) 简单、流式 函数调用开销大;并行难 DuckDB 旧版
Push (Vectorized push) 缓存友好 推到爆内存,需要显式背压 Polars、Photon
Push + control flow 可暂停 复杂 DuckDB 新 pipeline
Morsel-driven + tokio actor 算子级并行/异步 IO 直接复用 调度更复杂 Daft Swordfish

pub enum MorselSizeRequirement {

    Flexible(usize, NonZeroUsize),     // 区间 [lower, upper]

MorselSizeRequirement::combine_requirements(pipeline.rs:179-214)给出"算子链如何协商 morsel 大小":

当前要求 下游要求 合并结果
None Strict(s) Flexible(0, s)
None Flexible(_, u) Flexible(0, u)
Strict(s) 任意 Strict(s)(本节点优先)
Flexible(l, u) Strict(s) Flexible(min(l,s), min(u,s))
Flexible(l, u) Flexible(l', u') 区间交集;若不重叠 → 退回下游要求

3.3 IntermediateOperator —— 通用算子接口

intermediate_op.rs:41-69:

pub(crate) trait IntermediateOperator: Send + Sync {
    type State: Send + Sync + Unpin;
    type Stats: RuntimeStats = DefaultRuntimeStats;
    type BatchingStrategy: BatchingStrategy + 'static;

    fn execute(&self, input: MicroPartition, state: Self::State,
               runtime_stats: Arc<Self::Stats>, task_spawner: &ExecutionTaskSpawner,
               input_id: InputId) -> IntermediateOpExecuteResult<Self>;
    fn make_state(&self) -> Self::State;
    fn max_concurrency(&self) -> usize { get_compute_pool_num_threads() }
    fn morsel_size_requirement(&self) -> Option<MorselSizeRequirement> { None }
    fn batching_strategy(&self) -> DaftResult<Self::BatchingStrategy>;
}
  • State 是每个 worker 自己持有的可变状态(如 hash table 累积)。
  • max_concurrency 控制 worker 池上限——CPU 算子默认 compute_pool_num_threads,但 UDF / VLLM 等可能需要单实例模型,会重写为 1 或更小。
  • morsel_size_requirement 与 batching_strategy 配合 BatchManager 决定如何把上游的 chunks 拼成本算子需要的 batch 大小。

4.2 next_event —— tokio::select! 事件循环

pipeline.rs:111-146:

pub(crate) async fn next_event<TaskResult: Send + 'static>(
    task_set: &mut OrderingAwareJoinSet<DaftResult<TaskResult>>,
    max_concurrency: usize,
    receiver: &mut Receiver<PipelineMessage>,
    input_closed: &mut bool,
) -> DaftResult<Option<PipelineEvent<TaskResult>>> {
    if *input_closed && task_set.is_empty() { return Ok(None); }
    tokio::select! {
        msg = receiver.recv(),
              if task_set.len() < max_concurrency && !*input_closed => {
            // 上游来 morsel / Flush / 关闭
            ...
        }
        Some(task_result) = task_set.join_next(),
              if !task_set.is_empty() => {
            // 本节点的 worker 跑完了
            ...
        }
    }
}
flowchart TD Start([next_event 循环]) Check{input_closed AND<br/>task_set 空?} Done([返回 None,关闭节点]) Sel{tokio::select!<br/>哪个 future ready?} Cap{worker 数 &lt; max_concurrency?} NewIn[receiver.recv → Morsel/Flush/InputClosed] Wait[等] TaskDone[task_set.join_next → TaskCompleted] Start --> Check Check -->|是| Done Check -->|否| Sel Sel --> Cap Cap -->|是 + receiver 有消息| NewIn Cap -->|否| Wait Sel --> TaskDone NewIn --> Start TaskDone --> Start classDef event fill:#fff2cc class NewIn,TaskDone event

两个 guard 是关键:if task_set.len() < max_concurrency 防止超并发(否则上游灌入会 OOM);if !task_set.is_empty() 在没有进行中任务时不去调 join_next()(否则会立即返回 None 把循环误终止)。

}

5. 怎么优化的:四个工程要点

5.1 动态批次自适应

dynamic_batching/dyn_strategy.rs 实现的策略观察:

  • 上游来的 morsel 是不是太小?——累积直到达到 lower 才 dispatch,合并小 batch 减少 overhead;
  • 算子做完 batch 是不是太慢?——拆分下次 batch 大小,避免单次任务占满 worker。
flowchart LR subgraph 输入序列 A1[1k 行] --> A2[1k 行] --> A3[1k 行] --> A4[10k 行] --> A5[100k 行] end subgraph 静态固定 64k S1[等待 6 次 → 合并成 64k] -.-> S2[100k → 拆为 64k+36k] end subgraph 动态自适应 D1[3k 直接 pass<br/>(若 strategy 允许 low=0)] -.-> D2[10k pass] -.-> D3[100k 单独 pass<br/>(已大于 max,拆成 32k×3 + 4k)] end

5.2 HashJoin 两阶段时序

HashJoin 在 lowering 时分裂为 build + probe(plan.rs:2089 的 HashJoin 变体在 pipeline 构建阶段被切成两个 PipelineNode):

6.2 4 worker 一帧一帧的快照

T = 0s —— pipeline 启动,4 个 SourceNode worker 同时 tokio::spawn:

worker0  worker1  worker2  worker3
[scan]   [scan]   [scan]   [scan]
   │        │        │        │
   ↓        ↓        ↓        ↓
chan(filter) bounded

T = 2s —— Source 开始吐 morsel,Filter 算子下 4 个 worker 并行筛选:

filter.task_set.len() == 4 (满)  ← receiver.recv guard 阻塞
                                    上游 Source 的 send().await 挂起 ← 背压

T = 4s —— 部分 Filter 完成,morsel 流入 HashAgg.Build,Source 继续灌:

Source ──[m]──> Filter ──[m]──> HashAgg.Build (累积 hashtable,无下游输出)

T = 8s —— 所有 Source 都吐完 → Filter 收到 Flush → HashAgg.Build 收到 Flush → finalize:

HashAgg.Build.finalize → 4 个 hashtable merge → 吐到 HashAgg.Output
HashAgg.Output → PhysicalWrite (4 worker 并行写文件)

T = 12s —— PhysicalWrite finalize,把 file metadata 序列化成 MicroPartition → CommitWrite:

CommitWrite.sink × 4 → finalize → 1 次 catalog commit
