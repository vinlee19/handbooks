1. 解决了什么问题

DataFrame / SQL 的"声明式"前端,落到执行器之前必须先变成一棵可重写、可推理、可比较代价的中间表示。Daft 选择自研 LogicalPlan IR(不依赖 DataFusion),原因有三:

  1. 多模态算子不在 DataFusion 词汇表里——UDFProject、VLLMProject、Window、MonotonicallyIncreasingId、StageCheckpointKeys、Shard、AsofJoin 都需要专用变体;
  2. Push-down 边界更激进——Daft 的 Pushdowns 把 filter / projection / limit / aggregation / sharder 一并下到 ScanTask,而不是只下投影和 filter;
  3. 优化是 Python 可观测的——LogicalPlanBuilder.optimize_async 接受一个 observer 回调,每个 batch 的中间快照都能 dump 给 dashboard。
维度 DataFusion LogicalPlan Spark Catalyst Daft LogicalPlan
多模态算子 无 无 UDFProject / VLLMProject / Explode / Window
Pushdown 单元 filter+projection Catalyst rules Pushdowns { filters, partition_filters, columns, limit, sharder, aggregation }
Join 重排 DP-CCP / heuristic DP / GOO DP-CCP(可选)+ 启发式左深
子查询消除 unnest pass rewrite rules UnnestScalarSubquery + UnnestPredicateSubquery
Stats 注入 在物理层 在物理层 EnrichWithStats 是逻辑层 batch
Cycle 检测 否 否 LogicalPlanTracker 哈希去重

3.5 LogicalPlanTracker —— cycle 检测

src/daft-logical-plan/src/optimization/logical_plan_tracker.rs:用 HashSet<u64> 缓存每次 pass 后 plan 的哈希。如果新 plan 的哈希已经见过,则该 batch 立即终止——不一定是真的"等价",而是"我们刚才已经造出过同一个 plan",意味着进入了重复循环。optimizer.rs:355-365 是触发点。

这是 Daft 比 DataFusion 更激进的一个细节:PushDownProjection ↔ PushDownLimit 容易互相回滚(参见 optimizer.rs:175-186 的 TODO 注释),LogicalPlanTracker 提供了硬保护。

4.2 Optimizer::optimize 主循环

src/daft-logical-plan/src/optimization/optimizer.rs:318-332:

pub fn optimize<F>(&self, plan: Arc<LogicalPlan>, mut observer: F)
    -> DaftResult<Arc<LogicalPlan>>
where F: FnMut(&LogicalPlan, &RuleBatch, usize, bool, bool),
{
    let mut plan_tracker = LogicalPlanTracker::new(self.config.default_max_optimizer_passes);
    plan_tracker.add_plan(plan.as_ref());
    self.rule_batches.iter().try_fold(plan, |plan, batch| {
        self.optimize_with_rule_batch(batch, plan, &mut observer, &mut plan_tracker)
    })
}

单批执行:optimize_with_rule_batch(optimizer.rs:335-386)做三件事:

  1. 在 0..batch.max_passes() 循环内反复调用 optimize_with_rules;
  2. 每次产出 plan 都送进 plan_tracker.add_plan,看是否进入 cycle;
  3. 调 observer(...) 把当前快照、batch、pass index、是否变换、是否 cycle 报给上层。
stateDiagram-v2 [*] --> Pass0 Pass0 --> Pass1: rule applied & 新 plan Pass1 --> PassN: rule applied & 新 plan Pass0 --> Done: rule 未变换 PassN --> Done: rule 未变换 / 达到 max_passes PassN --> CycleStop: plan_tracker 命中 CycleStop --> Done Done --> [*]

4.3 单条规则的访问模式

每条规则实现 OptimizerRule::try_optimize,签名固定。绝大多数规则内部 plan.transform_down(|node| ...) 或 transform_up,基于 TreeNode trait(src/common/treenode/src/lib.rs:92)。

PushDownFilter 的骨架(src/daft-logical-plan/src/optimization/rules/push_down_filter.rs:36-44):

impl OptimizerRule for PushDownFilter {
    fn try_optimize(&self, plan: Arc<LogicalPlan>) -> DaftResult<Transformed<Arc<LogicalPlan>>> {
        plan.transform_down_with_subqueries(...).and_then(|t| {
            t.transform_data(|p| p.transform_down(|node| Self::try_optimize_node(node, ...)))
        })
    }
}

Transformed<T> 的语义见 src/common/treenode/src/lib.rs:1500+(枚举,Yes(T) | No(T)),其中 Yes 表示"我改了树,优化器请再来一遍",No 表示"已是不动点"。

4.4 transform_down 访问顺序

src/common/treenode/src/lib.rs:213-330 给出 transform_down 的语义:先访问当前节点,再递归访问子节点。这是大部分 push-down 规则的默认顺序——先在父节点上识别 Filter(child) 模式,再尝试把 Filter 推进 child 内部。

transform_up 语义相反:先递归访问子,再访问当前节点。两者的 macro handle_transform_recursion! 在 src/common/treenode/src/lib.rs:31-37。

5. 怎么优化的:11 个 batch 的执行顺序

src/daft-logical-plan/src/optimization/optimizer.rs:124-238 的 OptimizerBuilder::with_default_optimizations() 把规则编排成 11 个 batch,顺序敏感。

为什么 batch 顺序固定? 几个例子:

现象 必须的顺序 原因
FilterNullJoinKey 在主下推之前 Batch 3 < Batch 5 否则 Filter 已经被推到 Source 下,识别不到 join key
PushDownAntiSemiJoin 单独成 batch Batch 4 与 Batch 5 分开 与 PushDownProjection 同 batch 会出现交换-回滚(注释 optimizer.rs:151-153)
RewriteOffset + PushDownLimit 单独成 batch Batch 6 max=3 否则 limit 与 projection 交替交换永远无法收敛(issue #2616,注释 optimizer.rs:177-179)
SplitUDFs 在主下推之后 Batch 7 > Batch 5 普通投影下推完成后再切 UDF,避免每条规则都要特判 UDF
MaterializeScans 是最后 Batch 13 把 Pushdowns 实际烧到 ScanTask;之前的规则只改 Pushdowns 字段

ReorderJoins 是 with_default_optimizations 不包含的可选 batch,需调 OptimizerBuilder::reorder_joins(cfg, use_dp_ccp)(optimizer.rs:242-257)。源码在 src/daft-logical-plan/src/optimization/rules/reorder_joins/:

文件 作用
mod.rs:27 pub struct ReorderJoins 入口
join_graph.rs 把级联 Join 树压平成无向图(节点=表,边=join 谓词)

DP-CCP 搜索空间(3 表 A,B,C 全连接):
                {A,B,C}
               /   |   \
        {A,B}∪{C} {A,C}∪{B} {B,C}∪{A}
           |        |          |
          AB×C    AC×B       BC×A
           |        |          |
        ((A,B),C) ((A,C),B) ((B,C),A)

DP-CCP 的关键不变量:每个 csg(connected subgraph)与其 complement 都连通时才组合,n 表关系图的 csg-cmp 对数 ≪ n!,把搜索空间从超指数缩成多项式。
