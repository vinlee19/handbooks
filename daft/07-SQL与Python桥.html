pub fn plan(&mut self, input: &str) -> SQLPlannerResult<Statement> {
    let tokens = Tokenizer::new(&GenericDialect {}, input).tokenize_with_location()?;
    // ...预处理:nested_token / 处理 trailing semicolon / ...
    let mut parser = Parser::new(&GenericDialect {})
        .with_options(ParserOptions { ... });
    parser.parse_statement()
}

pub fn plan_sql(&mut self, sql: &str) -> SQLPlannerResult<LogicalPlanRef> {
    let stmt = self.plan(sql)?;
    self.plan_statement(&stmt)
}

Daft 直接复用社区的 sqlparser crate(use sqlparser::dialect::GenericDialect,planner.rs:36),自身不写词法/语法分析器;只在 plan_statement 这一层把 AST 翻译成 LogicalPlanBuilder 操作。

3.5 sql_exec Python 入口签名

src/daft-sql/src/python.rs:38-60:

#[pyfunction]
pub fn sql_exec(
    py: Python<'_>,
    sql: &str,
    session: &PySession,
    ctes: HashMap<String, PyLogicalPlanBuilder>,
    config: PyDaftPlanningConfig,
) -> PyResult<Option<pyo3::Py<pyo3::PyAny>>> {
    let ctes = ctes.into_iter()
        .map(|(name, builder)| (name, builder.builder))
        .collect::<HashMap<String, LogicalPlanBuilder>>();
    if let Some(plan) = execute_statement(session.session(), sql, ctes)? {
        let builder = LogicalPlanBuilder::new(plan, Some(config.config));
        let builder = PyLogicalPlanBuilder::from(builder);
        let builder = builder.into_py_any(py)?;
        Ok(Some(builder))
    } else {
        Ok(None)
    }
}

返回 Option<PyAny> 是因为有些 SQL(如 SET ...、USE ...)不产生 plan,只更新 session state。

4.2 GIL 释放 / 获取标注

run_iter_tables(src/daft-runners/src/runners.rs:102-132)在 Rust 中持有 Python<'py> 标记,但实际执行时:

sequenceDiagram participant App as Python (持 GIL) participant Rust as Rust API participant Tokio as tokio runtime App->>Rust: collect() activate App Rust->>Rust: 包 PyLogicalPlanBuilder Rust->>App: 调 NativeRunner.run_iter_tables (Python) deactivate App activate App App->>Rust: 内部进 NativeExecutor::run Rust->>Tokio: Python::detach_until or block_on (释放 GIL) deactivate App Tokio->>Tokio: 多 worker 并行计算 Tokio-->>Rust: 完成 Rust->>App: Python::attach (重获 GIL) activate App App-->>App: 包成 PyMicroPartition yield deactivate App

Rust 端跑 IO / compute 密集时必须释放 GIL,否则 Python 主线程被卡住。pyo3::Python::detach(以前叫 allow_threads)是关键 API,在 daft-local-execution/src/run.rs 等执行入口内部使用。

5. 怎么优化的:三个工程要点

5.1 SQL 路径完全复用 DataFrame 优化

flowchart LR SQL[SQL → AST] --> LB[LogicalPlanBuilder.filter/select/agg] DF[DataFrame API] --> LB LB --> Opt["Optimizer\n(14 batches)"] Opt --> Phys[Physical Plan] classDef shared fill:#d5e8d4 class LB,Opt,Phys shared

没有 SQL 专属优化器。所有规则(谓词下推、Join 重排、子查询消除——见 03 § 5)对两条路径同等生效。UnnestScalarSubquery/UnnestPredicateSubquery(optimization/rules/unnest_subquery.rs)是子查询消除规则,在 SQL 路径上特别活跃。

5.2 Bindings:作用域正确性

// planner.rs:101
impl<T> Bindings<T> {
    pub fn get(&self, ident: &str) -> Option<&T> { ... }
    pub fn insert(&mut self, name: String, target: T) -> Option<T> { ... }
    pub fn clear(&mut self) { ... }
}

SQLPlanner 自带三套 Bindings: - bound_ctes —— CTE(WITH foo AS ...) - bound_columns —— 当前 select clause 引入的列别名(SELECT a + 1 AS x → 在 WHERE x > 0 时可见) - current_plan.schema —— 当前已选好的 relation 的列

子查询通过 new_child()(planner.rs:184)创建,继承 parent 引用,实现 outer reference resolution。没有 child 自己的 bound_columns 与 outer 混淆——这正是 SQL 标准的 lexical scoping 要求。

5.3 单 cdylib vs 多模块的取舍

方式 优点 缺点 谁用
单 cdylib(Daft) 全局共享 FUNCTION_REGISTRY、零拷贝跨 crate;import 一次全到位 编译时间长(单 crate 链所有 dep);二进制大 Daft、Polars
多 cdylib(per crate) 编译并行;按需加载 跨 crate 调用要走 PyObject 中转;难共享全局态 早期 PyO3 项目
Python 子模块(m.add_submodule) 命名空间整洁 仍是同一个 cdylib;只是 Python 侧分组 DataFusion-python(部分用)

Daft 选择 单 cdylib + 同一命名空间 —— from daft.daft import X 一律到一个 .so/.dylib/.pyd 找符号。相对应,src/lib.rs 的 register_modules 调用顺序也要正确:daft_dsl::register_modules 必须在 daft_logical_plan::register_modules 之前调用,因为后者依赖 PyExpr。

8. 未解之谜

  1. FUNCTION_REGISTRY 的写锁竞争:src/lib.rs:158-186 在 #[pymodule] 初始化时拿 write() 锁,理论上模块加载只发生一次。但如果用户在 worker 进程 fork 后 import daft,LazyLock 会重做一遍初始化吗?(待验证 fork-safety)
