第 01 篇

物理架构与运行形态

先把"哪些东西跑在哪里"讲清楚：你的机器上有几个进程、pi 在磁盘上写了什么、它和云端之间只有哪些连接。这一篇是后面所有源码分析的空间坐标系。

1物理架构总图

Pi 的物理形态刻意简单：默认只有一个进程。你在终端敲 pi，shell fork 出一个 Node（或 Bun）进程，它包办 UI、Agent 循环、模型调用和会话存储。没有守护进程、没有本地服务端口、没有 IPC。它和外界只有三类物理边界：

  • 终端模拟器（另一个进程）：pi 通过 PTY 与它交换字节——读键盘输入字节流，写 ANSI 转义序列做差分渲染。这是唯一的"UI 通道"。
  • 本地磁盘：全局配置与凭证在 ~/.pi/agent/，项目级配置在 <项目>/.pi/，会话是纯 append 的 JSONL 文件。工具（bash/read/edit）直接操作你的项目源码——这也是 README 坦承"无内置权限系统、建议容器化"的原因。
  • 云端 HTTPS：模型 API 的 SSE 流、models.dev 模型目录、npm/GitHub 版本检查。没有任何私有二进制协议。
设计取舍

单进程无守护意味着不存在"pi 服务挂了"这类故障面，会话状态天然落在文件里，任何时刻 kill 掉进程最多丢当前正在流式输出的那半条消息。代价是扩展只能进程内加载（第 06 篇），远程/多客户端场景只能靠实验性的 server-client 形态补齐（第 5 节）。

终端是一等公民而非外设：pi 不假定终端支持什么，启动时逐一探测（Kitty 键盘协议、真彩、图片协议、超链接），探测不到就回退。这是第 07 篇的主题。

2进程内的启动入口

npm 包的 bin 指向 dist/cli.js，由 tsgo 直接从 src/cli.ts 编译而来（无打包器）。入口文件只有 21 行，全部精力花在两件事上：设置进程身份，以及在任何 provider SDK 发请求之前配好 undici 全局 dispatcher（代理、超时）：

packages/coding-agent/src/cli.ts完整文件，21 行
#!/usr/bin/env node
import { APP_NAME } from "./config.ts";
import { configureHttpDispatcher } from "./core/http-dispatcher.ts";
import { main } from "./main.ts";

process.title = APP_NAME;
process.env.PI_CODING_AGENT = "true";   // pi 专属标记
process.env.AI_AGENT = "pi";            // 通用 AI 代理标记（供上游工具识别）
process.emitWarning = (() => {}) as typeof process.emitWarning;

// Configure undici's global dispatcher before provider SDKs issue requests.
// Runtime settings are applied once SettingsManager has loaded global/project settings.
configureHttpDispatcher();

main(process.argv.slice(2));

真正的编排都在 main.ts（972 行）。它先处理 pi auth / pi install 等一次性子命令，然后解析参数、决定运行模式。模式判定逻辑值得逐行读——注意最后一条：stdin/stdout 只要有一端不是 TTY，就自动降级为 print 模式，这让 echo "..." | pi 无需任何标志就能工作：

packages/coding-agent/src/main.tsL118-129 · 模式判定
function resolveAppMode(parsed: Args, stdinIsTTY: boolean, stdoutIsTTY: boolean): AppMode {
  if (parsed.mode === "rpc") {
    return "rpc";
  }
  if (parsed.mode === "json") {
    return "json";
  }
  if (parsed.print || !stdinIsTTY || !stdoutIsTTY) {
    return "print";
  }
  return "interactive";
}

之后 main() 按固定顺序装配运行时，然后一次性分发到对应模式（节选，完整启动流程图见第 04 篇）：

packages/coding-agent/src/main.tsL923-964 · 模式分发
if (appMode === "rpc") {
  printTimings();
  await runRpcMode(runtime);
} else if (appMode === "interactive") {
  const interactiveMode = new InteractiveMode(runtime, {
    migratedProviders,
    modelFallbackMessage,
    autoTrustOnReloadCwd,
    initialMessage,
    initialImages,
    initialMessages: parsed.messages,
    verbose: parsed.verbose,
    tuiMode: parsed.tuiMode,
  });
  printTimings();
  await interactiveMode.run();
} else {
  printTimings();
  const exitCode = await runPrintMode(runtime, {
    mode: toPrintOutputMode(appMode),   // "text" | "json"
    messages: parsed.messages,
    initialMessage,
    initialImages,
  });
  stopThemeWatcher();
  restoreStdout();
  if (exitCode !== 0) {
    process.exitCode = exitCode;
  }
  return;
}

装配阶段的关键步骤（同一函数内，自上而下）：runMigrations() 迁移旧版 auth/session 存储 → createSessionManager() 按 --fork/--resume/--continue/--session 决定打开哪个会话文件 → ProjectTrustStore 判定当前项目是否受信任（决定项目级扩展/技能是否加载）→ createAgentSessionRuntime() 组装三件套（SettingsManager + ModelRuntime + ResourceLoader）并构建 AgentSession。这四步全部完成后，才轮到上面的模式分发。

3四种运行模式

同一个 pi 进程，按 stdin/stdout 的用法分成四种形态。它们的 Agent 循环、工具系统、会话存储完全相同——变的只是"事件如何进出进程"：

模式触发方式stdinstdout典型用途
interactive默认（两端皆 TTY）raw 模式按键流ANSI 差分渲染人类日常编码
print-p 或非 TTYprompt 文本（可选）最终回答纯文本脚本一句话、管道 cat err | pi -p "解释"
json--mode jsonprompt 文本事件 JSONL（首行 session header）程序化消费流式过程
rpc--mode rpc命令 JSONL响应 + 实时事件 JSONLIDE 插件、聊天 bot 等宿主集成
细节：output-guard

非 interactive 模式启动时会调用 takeOverStdout()（core/output-guard.ts）：把 process.stdout.write 换成自己的实现，防止工具输出或第三方库的杂散打印污染 JSONL 协议流。RPC 模式写事件用的是严格 LF 分行的 JSONL（modes/rpc/jsonl.ts）——特意不用 readline，因为 readline 会按 U+2028 行分隔符切分，而 JSON 字符串里可能出现它。

4实验形态：server-client

单进程模型满足不了"多个客户端共享一组会话"的场景（比如 IDE 面板和终端同时操作同一个 agent）。仓库里有一个实验性方案：把 AgentSession 搬进常驻的 pi-server 进程，客户端通过 Unix socket 用 CBOR 二进制协议连接。它与 第 3 节 的 RPC 模式是并存的两套协议——RPC 模式是 coding-agent 内建的 JSONL 子进程协议，server-client 是独立的 CBOR 套接字协议，互不依赖：

形态 B 的角色分工：packages/protocol 定义 TypeBox schema（快照、命令、事件）与 CBOR 编解码；packages/client 是传输无关的客户端 SDK（只要求一个 ByteTransport 接口，自带 Unix socket 实现）；coding-agent 的 src/server/create-harness.ts 把 read/bash/edit/write 四个工具和 system prompt 打包成 pi-agent-core 的 AgentHarness 交给 server 托管。协议细节在第 08 篇展开。
