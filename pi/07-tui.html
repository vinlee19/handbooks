TUI 渲染引擎：字符串、差分与 16ms

16,210 行，零内部依赖的终端 UI 库。它的核心模型朴素到令人意外：组件渲染成 string[]（一行一个 ANSI 字符串），渲染器保存上一帧的数组做逐行全等比较，只重写变化的行。没有 React、没有虚拟 DOM、没有 cell 网格。本篇拆帧循环、差分算法、输入管线与文本渲染管线。

1设计立场

三个反直觉但自洽的决策：

  • 字符串行数组，而非字符网格。终端本身就按行消费输出；把网格状态留在终端进程里，pi 只维护"我上一帧写了哪些行"。双缓冲就是两个 string[]，差分就是 ===。代价是做选区/命中测试时要自己追踪列坐标（alt-screen 的 AnsiCodeTracker 专门干这个）。
  • crash-fast 而非静默裁剪。组件渲染出超宽的行，主屏渲染器写 crash log 后直接抛异常——静默截断会让表格边框错位这类问题变成"灵异现象"，抛错则立即暴露写错的组件。
  • 主屏与全屏分治。承认终端 scrollback 不可编程：主屏模式渲染进自然文档流（终端拥有滚动），全屏模式接管 \x1b[?1049h 备用屏、自带布局引擎与应用级选区。两模式共享同一棵组件树。

2帧循环：16ms 节流 + 输入旁路

所有组件状态变化都只是调 requestRender()。渲染被合并成两种路径：常规路径走 16ms 节流（≈60fps），键盘输入路径绕过节流——注释里写明了原因：Windows 上 setTimeout(0) 也可能耗 16ms，打字延迟不可接受：

packages/tui/src/tui.tsL765-817 · 节流与旁路
requestRender(force = false): void {
  if (force) {
    this.resetRenderState();
    this.requestImmediateRender();
    return;
  }
  if (this.renderRequested) return;          // 已有待渲染帧：合并
  this.renderRequested = true;
  process.nextTick(() => this.scheduleRender());
}

private requestImmediateRender(): void {
  this.cancelRenderTimer();
  this.renderRequested = true;
  if (this.immediateRenderScheduled) return;
  this.immediateRenderScheduled = true;
  process.nextTick(() => {
    this.immediateRenderScheduled = false;
    if (this.stopped || !this.renderRequested) return;
    // A previously queued scheduleRender() can create a timer before this
    // callback runs. User input must preempt that throttled frame.
    this.cancelRenderTimer();                 // 关键：抢在节流帧之前
    this.renderRequested = false;
    this.lastRenderAt = performance.now();
    this.doRender();
  });
}

private scheduleRender(): void {
  if (this.stopped || this.renderTimer || !this.renderRequested) return;
  const elapsed = performance.now() - this.lastRenderAt;
  const delay = Math.max(0, TuiBase.MIN_RENDER_INTERVAL_MS - elapsed);   // 16ms
  this.renderTimer = setTimeout(() => { ... this.doRender(); ... }, delay);
}

每帧的全部输出被收集进单个字符串 buffer 一次 terminal.write()，并用 DECSynchronized Output（\x1b[?2026h/l）包裹——支持该特性的终端会把整帧作为原子操作上屏，杜绝撕裂：

const fullRender = (clear: boolean): void => {
  this.fullRedrawCount += 1;
  let buffer = "\x1b[?2026h"; // Begin synchronized output
  if (clear) {
    buffer += this.deleteKittyImages(this.previousKittyImageIds);
    buffer += "\x1b[2J\x1b[H\x1b[3J"; // Clear screen, home, then clear scrollback
  }
  for (let i = 0; i < newLines.length; i++) { ... buffer += line; ... }
  buffer += "\x1b[?2026l"; // End synchronized output
  this.terminal.write(buffer);      // 一帧 = 一次 write
};

3主屏差分算法

TuiMainScreen.doRender()（约 370 行）是主屏的心脏。全量渲染的四个触发条件先于差分判断（宽度变化=折行全变、高度变化、内容收缩、Kitty 图片行），其余情况走逐行比较：

// Find first and last changed lines
let firstChanged = -1;
let lastChanged = -1;
const maxLines = Math.max(newLines.length, this.previousLines.length);
for (let i = 0; i < maxLines; i++) {
  const oldLine = i < this.previousLines.length ? this.previousLines[i] : "";
  const newLine = i < newLines.length ? newLines[i] : "";
  if (oldLine !== newLine) {              // 整行字符串全等比较
    if (firstChanged === -1) firstChanged = i;
    lastChanged = i;
  }
}

if (firstChanged === -1) {
  // Nothing changed - just reposition the cursor
  this.positionHardwareCursor(cursorPos, newLines.length);
  return;
}

// Kitty 图片块会占据多行：把变更区间扩展到覆盖完整图片块

全屏渲染器 TuiAltScreen 的差分更简单：固定 height 行的屏幕缓冲逐行 === 比较，变化行用 \x1b[row;1H\x1b[2K 定点重写。它额外承担鼠标协议（SGR/X10 解析）、滚动条、应用级文本选区（字符/词/行三种粒度，双击/三击 500ms 判定，松开经 OSC 52 复制到系统剪贴板）与 OSC 8 超链接点击。tmux/zellij 下自动降级为 button-motion 鼠标——复用器转发全 motion 事件会卡。
