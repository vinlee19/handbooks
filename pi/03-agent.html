第 03 篇

pi-agent-core：12,416 行的"智能"本体

Agent 的全部"智能"就是一个循环：调模型 → 模型要工具 → 执行工具 → 结果回灌 → 再调模型，直到模型不再要工具。这个循环是纯函数（agent-loop.ts，796 行），可整段单测；状态管理是薄壳（agent.ts，592 行）；外围 harness 层提供工具、压缩、会话树。本篇逐段拆开它。

1包内部分层

内核对 pi-ai 的依赖只有一个函数形状。注释把契约写得非常直白：

packages/agent/src/types.tsL18-32
/**
 * Stream function used by the agent loop. `Models.streamSimple` satisfies
 * this shape.
 *
 * Contract:
 * - Must not throw or return a rejected promise for request/model/runtime failures.
 * - Must return an AssistantMessageEventStream.
 * - Failures must be encoded in the returned stream via protocol events and a
 *   final AssistantMessage with stopReason "error" or "aborted" and errorMessage.
 */
export type StreamFn = (
  model: Model<Api>,
  context: Context,
  options?: SimpleStreamOptions,
) => AssistantMessageEventStream | Promise<AssistantMessageEventStream>;

上一章的"错误编码进流"契约在这里被再次引用：循环从不 try/catch 模型调用，因为约定它根本不会抛。宿主把 ModelRuntime.streamSimple（一个满足该形状的方法）注入进来，agent 包就与 40+ provider 间接解耦了——这就是"循环是纯函数"得以成立的前提。

2主循环 runLoop 逐段拆解

循环是双层的：内层处理"模型响应 ↔ 工具执行 + steering 消息"，外层只在"agent 本应停下"时检查 follow-up 队列。先看骨架（完整源码 155-275 行，下面按语义切了四段）：

packages/agent/src/agent-loop.tsL163-199 · 双层结构与失败出口
let currentContext = initialContext;
let config = initialConfig;
let firstTurn = true;
// Check for steering messages at start (user may have typed while waiting)
let pendingMessages: AgentMessage[] = (await config.getSteeringMessages?.()) || [];

// Outer loop: continues when queued follow-up messages arrive after agent would stop
while (true) {
  let hasMoreToolCalls = true;

  // Inner loop: process tool calls and steering messages
  while (hasMoreToolCalls || pendingMessages.length > 0) {
    if (!firstTurn) {
      await emit({ type: "turn_start" });
    } else {
      firstTurn = false;
    }

    // Process pending messages (inject before next assistant response)
    if (pendingMessages.length > 0) {
      for (const message of pendingMessages) {
        await emit({ type: "message_start", message });
        await emit({ type: "message_end", message });
        currentContext.messages.push(message);
        newMessages.push(message);
      }
      pendingMessages = [];
    }

    // Stream assistant response
    const message = await streamAssistantResponse(currentContext, config, signal, emit, streamFunction);
    newMessages.push(message);

    if (message.stopReason === "error" || message.stopReason === "aborted") {
      await emit({ type: "turn_end", message, toolResults: [] });
      await emit({ type: "agent_end", messages: newMessages });
      return;                                    // 失败 = 立即整体退出
    }
packages/agent/src/agent-loop.tsL203-222 · 工具调用与截断防御
// Check for tool calls
const toolCalls = message.content.filter((c) => c.type === "toolCall");

const toolResults: ToolResultMessage[] = [];
hasMoreToolCalls = false;
if (toolCalls.length > 0) {
  // A "length" stop means the output was cut off by the token limit, so
  // every tool call in the message may carry truncated arguments. Fail
  // them all instead of executing potentially borked calls.
  const executedToolBatch =
    message.stopReason === "length"
      ? await failToolCallsFromTruncatedMessage(toolCalls, emit)   // 全部拒绝执行
      : await executeToolCalls(currentContext, message, config, signal, emit);
  toolResults.push(...executedToolBatch.messages);
  hasMoreToolCalls = !executedToolBatch.terminate;

  for (const result of toolResults) {
    currentContext.messages.push(result);
    newMessages.push(result);
  }
}
一个容易忽略的安全细节

模型输出被 token 上限截断（stopReason: "length"）时，消息里的工具调用参数 JSON 很可能只写了一半。直接执行会 rm -rf /foo/ba 式地坏掉。pi 的处理是把整批工具调用全部拒绝并生成错误 toolResult——模型下一轮能看到失败原因并自行补齐。terminate 语义：只有当一批结果全部标记 terminate 时循环才提前结束（例如权限门拦截了整批调用）。

三个钩子的分工：prepareNextTurn 是变形钩子（压缩就在这里把旧上下文换成摘要）；shouldStopAfterTurn 是刹车钩子（plan 模式用它限制轮数）；getSteeringMessages/getFollowUpMessages 是油门钩子（把用户中途插话灌进循环）。注意 0.84.4 的一个 breaking change：prepareNextTurn 只在确认还会开下一轮时执行，终止轮不再跑——收尾工作应挂到 agent_end。

AgentMessage 是开放联合类型：宿主可以通过 TypeScript 声明合并塞入自定义消息（coding-agent 用它放 compaction 摘要、custom_message 等），循环全程用 AgentMessage 思考，只在调模型的瞬间经 convertToLlm 折叠成 pi-ai 的 Message[]。循环因此对"会话里还有什么种类的数据"完全无感。

3工具执行流水线

一批工具调用经过三个阶段，每个阶段都有宿主挂载点：

4steering 与 follow-up：双队列

用户在 agent 干活时打的字去哪了？Agent 类持有两个队列，语义刻意不同：

  • steering（插话）："当前这趟活别忘了我刚说的"——在下一个轮次边界注入，干预进行中的工作。
  • follow-up（追加任务）："干完这个再做这个"——只在 agent 本应停止时检查，绝不打断进行中的工作。
packages/agent/src/types.tsL44-50 · 排空模式
/**
 * Controls how many queued user messages are injected when the agent loop reaches a queue drain point.
 *
 * - "all": drain and inject every queued message at that point.
 * - "one-at-a-time": drain and inject only the oldest queued message,
 *   leaving the rest queued for later drain points.
 */
export type QueueMode = "all" | "one-at-a-time";

6压缩与 AgentHarness 脚手架

harness/compaction/compaction.ts（848 行）是纯函数管线：estimateContextTokens → shouldCompact → findCutPoint（含 split-turn 切割）→ prepareCompaction（展开上次 retainedTail）→ LLM 摘要（带重试）→ CompactionEntry。全部可单测；何时触发（阈值、agent_end 时机）留给宿主。算法细节在第 05 篇逐段讲。

最后澄清一个容易困惑的点：AgentHarness（agent-harness.ts，508 行）在 0.84.x 里是一个故意发布的接口脚手架——私有构造器、静态 create() 抛 HarnessNotImplemented("create.restore")、所有操作返回 unavailable。它交付的是完整类型面（11 个 hook 名、RunOutcome、SuspendedOperation）与状态归约器（reducer.ts，667 行）；真正的 harness 驱动实现在 coding-agent 的 src/server/create-harness.ts。读源码时不要在这里找实现。
