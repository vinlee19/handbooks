1Pi 是什么

Pi（@earendil-works/pi-coding-agent，命令 pi）是一个运行在终端里的 AI 编码代理：你用自然语言提需求，它读取你的代码、执行 shell 命令、编辑文件，循环往复直到任务完成。但它对自己的定位不是"一个 CLI 工具"，而是 Agent Harness（代理挽具）——一个可自扩展的代理运行时，CLI 只是用它的公共 SDK 拼出来的第一个应用。

整个仓库是一个 monorepo，按依赖方向严格分层。底层是统一 40+ 家 LLM 供应商的 pi-ai；其上是实现"循环 + 工具调用 + 状态管理"的 pi-agent-core；旁边是一个不依赖任何业务包的终端渲染引擎 pi-tui；顶层 pi-coding-agent 把三者组装成产品。每个包都可以独立被第三方引用——事实上 coding-agent 自己就构建在这些公共 API 之上，它的 RPC 模式、扩展系统、JSON 事件模式没有走任何内部后门。

2包依赖关系

依赖图是一张严格的 DAG（有向无环图），这是整个仓库最重要的架构约束：pi-ai 不知道 pi-agent-core 的存在，pi-agent-core 不知道 coding-agent 的存在。每往下一层，代码就更通用一分；每往上一层，代码就更产品化一分。底层包因此可以被完全不同的宿主复用（比如用 pi-agent-core + 自定义工具做一个浏览器自动化代理）。

5贯穿全库的四个设计决策

读完 11.6 万行代码后，以下四个决策反复出现在每一层。理解它们，后面九篇里的大量细节都会变得"理所当然"：

决策 1
错误编码进流，而不是抛异常
pi-ai 的 StreamFunction 契约规定：流一旦开始，任何失败（网络、鉴权、解析）都必须作为 {type:"error"} 事件出现在流里，禁止向上抛。连动态 import 失败都会被 lazy.ts 转成 error 事件。上层因此可以用同一种"消费事件"的方式处理成功与失败，重试逻辑也得以在流边界统一实施。
决策 2
核心包零副作用、按需加载
pi-ai 的入口明确标注 "Core only, side-effect free"：不引模型目录、不注册 provider。模型目录是构建期从 models.dev 生成的代码；11 个 API 适配器各配一个 *.lazy.ts 做动态 import。这让 CLI 冷启动只加载用到的部分，也让底层包可以被 tree-shake。
决策 3
循环是纯函数，状态是薄壳
agent-loop.ts（796 行）是无状态的纯函数：输入 config + 消息，输出事件流，可用 faux provider 完整单测。Agent 类（592 行）只做三件事：持有消息队列、管理 AbortController、按序结算监听器。可测试性和可组合性都来自这个切分。
决策 4
事件溯源式会话 + 可插拔存储
会话是 append-only 的 JSONL 事件树：每条 entry 带 id/parentId，分支只是移动"叶子指针"，永不改写历史。存储实现可替换（内存 / JSONL），两者由同一套 993 行 conformance 测试套件验证一致性。压缩（compaction）也只是追加一条 CompactionEntry。
