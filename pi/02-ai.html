pi-ai：用一套类型抹平 40+ 家供应商

22,666 行。它是整个仓库的地基：定义"模型调用"这件事的全部类型（Context、AssistantMessage、事件协议），并用 10 个协议适配器把 Anthropic / OpenAI / Google / Bedrock / Mistral 等完全不同的 wire 协议翻译成同一种事件流。上层的 Agent 循环对此毫无感知。

1包定位：核心零副作用 + 按需加载

src/index.ts 的文件头是一句设计宣言："Core only, side-effect free"——入口只导出类型、工具函数和懒加载分发器，不引模型目录、不注册 provider 工厂、不含 OAuth 实现。39 个 provider 的模型目录和 11 个 API 适配器全部走子路径（@earendil-works/pi-ai/providers/*、/compat、/bedrock-provider）+ 动态 import。

懒加载的实现本身就很能说明这个包的错误哲学。看 lazyStream：连"动态 import 失败"这种最早期、最不加掩饰的错误，也被转成流里的一个 error 事件，而不是抛给调用方：

packages/ai/src/api/lazy.tsL46-61
export function lazyStream(
  model: Model<Api>,
  setup: () => Promise<AsyncIterable<AssistantMessageEvent>>,
): AssistantMessageEventStream {
  const outer = new AssistantMessageEventStream();

  setup()
    .then((inner) => forwardStream(outer, inner))
    .catch((error) => {
      const message = createSetupErrorMessage(model, error);
      outer.push({ type: "error", reason: "error", error: message });  // 失败 = 一个事件
      outer.end(message);
    });

  return outer;
}
设计决策 1：错误编码进流

这不是孤立技巧，而是全包的统一契约（见 第 2 节 的 StreamFunction 注释）。好处：调用方只需一种控制流（消费事件），重试、UI 提示、会话记录都挂在同一个位置；缺点是错误栈信息会被压平成 errorMessage 字符串。pi 认为这个交换值得——Agent 场景里"失败是常态"（限流、断网、坏 JSON），必须是一等公民。

输出侧的事件协议是全仓库最重要的接口。每个事件的 partial 字段都携带累积到当前时刻的完整 AssistantMessage——消费者不需要自己拼装增量，永远可以整块读取当前状态：

packages/ai/src/types.tsL515-539 · 事件协议
/**
 * Event protocol for AssistantMessageEventStream.
 *
 * Streams should emit `start` before partial updates, then terminate with either:
 * - `done` carrying the final successful AssistantMessage, or
 * - `error` carrying the final AssistantMessage with stopReason "error" or "aborted"
 */
export type AssistantMessageEvent =
  | { type: "start"; partial: AssistantMessage }
  | { type: "text_start"; contentIndex: number; partial: AssistantMessage }
  | { type: "text_delta"; contentIndex: number; delta: string; partial: AssistantMessage }
  | { type: "text_end"; contentIndex: number; content: string; partial: AssistantMessage }
  | { type: "thinking_start"; contentIndex: number; partial: AssistantMessage }
  | { type: "thinking_delta"; contentIndex: number; delta: string; partial: AssistantMessage }
  | { type: "thinking_end"; contentIndex: number; content: string; partial: AssistantMessage }
  | { type: "toolcall_start"; contentIndex: number; partial: AssistantMessage }
  | { type: "toolcall_delta"; contentIndex: number; delta: string; partial: AssistantMessage }
  | { type: "toolcall_end"; contentIndex: number; toolCall: ToolCall; partial: AssistantMessage }
  | { type: "done"; reason: "stop" | "length" | "toolUse" | "deferred"; message: AssistantMessage }
  | { type: "error"; reason: "aborted" | "error"; error: AssistantMessage };

注意 error 事件的 payload 也是一条完整的 AssistantMessage（stopReason 为 "error"/"aborted"，带 errorMessage）。也就是说失败的那一轮对话也是一条合法的历史消息，可以直接进会话记录——这就是"错误编码进流"的完整含义。

承载这些事件的容器是 EventStream（utils/event-stream.ts，88 行）——一个极简的异步迭代器：生产者 push()，消费者用 for await 拉；没人等就进队列，没数据就挂起等待。它还提供 result(): Promise<AssistantMessage>，让"只要最终结果不要过程"的调用方（比如 completeSimple）绕过逐事件消费：

packages/ai/src/utils/event-stream.tsL21-36 · push 与完成判定
push(event: T): void {
  if (this.done) return;

  if (this.isComplete(event)) {                    // done 或 error 事件
    this.done = true;
    this.resolveFinalResult(this.extractResult(event));
  }

  // Deliver to waiting consumer or queue it
  const waiter = this.waiting.shift();
  if (waiter) {
    waiter({ value: event, done: false });
  } else {
    this.queue.push(event);
  }
}

5手写 SSE 解析器

Anthropic 适配器没有用 SDK 内建的流解析，而是自己写了 120 行 SSE 帧解析（iterateSseMessages）。原因是控制力：需要在字节层面检测"流被截断"（收到 message_start 却没有 message_stop）、需要保留原始行用于错误诊断、需要响应 abort 信号：

packages/ai/src/api/anthropic-messages.tsL332-356 · 行→帧状态机
function decodeSseLine(line: string, state: SseDecoderState): ServerSentEvent | null {
  if (line === "") {
    return flushSseEvent(state);          // 空行 = 一帧结束，冲刷缓冲
  }

  state.raw.push(line);                   // 保留原始行，出错时附在异常信息里
  if (line.startsWith(":")) {
    return null;                          // SSE 注释行，忽略
  }

  const delimiterIndex = line.indexOf(":");
  const fieldName = delimiterIndex === -1 ? line : line.slice(0, delimiterIndex);
  let value = delimiterIndex === -1 ? "" : line.slice(delimiterIndex + 1);
  if (value.startsWith(" ")) {
    value = value.slice(1);               // 规范：冒号后的单个空格不属于值
  }

  if (fieldName === "event") {
    state.event = value;
  } else if (fieldName === "data") {
    state.data.push(value);               // data 可多行，join("\n")
  }

  return null;
}

7双层重试

重试被拆成职责不同的两层，互不重叠：

  • 传输层 utils/provider-retry.ts（125 行）：只管 HTTP 语义——429/5xx、retry-after 头、指数退避 + 抖动。sleep 可被 AbortSignal 打断（用户按 Esc 立即停止等待）。SDK 的 maxRetries 被置 0，退避策略完全接管，并且设了 maxRetryDelayMs 上限：超过就直接抛错交给上层，避免传输层无限耗时间。
  • 语义层 utils/retry.ts（228 行）：retryAssistantCall 消费一条 RetryPolicy{enabled, maxRetries, baseDelayMs}（由 coding-agent 的 settings.retry 映射而来），用两个大正则给错误分类——可重试（网络波动、超时、5xx）与不可重试（配额、账单、鉴权）——只重试前者，并暴露 onRetryScheduled 等回调供 UI 显示"将在 4s 后重试"。

包内没有跨 provider 的自动 fallback：Anthropic 挂了自动换 OpenAI 这种事由上层（coding-agent 的 provider 组合层）决定。pi-ai 只把 OpenRouter 的路由语义（OpenRouterRouting）建模为类型。
