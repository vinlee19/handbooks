无头模式与协议栈

pi 有两套并存的"机器接口"：内建的 JSONL RPC（--mode rpc，稳定，子进程 stdin/stdout）与实验性的 CBOR 二进制协议（packages/protocol + client + server，Unix socket）。它们共享同一个 AgentSession 内核，只是编解码与传输不同。本篇把 print/json 模式一起讲清。

1print 与 json 模式

runPrintMode（169 行）是最简单的消费者：把初始消息发给 AgentSession，订阅事件直到 agent_end。mode:"text" 只输出最后一条 assistant 文本；mode:"json" 把每个事件经 toJsonEvent 序列化输出——注意它对 message_update 做了特殊处理：

为什么 json 模式要"剥掉累积 partial"

内部事件协议里，message_update 的 partial 字段携带累积到当前的完整消息（02 篇）。对内存中的 UI 消费者这很方便，但逐行输出到 stdout 时会把同一段正文重复几十遍。于是 toJsonEvent（modes/json-event.ts，40 行）把它改写为只含本次 delta 的事件——机器消费者自己拼接增量，通信量降一个数量级。这是一个"同一事件协议，两种视角"的好例子。

2内建 JSONL RPC

RPC 模式是给宿主程序（IDE 插件、bot、测试）用的常驻接口：spawn("pi", ["--mode", "rpc"]) 后长期持有子进程，stdin 发命令、stdout 收响应与实时事件。命令面几乎覆盖 AgentSession 全部动作：

3实验性 CBOR 协议栈（protocol / client / server）

当集成方不是"能 spawn 子进程的 shell 世界"（比如编辑器扩展宿主、多客户端共享会话）时，JSONL 子进程模型不够用。packages/protocol（1,236 行）定义了二进制协议，设计原则写在它的 README 里：快照权威，progress 事件只是瞬态 UI 提示，不得折入权威状态——客户端状态归并只认 SessionSnapshot，事件只用来触发重绘。

// FRAME_HEADER_LENGTH = 4（大端 uint32 长度前缀）
export function encodeFrame(payload: Uint8Array): Uint8Array {
  if (payload.byteLength > MAX_UINT32) throw new RangeError(...);
  const frame = new Uint8Array(FRAME_HEADER_LENGTH + payload.byteLength);
  const length = payload.byteLength;
  frame[0] = length >>> 24;
  frame[1] = length >>> 16;
  frame[2] = length >>> 8;
  frame[3] = length;
  frame.set(payload, FRAME_HEADER_LENGTH);
  return frame;
}

packages/client（1,225 行）是协议的消费端 SDK：传输无关（ByteTransport 接口 + Unix socket 实现）、显式不自动重连、会话租约（SessionLease，exclusive/shared 两种，AsyncDisposable，引用计数到最后一个租约释放才发 detach）。packages/server 用 coding-agent 的 create-harness.ts 承载会话。四者的关系回看 01 篇图 1-3。

4两套协议怎么选

JSONL RPC（稳定）CBOR protocol/client/server（实验）
传输子进程 stdin/stdout 管道Unix socket
编解码文本 JSON 行，人眼可调4 字节长度前缀 + CBOR，TypeBox 校验
进程模型1 会话 = 1 子进程常驻 server 承载多会话、多客户端 attach
状态模型命令/响应 + 事件流快照权威 + 瞬态事件；租约管理所有权
适合脚本、测试、单宿主集成编辑器深度集成、多面板共享、远程化前奏
