构建与发布：把源码变成可信任的安装物

约 3,000 行构建脚本 + 一条 tag 驱动的 CI 流水线。这一篇不讲代码逻辑，讲"信任如何被制造"：依赖精确 pin、二进制从确定性源码归档构建、npm OIDC 免 token 发布、R2 版本指针用 ETag CAS 推进——每一层都假设上一层可能出问题。

1产物矩阵：npm 包与 Bun 二进制

pi 有两种安装形态。npm 路线：tsgo 直接 tsc 到 dist/（无打包器），bin 指向 dist/cli.js，依赖由 npm-shrinkwrap.json 钉死。二进制路线：bun build --compile 产出单文件可执行（六平台：darwin/linux/windows × arm64/x64），内嵌 Bun 运行时。

2依赖卫生

  • 精确 pin：所有外部依赖写死精确版本（无 ^/~），check-pinned-deps.mjs 在 npm run check 里强制；工作区内部包才允许版本区间。
  • lifecycle 脚本默认禁用：开发与 CI 一律 npm ci --ignore-scripts。带 install script 的新依赖必须人工审码并加入 allowlist——shrinkwrap 生成器（365 行）里当前只有两条：@google/genai@1.52.0 与 protobufjs@7.6.5，各带理由注释。
  • npm-shrinkwrap.json：由根 lockfile 生成，发布随包走。生成器做硬校验：无 link/file/workspace resolved、无本地路径、闭包完整性、平台 specific 包齐全——保证用户 npm install -g 得到与 CI 完全相同的树。
  • install-lock：另一个生成器产出 pi-coding-agent-install 的 pinned 清单（release 资产），给自更新脚本复现安装。
