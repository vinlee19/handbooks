05 · Pipeline 执行：Push-based + Event 状态机

基于 commit fe693bb677。本篇覆盖 databend-common-pipeline 与 databend-query::pipelines，从 Processor trait 到 worker 调度，再到 PhysicalPlan 如何落到 Pipeline。

1. 解决了什么问题

向量化 OLAP 引擎的执行层有两条主路：

  • 拉式（Volcano / iterator-based）：next() 自顶向下递归。简单，但是每次取一行/一个 batch 都过一遍调用栈，调度边界等同于函数边界。
  • 推式（Push / morsel-driven）：算子主动把 batch 推给下游；每次决策由 batch 而不是行驱动。在大并发下能减少状态切换、便于 work-stealing。

直接采用 Volcano 的反例：

反例 1：每个 next() 都是一次虚函数调用
        → 在数十亿行下，调用栈本身就是显著开销

反例 2：算子无状态机，调度器无法决定"下个该跑谁"
        → 不能跨 batch 重叠 IO 与 CPU

反例 3：异步算子要靠 future 嵌入 next()
        → 嵌套 future 会污染所有上层算子

Databend 的取舍：借鉴 ClickHouse Processors——每个算子是一个状态机（Processor trait），用 Event 显式告诉调度器"我现在需要数据/需要消费/能同步跑/能异步跑/已结束"。调度器拿到 Event 自己决定让哪个 worker 在什么时候推动哪个算子。

processor.rs::L≈49 注释直白写着 "The design is inspired by ClickHouse processors"。

3. 关键数据结构

3.1 Processor trait

// src/query/pipeline/src/core/processor.rs:32
#[derive(Debug)]
pub enum Event {
    NeedData,    // 输入空，等输入
    NeedConsume, // 输出已满，等下游消费
    Sync,        // 可以立即跑同步 process()
    Async,       // 应该跑 async_process()
    Finished,    // 终止
}

// src/query/pipeline/src/core/processor.rs:51
#[async_trait::async_trait]
pub trait Processor: Send {
    fn name(&self) -> String;
    fn as_any(&mut self) -> &mut dyn Any;

    fn event(&mut self) -> Result<Event> { ... }                 // 决策"现在该做什么"
    fn event_with_cause(&mut self, _: EventCause) -> Result<Event>;
    fn un_reacted(&self, _: EventCause, _id: usize) -> Result<()>;

    fn interrupt(&self) {}                                       // 终止长时间同步任务
    fn process(&mut self) -> Result<()> { Err(...Unimplemented) }
    async fn async_process(&mut self) -> Result<()> { Err(...) }

    fn details_status(&self) -> Option<String> { None }
    fn set_id(&mut self, _: NodeIndex) {}
}
stateDiagram-v2 [*] --> Idle Idle --> NeedData : input empty Idle --> NeedConsume : output full Idle --> Sync : can compute now Idle --> Async : need IO / network Sync --> Idle : process() ok Async --> Idle : async_process() ok Idle --> Finished : 输入关闭 + 状态机走完 Finished --> [*]

每次调度器决定"是否推动这个 Processor"时，调用 event() 拿到状态：

Event 调度器动作
NeedData / NeedConsume 把它放回等待队列，依赖事件唤醒
Sync 取一个 worker 直接 process()
Async 把 async_process() future 提交给 tokio
Finished 从图上摘除；触发下游也走 Finished

3.2 ProcessorPtr — 在不可变 self 上跑可变状态

// src/query/pipeline/src/core/processor.rs:111
#[derive(Clone)]
pub struct ProcessorPtr {
    id: Arc<UnsafeCell<NodeIndex>>,
    inner: Arc<UnsafeSyncCelledProcessor>, // UnsafeCell<Box<dyn Processor>>，标记 Sync
}

为什么必须 UnsafeCell：调度器需要 Arc<ProcessorPtr>（共享）+ event()/process() 是 &mut self。Rust 不允许通过 Arc 取得 &mut，所以用 UnsafeCell + 「同时只有一个 worker 推动它」的不变量来保证安全。这是引擎层最 unsafe 的地方之一，但是规则严格：同一时刻只有一个 worker 持有该 processor 的访问权，由 ScheduleQueue 担保。

注意：

  • 多 source、多 sink、多分支都允许。Pipe 是「一组同列输入/输出 port 对齐的多 processor」单元，方便把同构并行片段一次性插入图。
  • Resize 是一个特殊 processor，把 N 个输入 reshape 成 M 个输出（典型用法是把 partition 数 → 线程数）。
  • max_threads 是 Pipeline 自己声明的并行度上限；执行器会取 pipeline.get_max_threads() 决定 worker 数。

4.3 同步 vs 异步：把 IO 推到 tokio

flowchart LR N[event() = Async] --> P[ProcessorAsyncTask\nprocessor_async_task.rs] P --> TR[tokio Runtime] TR --> AP[async_process()] AP --> CB[完成回调\nCompletedAsyncTask 入列] CB --> SQ[ScheduleQueue 唤醒 worker]

「同步 worker 不应该被 IO 阻塞」是 push-based 模型相比 pull 模型的关键收益。async_runtime: Arc<Runtime> 是单独建的 tokio 运行时，避免 query 内部 IO 与服务侧 HTTP/Flight handler 在同一 runtime 上互相饿死。

注意：

  • TableScan 不只是一个 processor——它是 N 个 source processor + 解码 transform，真正的 IO 在 event() 返回 Async 时跑 async_process。
  • FilterTransform / PartialAggregate 是 sync——纯 CPU，不会 yield。
  • Resize 是单点收敛——把 N 路并行减成 1 路，方便 FinalAggregate 跑单 worker。
  • 执行结束后 on_finished_chain 触发：清理 spill、上报 profile、记录 history log。
