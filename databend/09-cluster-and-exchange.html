09 · 集群与 Exchange：节点发现 + Flight Shuffle

基于 commit fe693bb677。本篇覆盖 service/src/clusters/ 与 service/src/servers/flight/，把"无状态 query 集群如何协同"以及"DataBlock 如何在节点间穿梭"讲清楚。

1. 解决了什么问题

无状态 query 集群有两个绕不开的子问题：

  1. 节点发现：query 节点是临时的，启动 / 失效都不该对客户端可见；查询规划要知道当前活着的节点。
  2. 节点间数据搬运：MPP 查询会在不同节点上跑同一个查询的不同分片，分片之间需要交换 DataBlock（join 的 hash shuffle、广播小表、最终合并到 coordinator）。

直接拿 ZK / 自带 gRPC 写一套的反例：

反例 后果
节点信息存在每个节点本地 一旦节点失效，集群视图分裂
用普通 gRPC 流序列化 DataBlock 反复序列化/反序列化 + 没有零拷贝
客户端走与节点间相同的协议 边界混淆；客户端协议升级会牵连节点间通讯
一条流过一个 RPC 大查询的 shuffle 直接打满单连接

Databend 的取舍：

  • 集群视图寄存在 meta-service：query 节点启动时 register、心跳续约、watch 变更。
  • 节点间通讯走 Arrow Flight——RecordBatch 是 wire 格式，列存零拷贝；客户端通讯（MySQL/HTTP/FlightSQL）完全独立。

3.2 FlightService（节点间 RPC 入口）

// src/query/service/src/servers/flight/flight_service.rs:33
pub struct FlightService { /* tonic + arrow-flight 服务 */ }

FlightService::start 在 entry.rs::start_services (L≈146) 启动，监听 flight_api_address（默认 9091）。它实现 arrow_flight::flight_service_server::FlightService 这个 trait，关键方法：

  • do_action(action: Action) → 处理 ClusterHelper::do_action 类型的"广播一段消息给特定节点"。
  • do_get(ticket: Ticket) → 单向流式拉取数据（用于 Merge / NodeToNodeExchange）。
  • do_exchange(stream: Stream<FlightData>) → 双向 ping-pong 流（用于 Broadcast / GlobalShuffleExchange）。
  • do_put(stream) → 流式 push（统计、状态同步等）。

3.3 DataExchange — 四种交换类型

// src/query/service/src/servers/flight/v1/exchange/data_exchange.rs:19
pub enum DataExchange {
    Merge(MergeExchange),
    Broadcast(BroadcastExchange),
    NodeToNodeExchange(NodeToNodeExchange),       // 普通 hash shuffle
    GlobalShuffleExchange(NodeToNodeExchange),    // 跨阶段全局 shuffle
}

impl DataExchange {
    pub fn use_do_exchange(&self) -> bool {
        matches!(self,
            DataExchange::Broadcast(_) | DataExchange::GlobalShuffleExchange(_))
    }
}
flowchart TB subgraph Merge["Merge (do_get)"] M1[Worker A] M2[Worker B] M3[Worker C] MD[(coordinator 单点)] M1 --> MD M2 --> MD M3 --> MD end subgraph Broadcast["Broadcast (do_exchange ping-pong)"] B1[Source] B1 --> BD1[Dest 1] B1 --> BD2[Dest 2] B1 --> BD3[Dest 3] end subgraph N2N["NodeToNodeExchange (do_get hash shuffle)"] NA[Node A] --hash--> NB1[Node B 桶 1] NA --hash--> NB2[Node B 桶 2] NB1 --hash--> NA1[Node A 桶 1] end subgraph GS["GlobalShuffleExchange (do_exchange)"] G1[阶段 1 全节点] G2[阶段 2 全节点] G1 -- ping-pong --- G2 end

为什么 Broadcast 与 GlobalShuffle 用 do_exchange 而 Merge / NodeToNode 用 do_get：

  • do_get 是单向流——发送方推完即可结束。Merge 把数据汇聚到一个目的端；NodeToNode 单向拉。
  • do_exchange 是双向流——上下游都能在同一连接上发送握手 / 反压 / 状态。Broadcast 需要等所有目的端 ack；GlobalShuffle 在跨阶段时上下游互相确认水位。

DataExchangeManager 是全局单例，但每个 query_id 进来时建一个 QueryCoordinator：里面持有该 query 涉及的所有 sink / source / buffer。query 结束时 coordinator 被擦掉，资源即时释放。

SyncUnsafeCell<HashMap> + ReentrantMutex 的组合：因为 query 内的多个组件可能在持锁状态下回调到 manager，需要可重入锁；外层 SyncUnsafeCell 是为了让 Mutex 持锁后获得 &mut HashMap。

3.5 ExchangeSink / ExchangeSourceReader / 内部 Pipeline

flowchart LR subgraph SrcPipe["发送侧 Pipeline (本节点)"] OP[上游算子] --> ETS[ExchangeTransformScatter\n按 hash 分桶] ETS --> HSS[HashSendTransform / HashSendSink] HSS --> ESB[ExchangeSinkBuffer\n背压窗] ESB --> EW[ExchangeSinkWriter\n→ FlightClient] end subgraph Net[Arrow Flight stream] EW -->|RecordBatch| RR end subgraph DstPipe["接收侧 Pipeline (对端节点)"] RR[ExchangeSourceReader] --> ESS[ExchangeSource processor] ESS --> DSP[下游算子] end

要点：

  • 背压：ExchangeSinkBuffer 有"未 ack 字节数"窗口，写满则停。
  • 行/列零拷贝：写出时 DataBlock 直接转 Arrow RecordBatch；接收侧不用 deserialize 整张表。
  • 失败传播：任一边断流，立刻向对端发 error frame，coordinator 触发整 query 中止。

4.1 节点上下线

ClusterDiscovery 的 lru_cache 缓存 CachedNode——同一 query 内多次 discover 不会反复打 meta-service。

4.2 一次分布式查询

注意：

  • 每个节点都跑同一份 PhysicalPlan——只是 ExchangeSink/Source 上的 partition 子集不同。
  • init_query_env 把整个 plan 预先广播给所有节点，省得每次有数据 shuffle 都重新协商。
  • Coordinator 是"刚好被客户端选中的那个节点"，没有专属角色——这是 stateless 的红利。

最大的差异：Databend 没有"Coordinator/Worker"角色之分——任何节点都可以当 coordinator。这与 stateless 的设计一致：客户端可以负载均衡到任意节点，集群的拓扑信息全在 meta-service，本地节点不持久化任何状态。

注意：

  • count(*) 的中间状态只需传一个 u64 per partition，跨节点流量极小；这就是 partial+final 设计的精髓——大数据集流量被压缩到 worker_count × group_count。
  • 没有 join，所以也没有 hash shuffle；本例只用 Merge 一种 Exchange。

8. 未解之谜

  • assigned_warehouse 与 warehouse_id：节点可以未分配仓库时仍然在线（Cluster.create 检查 unassign）；具体 warehouse 调度策略（动态分配 / 弹性扩缩）需要在 EE 模块或 cloud-control 协议里看。
  • statistics_sender / statistics_receiver：本篇仅记录其存在；它们如何与 ExplainAnalyze 的 profile 协同？
  • exchange_transform_shuffle.rs vs exchange_transform_scatter.rs：两个 transform 看起来都做 hash 重分桶；差异点在于何时丢给 sink 还是再过一次本地 transform。
  • 多端口安全：9091（节点间）与 8900（FlightSQL 客户端）共用 tonic，但前者必须验证 local_secret。secret 校验路径在 do_action 入口还是更深层？
  • DNS / IP 漂移：节点 flight_address 在 register 时记录；如果集群跑在 k8s pod 上 IP 随重启变化，靠的是"先 deregister 再 register"还是"watch 触发新 NodeInfo"？需要看心跳里携带的字段。
  • 一致性 vs 可用性：心跳过期后节点被踢出，正在跑的查询会怎么样？看起来是查询级别的 fail-fast（fragment 收不到对端 ack 即报错），而非系统级容错重跑——本篇未在 QueryCoordinator 层面验证。
