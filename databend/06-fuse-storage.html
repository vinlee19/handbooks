06 · FUSE 存储引擎：Snapshot / Segment / Block

基于 commit fe693bb677。FUSE 是 Databend 的默认表引擎；理解它是理解整个系统的钥匙。本篇用三层文件结构 + 一次 commit 时序，把 read / write / compact / recluster / time-travel 全部串起来。

1. 解决了什么问题

把「ACID + Time Travel + 列存 + 索引」做在只读对象存储之上。对象存储有几条硬约束：

  • 没有 rename 原子性（GCS 部分有，S3 视区域而定）。
  • 没有就地修改（PUT 只能整文件覆盖；object 是不可变的）。
  • list 有强一致性，但成本高、延迟大。
  • 极强一致性下的 PUT 一定是「新对象」——同 key 多写其实是创建多个版本。

直接在对象存储上做 OLAP 表面临的反例：

反例 1：每次 INSERT 都改写表元数据
        → 大事务并发争抢一把"全表锁"，写吞吐塌掉

反例 2：把元数据放对象存储里、写时锁
        → list-and-scan 的延迟把延迟拉到秒级

反例 3：直接拿 Parquet 当表
        → 没有事务，没有版本，没有列裁剪以外的索引

FUSE 的取舍是：所有数据/元数据都是「不可变对象」，靠一个外部强一致 KV（meta-service）只翻一个指针。任何写入都生成新文件，提交时只需要在 meta 中原子地把「表当前指向的 snapshot 路径」从旧值改到新值。回滚 = 改回旧指针。Time Travel = 沿着 prev_snapshot_id 走链表。

记住：索引和虚拟列都不在 parquet 文件里，而是各自的独立对象，仅靠 BlockMeta 上的 location 字段串联。这让索引可以独立缩放、独立淘汰、独立打开 / 关闭。

3.3 对象存储 key 命名

TableMetaLocationGenerator 在 src/query/storages/fuse/src/io/locations.rs::TableMetaLocationGenerator (L≈66) 生成所有路径，前缀来自 src/query/storages/fuse/src/constants.rs：

<table_storage_prefix>/                  # 来自 TableInfo.meta.options.storage_prefix
├── _ss/<uuid>_v<ver>.json|mpk           # snapshot
│       ↑ FUSE_TBL_SNAPSHOT_PREFIX = "_ss"
├── _ts/<uuid>_v<ver>.mpk                # snapshot statistics
├── _sg/<vacuum2-prefix><uuid>_v<ver>.mpk  # segment（默认 mpk = MessagePack+ZSTD）
│       ↑ FUSE_TBL_SEGMENT_PREFIX = "_sg"
│       column-oriented 时是 .col
├── _b/<vacuum2-prefix><uuid_v7>_v<ver>.parquet   # 数据块
│       ↑ FUSE_TBL_BLOCK_PREFIX = "_b"
├── _i_b_v2/<uuid>_v<ver>.parquet         # bloom filter（xor8）
│       ↑ FUSE_TBL_XOR_BLOOM_INDEX_PREFIX
├── _i_i/<...>                            # inverted index (Tantivy)
├── _i_v/<...>                            # vector index (HNSW)
├── _i_s/<...>                            # spatial index
└── _v/, _agg/, ...                       # 虚拟块、aggregating index 等

「_b」「_sg」「_ss」这种单字母 + 下划线前缀的好处：在对象存储上 prefix list 时所有同类对象集中分布，便于 GC 与 vacuum。

4.2 写：从 INSERT 到新的 snapshot

写入有两条路径，由 enable_stream_block_write 设置切换（operations/append.rs::L≈54）：

  • 流式块写：边收边写，每攒够一块立刻落盘 + 累积统计。
  • 传统批量写：先在内存里 compact 出大块，再统一 serialize → write。
flowchart LR IN[InsertInterpreter] --> AP[do_append_data\nappend.rs L≈48] AP -- enable_stream_block_write --> SBuilder[TransformBlockBuilder\n+ TransformBlockWriter] AP -- 否 --> BC[build_compact_block_pipeline] BC --> SB[TransformSerializeBlock] SBuilder --> SS[TransformSerializeSegment] SB --> SS SS --> CMA[TableMutationAggregator] CMA --> CS[CommitSink] CS --> Meta[update_table_meta\n→ meta-service KV CAS] CS --> ObjStore[(对象存储\nsnapshot/segment/block)]

do_commit (commit.rs::L≈81) 把 commit 也做成了一段流水线，不是一次 RPC：

// src/query/storages/fuse/src/operations/commit.rs:81
pipeline.try_resize(1)?;                                    // 收敛到单线程
pipeline.add_transform(new_serialize_segment_processor)?;   // 攒成 segment 文件
pipeline.add_async_accumulating_transformer(
    || TableMutationAggregator::create(...));               // 聚合所有变更
pipeline.add_sink(|input| CommitSink::try_create(...));     // 写 snapshot + 更新 meta（CAS）

CommitSink 内部在写 snapshot 文件后调用 commit_to_meta_server (commit.rs::L≈141)，里面是两步：

  1. snapshot.write_meta(operator, &snapshot_location)：先把新 snapshot 文件 PUT 到对象存储；
  2. update_table_meta(...)：以「prev_table_seq」为前提条件向 meta-service CAS 更新 TableInfo.options[OPT_KEY_SNAPSHOT_LOCATION]。
sequenceDiagram autonumber participant W as Worker participant OD as OpenDAL participant M as meta-service W->>OD: PUT snapshot.json (新 snapshot) W->>M: update_table_meta(prev_seq, new_loc) alt CAS 成功 M-->>W: ok else 表 seq 已变 M-->>W: TableVersionMismatched W->>W: backoff + 重读 snapshot 重新 merge\nset_backoff (operations/util) W->>OD: PUT snapshot' (基于新 base 的 snapshot) W->>M: update_table_meta(prev_seq', ...) end

写失败重试在 set_backoff 里实现（指数退避），冲突场景下数据文件不变、只重写 snapshot，因此冲突重试是廉价的。

4.3 Compact / Recluster / Time-Travel

Compact

flowchart LR C[compact 命令 / 自动触发] --> CS[do_compact_segments\nL≈43] C --> CB[do_compact_blocks\nL≈77] CS -.合并小 segment.- N1[新 segment 文件] CB -.合并小 block.- N2[新 block 文件] N1 --> CMT[CommitSink] N2 --> CMT CMT --> SS[新 snapshot]

源码：src/query/storages/fuse/src/operations/compact.rs： - do_compact_segments (L≈43)：把多个小 segment 合并成大 segment，不重写 block 文件——所以非常便宜，主要降低读时元数据 I/O。 - do_compact_blocks (L≈77)：把多个小 block 真正合并成大 block，要解压再压缩，重新写。

Recluster

do_recluster (operations/recluster.rs::L≈46)：当表声明了 cluster key 时，按 cluster_stats 把"乱序的旧 block"重排成"按 cluster key 排序的新 block"。Hilbert 聚簇是企业版能力（位于 src/query/ee_features/hilbert_clustering/），在 do_read_partitions 内有特殊路径（见 read_partitions.rs::L≈146 的 selected_segment_locations）。

Time Travel

flowchart TB Q[SELECT * FROM t AT (TIMESTAMP => '2026-04-30')] --> NP[navigate_to_point\nnavigate.rs L≈56] NP -->|TimePoint| NTP[navigate_to_time_point\nL≈117] NP -->|SnapshotID| NSI[navigate_to_snapshot\nL≈148] NP -->|StreamInfo| LBL[load_table_by_location] NP -->|TableTag| GTSL[get_tag_snapshot_location\n→ load_table_by_snapshot] NTP --> FIND[find: 沿 prev_snapshot_id 反向遍历\n直到 ts <= time_point] NSI --> FIND FIND --> NEW[FuseTable 复制一份\ntable_info 指向旧 snapshot_loc] NEW -.下游使用同一套读路径.-> Q

实现要点：

  • Time travel 不是数据库层逻辑，而是「把 FuseTable 指向另一个 snapshot」，下游 do_read_partitions 完全不变。
  • 反向遍历由 find 函数完成（在 navigate.rs 内部），逐个加载 prev_snapshot_id 指向的 snapshot 直到谓词满足；这条链是用对象存储上一组小 JSON 文件实现的。
  • Stream（CDC）实际上也复用 navigate_to_point::StreamInfo，「读取增量」在这里被建模成「读取两个 snapshot 之间的差集」。

5. 性能与优化点

三层裁剪：snapshot summary → segment summary → block min/max prune_snapshot_blocks 与 do_build_prune_pipeline 大多数 OLAP 查询能在还没 GET parquet 之前裁掉 90%+ 的块
Distributed pruning read_partitions.rs L≈121, 166 当 segment 多于节点数时，把"读 segment 元数据 + 块裁剪"分布到各 worker，避免单点

FUSE 没有 Iceberg 那种"manifest of manifests"的抽象层；segment 就是 manifest 的等价物，但不能跨 snapshot 共享——每次写都生成新 segment。换来的好处是写路径极简、提交一次只写一个 snapshot 文件。

sequenceDiagram autonumber participant Plan as PhysicalPlan::TableScan(t) participant FT as FuseTable participant OD as OpenDAL participant C as 多级 Cache participant Idx as RangeIndex/BloomIndex participant Pipe as Pipeline Plan->>FT: do_read_partitions(push_downs={ filter: x>1 }) FT->>C: snapshot_loc C-->>FT: Arc<TableSnapshot>（包含 segments[]） FT->>FT: 决定 distributed_pruning=false（小表） loop 每个 segment_loc FT->>C: SegmentInfo C-->>FT: blocks[] FT->>Idx: RangeIndex(col_stats[x].min/max vs >1) alt 区间确定不满足 Idx-->>FT: 整块剪掉 else 区间不能定论 FT->>C: bloom_filter_index_location for x C-->>FT: BloomFilter bytes FT->>Idx: bloom 查询 hash(x>1) 不可行→跳过 bloom Note over FT,Idx: count(*) 没有等值谓词，bloom 跳过 end end FT-->>Plan: Partitions（仅存活块） Plan->>FT: read_data → Pipeline FT->>OD: 并发 GET *.parquet（仅 col=x 与必要列） OD-->>Pipe: bytes Pipe->>Pipe: ColumnReader(x) → FilterTransform(x>1) → FinalAggregate(count) Pipe-->>Plan: DataBlock { count: N }

注意：

  • count(*) 这种只需要 row_count 的查询，可以直接读 BlockMeta.row_count 求和，根本不打开 parquet——但这要求没有过滤谓词或谓词能完全靠 col_stats 决定。本例 WHERE x > 1 在多数数据分布下做不到，所以仍需读列。
  • 如果谓词改成 x = 'a'（等值字符串），bloom 会真的发挥作用，把绝大多数 block 在打开 parquet 之前裁掉。
