08 · 索引与搜索：Bloom / Inverted / Vector / Range / Page / Spatial

基于 commit fe693bb677。本篇覆盖 databend-storages-common-index，把"几张索引"从概念图变成一组带 location 字段的真实文件。

1. 解决了什么问题

OLAP on 对象存储 + 向量检索 + 全文搜索的统一引擎，索引层要兼顾三个完全不同的访问模式：

模式 例子 经典做法
等值/范围裁剪 WHERE x = 'a'、WHERE ts > '2024-01-01' min/max 列统计 + Bloom
文本搜索 WHERE content @> 'rust databend' 倒排索引（Lucene/Tantivy）
向量检索 ORDER BY embedding <-> [...] LIMIT 10 HNSW/IVF

如果把它们做成"另一张表"或者外挂服务（如 ES + Qdrant），就要付出"两份数据 + 两份元数据 + 两套查询 API"的代价。Databend 的取舍：所有索引都和数据块绑定，建在同一次写入，按 BlockMeta.<idx>_index_location 引用，读时按需 GET——索引退化为「带索引的对象存储路径」。

3.2 RangeIndex — 0 IO 的"免费裁剪"

// src/query/storages/common/index/src/range_index.rs:65
pub struct RangeIndex {
    expr: Expr<String>,                           // WHERE 子句的可裁剪部分
    func_ctx: FunctionContext,
    schema: TableSchemaRef,
    default_stats: StatisticsOfColumns,           // 给后加列的兜底
    predicates: Vec<SpatialPredicate>,            // 空间谓词（独立分支）
}

// apply(...) bool —— true=保留这块；false=裁掉

特点：

  • 数据来源是内存里的 BlockMeta.col_stats，不发任何 RPC。
  • 用「可单调的表达式归纳」做区间运算：把 x>1 在 [min=2, max=10] 上化简成 true；x>1 在 [min=-5, max=0] 上化简成 false；任何无法在区间内化简的式子保留为 unknown，块保留。
  • default_stats：表加了新列后，旧 block 的 col_stats 不含新列；用 default 兜底。

    // ...
    // 内部按列存放 FilterImpl（Xor8Filter 或 BinaryFuseFilter）
}

// src/query/storages/common/index/src/bloom_index.rs:133
pub struct BloomIndexMeta {
    pub columns: Vec<(String, SingleColumnMeta)>,  // 每列在 bloom .parquet 中的偏移
}

为什么不是经典 BloomFilter？经典 Bloom 的假阳率随负载升高显著退化、删除困难。Xor8 / Binary Fuse 是现代「最小完美哈希家族」，相同 false-positive 下空间显著更小、查询恒定 O(1)。源码 (bloom_index.rs::L≈87, 97) 直接 import 了这两种 filter 的 builder。

每个 block 每列一个 filter（注释 L≈209）：

+---name--+--age--+
| "Alice" |  20   |
| "Bob"   |  30   |
+---------+-------+

→ 写出 1 个 bloom .parquet：
+---Bloom(name)--+--Bloom(age)--+
|  序列化 filter |  序列化 filter|
+----------------+--------------+

Bloom .parquet 自身用 parquet 存（一行多列），方便共享 reader 与 footer 缓存。

3.5 HnswIndex — 层级图向量检索

flowchart TB subgraph HNSW["src/query/storages/common/index/src/hnsw_index/"] direction TB GL[graph_layers.rs / graph_layers_builder.rs] GLINK[graph_links / graph_links.rs] PS[point_scorer.rs] SC[search_context.rs] EP[entry_points.rs] VP[visited_pool.rs] Q[quantization/] HN[hnsw.rs] end WRITE[io/write/vector_index_writer.rs] --> GL GL --> GLINK GL --> PS HN --> EP HN --> SC SC --> PS HN --> VP HN --> Q

HNSW 是层级"小世界"图：每个点在多层中根据概率出现；上层稀疏快速跳跃，下层密集精确收敛。Databend 的实现亮点：

  • graph_links 子模块：把邻居关系做成连续布局，一次 mmap 友好。
  • visited_pool：把每次查询要用的 visited bitset 做 pool 复用，避免高并发下分配抖动。
  • quantization/：标量量化（PQ/SQ），用近似距离换内存。
  • point_scorer：把"距离函数"抽象成 trait（L2/IP/Cosine 都是 PointScorer 实现）。

写入侧 vector_index_writer.rs 在 block 收齐后离线建图，落 <block_id>_v<ver>.parquet（前缀 _i_v，参见 06 文档）。读取侧由查询的 ORDER BY <expr_dist> LIMIT k 触发，绕过 RangeIndex 直接命中 HNSW search。

PageIndex 用于 native 列存里"页"级别的 row offset 映射；有了它，按行号子集（如 inverted 检索后的 row_id 集合）回填实际列时，不需要扫整 block。它不是独立物理文件——信息已经在 BlockMeta.col_metas[ColumnMeta::Native(NativeColumnMeta { pages })] 里。

4. 关键流程

4.1 写：索引和数据并行落地

sequenceDiagram autonumber participant Pipe as Pipeline participant TS as TransformSerializeBlock participant BW as block_writer.rs participant BLOOM as bloom_index_writer.rs participant INV as inverted_index_writer.rs participant VEC as vector_index_writer.rs participant SPA as spatial_index_writer.rs participant OD as OpenDAL Pipe->>TS: DataBlock TS->>BW: 写 .parquet（数据列 + footer） par 并行索引旁路 BW->>BLOOM: 抽样列 build Xor8/BinaryFuse32 → put 到 _i_b_v2/ BLOOM->>OD: PUT bloom .parquet OD-->>TS: bloom_filter_index_location + size and BW->>INV: 文本列 build Tantivy index → put 到 _i_i/ INV->>OD: PUT inverted file OD-->>TS: inverted_index_size and BW->>VEC: 向量列 build HNSW → put 到 _i_v/ VEC->>OD: PUT vector index OD-->>TS: vector_index_location + size and BW->>SPA: 几何列 build spatial → put 到 _i_s/ SPA->>OD: PUT spatial index OD-->>TS: spatial_index_location + size end TS->>TS: 合并 BlockMeta（含所有 location/size） TS-->>Pipe: 下游 SerializeSegment / CommitSink

并行的代价是写入路径需要更多 IO 与 CPU 空间；收益是索引建好就能查，避免「写完再后台 build 索引导致前期查询走全表扫」的体验断层。

4.2 读：层层裁剪 + 必要时 search

flowchart TB WHERE[push_downs（filter/limit/sort/projection）] --> CK1{有 filter?} CK1 -- 否 --> KEEP[保留所有 block] CK1 -- 是 --> R0[RangeIndex.apply\n纯内存 col_stats] R0 -- false --> SKIP1[裁掉块] R0 -- true --> R1{filter 含等值/IN?} R1 -- 是 --> B0[读 bloom_filter_index_location] B0 --> BAPPLY[BloomIndex.apply_predicate] BAPPLY -- 必无 --> SKIP2[裁掉块] BAPPLY -- 可能有 --> R2{含全文 MATCH?} R1 -- 否 --> R2 R2 -- 是 --> INV[InvertedIndex search → row_id 集合] R2 -- 否 --> R3 INV --> R3{含向量距离?} R3 -- 是 --> HN[HnswIndex.search(top-k)] R3 -- 否 --> KEEP HN --> KEEP KEEP --> READ[do_read_data 拉 parquet 列]

注意几条隐含规则：

  • RangeIndex 永远第一关：它 0 IO，先把绝大多数无关 block 干掉。
  • Bloom 只在等值类谓词上才发挥作用：x > 1 这种范围谓词跳过 bloom（count(*) 案例就是这样）。
  • Inverted 与 Vector 是「主动检索」而非「被动裁剪」：它们直接产生候选 row_id 集合，下游再回填列。这与传统数据库"裁剪 + 顺序扫描"不同——更像是搜索引擎的执行路径。
  • Spatial 内嵌在 RangeIndex：因为空间谓词的本质也是区间相交。
