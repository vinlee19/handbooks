10 · 扩展：Stream / UDF / Iceberg / Delta

基于 commit fe693bb677。本篇覆盖 Databend「FUSE 之外」的几条主线：流式增量（Stream）、外部表格式（Iceberg / Delta）、外部 UDF（Arrow Flight + Script Runtime）。这些都是把统一引擎和外部世界缝起来的胶水。

1. 解决了什么问题

OLAP 引擎只有"自家表"是不够的，三类外部需求会跟来：

  1. CDC / 增量：上游业务库连续写入，下游 BI / agent 需要"看新增的那部分"，不是每次都重扫全表。
  2. 外部表格式：用户已有 Iceberg / Delta 表（其它引擎写出来的），想直接 SQL 查，不能强迫迁移到 FUSE。
  3. 可编程 UDF：常见标量/聚合不够，agent / 业务逻辑需要 Python / Rust UDF；不能让 UDF 在引擎进程里跑（崩了拖死引擎）。

直接做的反例：

反例 后果
每次拷贝外部 Iceberg 数据进 FUSE 数据双份；维护成本爆炸
Stream 用上游订阅触发器 事务可见性混乱；语义难定义
UDF 用 dlopen 进同一进程 安全 / 稳定 / 资源不可控
把 Python UDF 用 PyO3 嵌入 GIL；崩溃即整个 query 节点挂

Databend 的取舍：

  • Stream 复用 FUSE 的 snapshot 链——Stream 表实际上是一个"指向源表 + 持有 offset"的 view，读出来的是两个 snapshot 之间的差。
  • Iceberg / Delta 各起一个 Catalog，沿用 Databend 的 Catalog trait；表的 read_data 直接走它们各自的库（iceberg-rust、deltalake-rs）。
  • UDF 走 Arrow Flight：Databend 是 client，外部 UDF Server 在另一个进程/容器里；Pipeline 用 TransformUdfServer 把 DataBlock 切成 batch、并发发给 endpoint。

要点：

  • StreamTable 自身不存数据；它持有「源表 id + offset 起点」。
  • 读取时通过 source_table() 拿到底层 FuseTable，再让 FuseTable 在 changes_desc 模式下走 do_read_changes_partitions（06 文档已点出）。
  • Stream 本身的"消费"通过修改 offset 推进——这部分语义在 commit_table_meta 时与底层 FUSE 一并 CAS 更新（详见 02 文档）。
  • StreamStatus::MayHaveData / NoData 让 SHOW STREAMS 等 SQL 知道当前有没有新数据，免去扫表确认。

3.4 外部 UDF：Arrow Flight + Endpoint Pool

classDiagram class TransformUdfServer { +funcs +endpoints: BTreeMap +semaphore: Arc Semaphore +request_batch_rows +retry_times +transform_inner(ctx, block) DataBlock } class UDFFlightClient { +build_endpoint(addr,connect_timeout,request_timeout,user_agent) +do_exchange(stream) } class UdfFunctionDesc { +name +udf_type: UDFType +arg_types / return_type } TransformUdfServer --> UDFFlightClient TransformUdfServer --> UdfFunctionDesc

设计要点：

  • Arrow Flight do_exchange：把 DataBlock 转 RecordBatch 流式发给 Server，Server 计算后回流；列存零拷贝。
  • request_batch_rows 切小块：一个大的 DataBlock 切成多个小请求，提升并发与失败粒度。
  • Semaphore 全局上限：多个 query 同时跑 UDF 时不至于打爆 endpoint。
  • endpoints 按 server_addr 复用：跨多个 UDF 函数若指向同一 Server，共用 endpoint 连接池。
  • retry_times + 连接超时：网络波动时自动重试。

3.5 Script UDF — 同进程 Pool

pub trait RuntimeBuilder<T> {

}
classDiagram class Pool~R,B~ { +builder: B +runtimes: Mutex Vec~R~ +call(op) Result } class TransformUdfScript { +pool: Pool<JsRuntime, ...> } class UdafScript { +pool: Pool<...> } class UdfAggState { +Arc dyn Array } Pool --> TransformUdfScript Pool --> UdafScript UdafScript --> UdfAggState : 聚合中间态

特点：

  • 进程内 runtime（如 wasm/js/python embedded），用 Pool 复用，避免每个 batch 启动开销。
  • stub 实现：transform_udf_script_stub.rs / udaf_script_stub.rs 在编译没有 script-udf feature 时直接报错——保证 OSS 与 EE 二进制的一致行为。
  • UDAF 中间态是 Arc<dyn Array>：跨 partition 累计的部分聚合直接以 Arrow Array 在内存里传递，方便 partial+final 模型。

4. 关键流程

4.1 Stream 的"读增量"

sequenceDiagram autonumber participant Q as SELECT * FROM stream_t participant Cat as CatalogManager participant ST as StreamTable participant FT as FuseTable participant Read as do_read_changes_partitions Q->>Cat: get_table("default","stream_t") Cat-->>Q: StreamTable Q->>ST: source_table() / offset() ST->>FT: load source FuseTable + verify table_id 未变 ST->>FT: check_changes_valid(offset) Q->>FT: read_partitions(push_downs, change_type=Insert) FT->>Read: do_read_changes_partitions(snapshot 起点 -> 当前) Read->>Read: 沿 prev_snapshot_id 找区间，diff 出新 block + tombstone Read-->>Q: Partitions（增量 BlockMeta 集） Q->>Q: 跑常规 read_data + Pipeline

增量等价于 snapshot 链上的"区间 diff"：从 stream offset 处的 snapshot 开始，沿 prev_snapshot_id 反向走到当前最新；中间出现的新 block 就是 INSERT，删掉的对应 DELETE。结合表上的 change_tracking 选项（详见 06 文档 §8 未解之谜），可以拿到行级 _change_type。

注意：

  • UDF 的元数据持久化在 meta-service（UdfMgr → UserDefinedFunction 类型，在 META_CHANGE_LOG v160 加 update_on 字段，详见 02 文档）。
  • UDF Server 部署独立：可以是 Python/Wasm/任意语言，只要实现 Arrow Flight do_exchange。崩溃不会拖死 Databend 进程。

8. 未解之谜

  • Stream offset 推进的精确时机：上面案例说"消费推进 offset"，但实际是「显式 CONSUME」语句还是「INSERT INTO target SELECT FROM stream」隐式触发？需要在 binder 端跟踪 Statement::ConsumeStream（如果存在）。
  • change_tracking 与 _change_type：FUSE 表上要开启 change tracking 才能获得行级变更类型（insert/delete/update）；本仓库内 OPT_KEY_CHANGE_TRACKING 的写入路径与读取展开未深读，留给后续版本再展开。
  • Iceberg / Delta 写入路径：本篇侧重读；Iceberg 的 append.rs 与 Delta 的 commit 路径 (deltalake::DeltaOps) 用法如何映射到 Databend 的 commit_insertion，需要再读代码。
  • UDF Server 鉴权：endpoint 是 plain gRPC，没看到 mTLS / token 在 client 侧 enforce；可能在外部 sandbox 服务自己做。
  • 「Sandbox UDF + Agent」：README 强调 agent-ready，但本仓库内 agent 编排没有专属代码——它实际上就是「SQL + 外部 UDF Server」的别名，加上 Branching（FUSE Time-Travel）。这与用户原始假设里的"Python sandbox 子进程"不一致，本系列 01 文档已经标注。
  • HiveCreator 与 databend-common-storages-hive 不在本仓库 src/query/storages/ 下；它在 common/ 路径还是 EE 模块？global_services.rs::L≈132 直接 use databend_common_storages_hive::HiveCreator，但本系列没去找定义。如果用户实际跑 Hive 表，建议直接定位该 crate。
