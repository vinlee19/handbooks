07 · IO 与多级缓存：OpenDAL Layer 栈 + CacheManager

基于 commit fe693bb677。本篇覆盖 databend-common-storage（Operator 工厂与 Layer 栈）和 databend-storages-common-cache（CacheManager 的 20+ 种缓存）。这两层把"对象存储延迟"变成了"系统能容忍的延迟"。

1. 解决了什么问题

把列存表跑在对象存储上，IO 设计要解决三个矛盾：

  1. 统一接口 vs 后端碎片化：S3、GCS、Azure、OSS、OBS、COS、HDFS、本地 FS 都要支持，每家都有怪癖（签名版本、认证流程、API quirk）。
  2. 对象存储尾延迟 vs 用户期望毫秒级响应：S3 P99 经常上百毫秒；不能让裁剪/读 meta 这些"应该瞬完成"的操作裸跑。
  3. 重复读放大成本：同一张表的 snapshot/segment/bloom 在并发查询里被反复读，纯靠 OpenDAL 重读是钱多人傻的做法。

直接拿 aws-sdk-s3 加一个 LRU 的反例：

反例 后果
把 retry/timeout 写在每个调用点 漏一个就在生产挂死
简单全局 LRU 缓存原始 bytes 命中率低（key 太细），且每次都要再 deserialize
把缓存放在表级别 跨表的索引/分区元数据不复用；CTE 等场景重复加载
不区分 meta/data 缓存 大数据列把小元数据挤出去，命中率塌掉

Databend 的取舍：OpenDAL 把后端差异统一，再叠一组 Layer 处理重试/超时/限流/可观测性；CacheManager 按"对象类型"切了 20+ 个独立 LRU/Hybrid 缓存，让小 meta 不被大 data 挤掉。

3. 关键数据结构

3.1 OpenDAL Operator 与 Layer 栈

flowchart TB Op["Operator (动态/静态混合)"] --> L1["TimeoutLayer (must be first!)"] L1 --> L2["RuntimeLayer(GlobalIORuntime)\n所有 future 强制丢回 IO runtime"] L2 --> Finish[".finish() — 静态/动态 dispatch 边界"] Finish --> L3[HttpClientLayer] L3 --> L4["RetryLayer\n(jitter + DatabendRetryInterceptor)"] L4 --> L5[AsyncBacktraceLayer] L5 --> L6[LoggingLayer] L6 --> L7[FastraceLayer] L7 --> L8[METRICS_LAYER\n(Prometheus opendal_*)] L8 --> L9{有 max_concurrent_io_requests?} L9 -- 是 --> L10[ConcurrentLimitLayer] L9 -- 否 --> Backend L10 --> Backend["S3 / GCS / OSS / ..."]

来自 build_operator (L≈152) 的实际拼装顺序，这是源码里的硬规则：

  • TimeoutLayer 必须最先叠——OpenDAL 内部 future 只有被外层 timeout 包住才能在超时时被取消。
  • RuntimeLayer 紧跟 TimeoutLayer：把所有 IO future 转发到 GlobalIORuntime 这个独立 tokio runtime，避免污染 server 侧。
  • .finish() 是分界：之前的 layer 走静态 dispatch（编译期生效，性能更高），之后走动态 dispatch（避免编译时间爆炸——源码注释里有 rustc overflow evaluating 的吐槽）。
  • RetryLayer 在 HttpClientLayer 之后：retry 需要看到 HTTP 错误才能决定是否重试。
  • METRICS_LAYER 在最后：每一层的延迟都被它统计，确保指标真实反映"用户感知到的延迟"。
  • 环境变量后门：_DATABEND_INTERNAL_RETRY_TIMEOUT / _DATABEND_INTERNAL_RETRY_IO_TIMEOUT / _DATABEND_INTERNAL_MAX_CONCURRENT_IO_REQUEST / _DATABEND_INTERNAL_POOL_MAX_IDLE_PER_HOST 全在 build_operator 中读取——生产事故时不需要改 config 文件就能临时降级。

为什么按对象类型切？因为这些对象的体积分布相差几个数量级：snapshot ≈ KB，segment ≈ KB-MB，bloom 文件 ≈ KB-MB，column data ≈ MB-GB。共享一个 LRU 等于让大 data 把小 meta 挤掉，命中率塌掉。各自一个 LRU 的代价是配置项变多，但是 Databend 在 CacheConfig 里给每种缓存独立的容量上限。

3.5 HybridCache：内存优先 + 异步回填磁盘

flowchart LR GET["get(k)"] --> M{内存命中?} M -- 是 --> Hit[返回] M -- 否 --> D{磁盘命中?} D -- 是 --> P[Promote 到内存] P --> Hit D -- 否 --> Miss[返回 None\n上层去 OpenDAL 拿] PUT["put(k,v)"] --> Mem[写内存] Mem --> Q[异步入队\n(by table_data_cache_population_queue_size)] Q --> Disk[磁盘 LRU 写]

异步入队——put 是非阻塞的；磁盘写在后台 queue 上跑，避免拖累查询主线程。table_data_cache_population_queue_size 默认是 available_parallelism * 5（manager.rs::L≈168）。

EE only：allows_on_disk_cache: AtomicBool 在 OSS 模式下硬性为 false（manager.rs::L≈166）。

4. 关键流程

4.1 读路径：先缓存、后 OpenDAL

sequenceDiagram autonumber participant FT as FuseTable.do_read_partitions participant CM as CacheManager participant SnapC as TableSnapshotCache participant SegC as CompactSegmentInfoCache participant BFC as BloomIndexFilterCache participant OD as OpenDAL Operator participant LayerStack as Timeout/Retry/Limit Layer FT->>CM: get(snapshot_loc) CM->>SnapC: get alt 命中 SnapC-->>FT: Arc<TableSnapshot> else 未命中 SnapC-->>CM: None CM->>OD: read snapshot.json OD->>LayerStack: future LayerStack-->>CM: bytes CM->>SnapC: put CM-->>FT: Arc<TableSnapshot> end loop 每个 segment_loc FT->>CM: get(segment_loc) CM->>SegC: get alt 命中 SegC-->>FT: SegmentInfo else 未命中 CM->>OD: read segment.mpk OD-->>CM: bytes (zstd 解压) CM->>SegC: put end end loop 每个 BlockMeta FT->>FT: RangeIndex 裁剪（用内存里的 col_stats，零 IO） alt 仍存活 FT->>CM: get(bloom_filter_index_location) CM->>BFC: get alt 命中 → 用 bloom 再裁 else 未命中 → 读磁盘/对象存储 + put end end end

CachedReader / CachedTtlReader（src/query/storages/common/cache/src/read/）封装了上面这套"先 cache 后 OpenDAL + miss 时反向 put"的逻辑，所有 reader 都基于它。

4.2 写路径：旁路写缓存

写入侧并不依赖 cache miss-then-fill；而是在写完一个 snapshot/segment 后主动 put，让随后的查询直接命中：

// src/query/storages/fuse/src/operations/commit.rs:191（节选）
// 写完 statistics 文件后立刻塞 cache，不等下次查询去 GET
TableSnapshotStatistics::cache().insert(table_statistics_location, table_statistics.unwrap());

类似地，bloom/inverted/vector index 写入侧也会主动喂 cache（详见 08 文档）。

4.3 ConcurrentLimitLayer：把"突发并发"压成"稳定吞吐"

flowchart LR Q[N 个 worker 同时\nGET 不同 block.parquet] --> CL[ConcurrentLimitLayer\n(permits = max_concurrent_io_requests)] CL -- 通过 --> S[实际发 HTTP 到 S3] CL -- 阻塞 --> W[等许可]

没有这层时，event=Async + worker=64 的查询会瞬间发 64 个 GET 给 S3，遇到 P99 100ms+ 时把 socket 池打爆。max_concurrent_io_requests 通常按 「带宽 ÷ 平均块大小」推算。

4.4 RetryLayer：抖动 + 自定义拦截

flowchart LR ERR[请求出错] --> CLS{HTTP 状态} CLS -- 5xx / 网络抖动 --> R[RetryLayer 决定重试] CLS -- 4xx 永久错误 --> F[直接失败] R --> J[Jitter 退避] J --> RETRY[重发请求] RETRY --> METRIC[METRIC_OPENDAL_RETRIES_COUNT.inc()] RETRY --> NOTI[DatabendRetryInterceptor.notify\n打 log]

with_jitter() 是关键——多 worker 同时遇到限流时，指数退避必须加抖动，否则下一轮还会同步重试，雪崩。

7. 端到端案例

SELECT count(*) FROM t WHERE x > 1，IO/缓存段：

sequenceDiagram autonumber participant FT as FuseTable participant CM as CacheManager participant OD as OpenDAL participant TL as Timeout/Retry/Concurrent Layer participant S3 FT->>CM: TableSnapshotCache.get(snapshot_loc) CM-->>FT: Arc<TableSnapshot> (命中，0 RPC) loop segments FT->>CM: CompactSegmentInfoCache.get alt 命中 CM-->>FT: SegmentInfo else 首次访问 CM->>OD: read segment_loc OD->>TL: future TL->>S3: GET object S3-->>TL: bytes (压缩后) TL-->>OD: bytes OD-->>CM: 解压 + 反序列化 → SegmentInfo CM->>CM: put SegmentInfo CM-->>FT: SegmentInfo end end FT->>FT: RangeIndex 裁剪（纯内存 col_stats，0 RPC） FT->>CM: BloomIndexFilterCache.get for bloom on x（本例不适用，跳过） FT->>CM: ParquetMetaDataCache.get(block.parquet) alt 命中 CM-->>FT: footer metadata else CM->>OD: range read footer (~ 8KB tail) OD->>TL: future TL->>S3: GET range S3-->>TL: bytes TL-->>CM: footer end FT->>OD: 并发 GET col=x 范围 OD->>TL: ConcurrentLimitLayer 排队 TL->>S3: 受限并发 GET S3-->>FT: parquet pages FT->>CM: ColumnDataCache.put(命中后续查询)

注意：

  • RangeIndex 不是缓存命中或未命中——它使用的 col_stats 已经在 BlockMeta 里，整个裁剪不发任何 RPC，只是内存比较。
  • Parquet footer 是 range read——典型 8KB，非常小，但是命中率影响巨大（footer 决定列偏移）。
  • ColumnDataCache 默认是 Hybrid——磁盘大但命中率高的列（频繁过滤的列）会被异步落盘。
