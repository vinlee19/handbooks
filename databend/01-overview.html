01 · 总览：三层架构与设计取舍

基于 commit fe693bb677。本篇用一个进程视角与一个数据视角，把 Databend 的「为什么是这样的」一次性串清楚，作为后续 10 篇专题文档的索引。

1. 解决了什么问题

Databend 的目标是在对象存储（S3/GCS/Azure/OSS/HDFS）之上跑 OLAP，并把分析、向量检索、全文检索、agent 编排（Sandbox UDF + SQL）放进同一个引擎。

它不是 ClickHouse/Doris 那种「本地盘 shared-nothing」体系，也不是 Snowflake 那种专有云服务——它的取舍是：

本地盘 OLAP                 Snowflake                 Databend
┌─────────────┐            ┌─────────────┐           ┌─────────────┐
│ 数据 = 节点  │            │ 数据 = 内部 │           │ 数据 = 客户  │
│ 关键路径上   │            │ FDN，受厂商 │           │ S3 桶，自托管│
│ 最快但难弹性 │            │ 控制         │           │ 弹性 + 开放  │
└─────────────┘            └─────────────┘           └─────────────┘
维度 本地盘 OLAP（CK/Doris/StarRocks 共享 Nothing） Snowflake Databend
数据所在位置 节点本地盘 厂商云存储（FDN） 客户对象存储（S3/GCS/Azure/OSS）
计算节点状态 有状态（数据 + 元数据 + 计算） 无状态 完全无状态
弹性 扩缩容需 reshard，慢 秒级弹性（厂商提供） 秒级，新 query 节点拉一份 catalog 即可
元数据 与计算共置 / 单独服务 厂商内部 独立 Raft 服务（已迁出主仓）
表格式 自有列存格式 专有 FUSE 引擎 + Parquet（开放）
索引 Bitmap/Bloom/二级索引 自动微分区 Bloom + Inverted(Tantivy) + Vector(HNSW) + Range + Spatial
Time Travel 部分支持 支持 原生 Git-like 链表
二开难度 中（C++/Java） 关闭 Rust 全栈开源

2. 在 Databend 中的位置：进程拓扑

Databend 是一个严格三层的分布式系统。客户机不直接读写存储；元数据由独立服务承载。

flowchart TB subgraph Client["Client"] C1[bendsql / mysql client / driver] end subgraph QueryCluster["databend-query 集群（无状态，可水平扩展）"] direction TB Q1["query node #1\nMySQL/HTTP/FlightSQL\nFlight RPC（节点间）"] Q2["query node #2"] Q3["query node #N"] end subgraph Meta["databend-meta 集群（OpenRaft，奇数节点）"] M1[Leader] M2[Follower] M3[Follower] end subgraph Storage["对象存储（OpenDAL 抽象）"] direction LR S3[S3 / GCS / Azure / OSS / HDFS / FS] end C1 -- "MySQL 3307 / HTTP 8000 / FlightSQL 8900" --> Q1 Q1 <-- "Flight RPC 9091\n(集群发现 + Shuffle)" --> Q2 Q1 <-- "Flight RPC" --> Q3 Q1 -- "gRPC" --> M1 Q2 -- "gRPC" --> M1 Q3 -- "gRPC" --> M1 M1 <-- "Raft" --> M2 M1 <-- "Raft" --> M3 Q1 -- "OpenDAL" --> S3 Q2 -- "OpenDAL" --> S3 Q3 -- "OpenDAL" --> S3

三个关键事实，必须在阅读源码前消化：

  1. query 节点完全无状态——没有任何持久化数据落本地盘（除磁盘缓存外）。重启即可。
  2. meta 服务的核心实现已迁出本仓库到 databend-meta。本仓库内 src/meta/ 只剩客户端类型、protobuf、MetaStore 接口和 metactl/metabench/metaverifier 工具。详见 02-meta-service.md。
  3. embedded meta 模式硬性禁用——entry.rs::init_services (L≈89) 直接 return Err，不允许把 meta 嵌进 query 进程。

源码：src/binaries/query/entry.rs::start_services (L≈121)。请注意：

  • FlightService 是节点间 RPC——不是面向客户端的 FlightSQL。FlightSQL 走另一个端口（flight_sql_handler_port，默认 8900）。
  • MetricService 是 Prometheus exporter，路径 /metrics。
  • AdminService 提供 cluster/node 自检 HTTP API，与 MetricService 端口分开。

7. 端到端案例：SELECT count(*) FROM t WHERE x > 1

这条 SQL 会在后续每篇文档中被局部展开。这里只画进程边界视角，让你看到「请求到底在哪些进程之间流动」。

sequenceDiagram autonumber participant Cli as bendsql participant Q as query node participant Meta as meta-service participant S3 as S3 (OpenDAL) Cli->>Q: HTTP POST /v1/query \n {sql: "SELECT count(*) FROM t WHERE x > 1"} Q->>Q: parse_sql + Binder::bind Q->>Meta: get_table("default", "t") (gRPC) Meta-->>Q: TableInfo + 最新 Snapshot location Q->>Q: Cascades / DPHyp 优化 → PhysicalPlan Q->>Q: PipelineBuilder::finalize → Pipeline DAG Q->>S3: GET <snapshot.json> S3-->>Q: TableSnapshot Q->>S3: GET <segment.json> 数个 S3-->>Q: SegmentInfo[] Q->>Q: 用 BlockMeta(min/max + bloom) 裁块 Q->>S3: 仅对存活的 block 发 GET (parallel) S3-->>Q: Parquet bytes (压缩) Q->>Q: 解压 → DataBlock → FilterTransform(x>1) → FinalAggregate(count) Q-->>Cli: {data: [[N]]}

注意第 5、7 步：Snapshot 和 Segment 都是 JSON/二进制小文件，不是数据本身；真正的列存数据在第 9 步才被并发拉取，且仅拉通过裁剪后的 block——这是 Databend 在对象存储上还能压住延迟的根本原因。
