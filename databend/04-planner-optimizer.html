04 · Planner / Optimizer：从 SExpr 到最优计划

基于 commit fe693bb677。本篇覆盖 databend-common-sql::planner::optimizer，把 Binder 给出的 SExpr 一路打磨成 Cascades / DPHyp 协同后的最终逻辑+物理混合树。

1. 解决了什么问题

OLAP 优化器同时面对四类问题，没有任何单一框架能"一招打十"：

类型 例子 适合的方法
表达式重写 x = 1 OR x = 1 → x = 1 等价规则（heuristic）
谓词下推 / 投影下推 WHERE x>1 AND y='a' 推到 Scan RBO 规则
子查询解相关 IN (SELECT ... WHERE outer.x = inner.x) → SemiJoin 专门的 decorrelator
Join 重排 10 表 join，如何选最便宜的连接顺序 DPHyp / Cascades CBO

把这些都丢给一个 Cascades 引擎并不现实——Cascades 在大查询树上爆炸。Databend 的取舍：把流水线拆开，先用一组规则做掉廉价重写、再用 DPHyp 解决 join 顺序、最后用 Cascades 做精细的物理性质（distribution、order）枚举。每段都可以独立替换。

3. 关键数据结构

3.1 SExpr — 不可变逻辑表达式树

// src/query/sql/src/planner/optimizer/ir/expr/s_expr.rs:48
pub struct SExpr {
    pub plan: Arc<RelOperator>,
    pub children: Vec<Arc<SExpr>>,

    original_group: Option<IndexType>,  // 来自 cascades memo 的回溯指针

    rel_prop: Arc<OnceLock<Arc<RelationalProperty>>>, // 输出列、属性
    pub(crate) stat_info: Arc<OnceLock<Arc<StatInfo>>>, // 估算基数 + 列直方图
    pub(crate) applied_rules: AppliedRules,           // 位图，避免重复应用
}

要点：

  • 不可变：所有变换都生成新 SExpr，children 是 Arc，复用上一版子树。
  • 记忆化：rel_prop / stat_info 用 OnceLock 懒计算；同一个子树的属性在多个父算子里只算一次。
  • applied_rules：cascades 探索时用位图记录"这个 SExpr 已经试过哪些 rule"，杜绝循环。

3.2 RelOperator — 24 种关系算子

// src/query/sql/src/planner/plans/operator.rs:147
pub enum RelOperator {
    Scan(Scan),                              // 表扫描
    Join(Join),                              // 单一节点，类型由内部 JoinType 决定
    EvalScalar(EvalScalar),                  // 计算列
    Filter(Filter),                          // WHERE / HAVING
    Aggregate(Aggregate),                    // 聚合
    Sort(Sort), Limit(Limit),
    Exchange(Exchange),                      // 分布式数据交换（hash/broadcast/merge）
    UnionAll(UnionAll),
    DummyTableScan(DummyTableScan),          // SELECT 1 这类不读表的语句
    Window(Window), ProjectSet(ProjectSet),
    ConstantTableScan(ConstantTableScan),
    ExpressionScan(ExpressionScan),          // 子查询表达式扫描（hash join build cache）
    CacheScan(CacheScan),
    Udf(Udf), AsyncFunction(AsyncFunction),
    RecursiveCteScan(RecursiveCteScan),
    Mutation(Mutation), CompactBlock(CompactBlock), MutationSource(MutationSource),
    MaterializedCTE(MaterializedCTE), MaterializedCTERef(MaterializedCTERef),
    Sequence(Sequence),                      // 序列化执行依赖
}

注意 Exchange 也是逻辑算子——它在优化器内部就被引入，不是物理化阶段才出现。这让"分布式优化"也能 reuse 同一套规则框架。

3.4 Cascades 内部结构

classDiagram class CascadesOptimizer { +memo: Memo +cost_model: Box dyn CostModel +explore_rule_set: RuleSet +optimize_sync(s_expr) Result~SExpr~ +optimize_internal(s_expr) } class Memo { +groups: Vec~Group~ +root: Option~GroupIndex~ } class Group { +group_index +exprs: Vec~MExpr~ +winner: Option~MExpr~ +rel_prop / stat_info } class MExpr { +group_index +children: Vec~GroupIndex~ +applied_rules: AppliedRules } class TaskManager { +pending: VecDeque~Box dyn Task~ +run_until_empty() } class Task { <<trait>> OptimizeGroup OptimizeExpr ExploreGroup ExploreExpr ApplyRule } CascadesOptimizer --> Memo CascadesOptimizer --> TaskManager Memo --> Group Group --> MExpr TaskManager --> Task

Memo 把所有等价的 SExpr 折叠到同一个 Group，避免组合爆炸；TaskManager 推动「先 explore，再 optimize」的经典 Cascades 调度。

4. 关键流程

4.1 顶层流水线

optimize_query (optimizer.rs::L≈246) 内部按这个顺序串接（每行都是源代码里的 .add(...)）：

flowchart TB S0[SExpr from Binder] S0 --> A1[SubqueryDecorrelatorOptimizer] A1 --> A2[RuleStatsAggregateOptimizer] A2 --> A3[CollectStatisticsOptimizer] A3 --> A4[RuleNormalizeAggregateOptimizer] A4 --> A5[PullUpFilterOptimizer] A5 --> A6{enable_cse_optimizer?} A6 -- 是 --> A7[CommonSubexpressionOptimizer] A6 -- 否 --> A8 A7 --> A8[RecursiveRuleOptimizer\n@DEFAULT_REWRITE_RULES] A8 --> A9[CTEFilterPushdownOptimizer] A9 --> A10[SyncMaterializedCTERefOptimizer] A10 --> A11[RecursiveRuleOptimizer\n@SplitAggregate] A11 --> A12[DPhpyOptimizer\n标记 dphyp_optimized=true] A12 --> A13[EliminateSelfJoinOptimizer] A13 --> A14[SingleToInnerOptimizer] A14 --> A15[DeduplicateJoinConditionOptimizer] A15 --> A16{enable_join_reorder?} A16 -- 是 --> A17[CommuteJoin Rule] A16 -- 否 --> A18 A17 --> A18{force_eager_aggregate?} A18 -- 是 --> A19[RuleEagerAggregation] A18 -- 否 --> A20 A19 --> A20[CascadesOptimizer] A20 --> A21{planning_agg_index?} A21 -- 否 --> A22[EliminateEvalScalar] A21 -- 是 --> A23 A22 --> A23[CleanupUnusedCTEOptimizer] A23 --> OUT[最终 SExpr]

关键设计取舍：

  • 解相关在最前面——一旦消除了相关子查询，下游所有规则都不需要处理「外层引用」的特殊情况。
  • 统计在第 3 步采集，但要到第 12 步（DPHyp）才真正用：早采集是因为后续多个规则（CSE、聚合规则、CTE）也要参考估算基数。
  • DPHyp 在 Cascades 之前：DPHyp 对 join 顺序做完最优搜索后，把 dphyp_optimized 这个 flag 写进 OptimizerContext，Cascades 在 optimize_internal 里看到它就关闭 join enumeration 规则集（见 cascade.rs::L≈185），只做剩余的物理性质 / 算子选择。
  • Cascades 失败回退：如果 Cascades 因超时或其他原因失败，optimize_sync 会 fallback 到 DistributedOptimizer（或者干脆原 SExpr）（cascade.rs::L≈107）——这是工业系统的 must-have，不能因为优化器内部 bug 让查询直接挂掉。

4.2 RBO 规则——push-down/eliminate 范式

DEFAULT_REWRITE_RULES 在 rule.rs 里有近 40 条，按"先简化 → 后下推 → 再处理 join → 最后扫描层"的顺序：

flowchart TB subgraph Simplify["简化"] EliminateSort DeduplicateSort EliminateUnion MergeEvalScalar NormalizeScalarFilter FilterNulls EliminateFilter MergeFilter end subgraph PushFilter["谓词下推"] PushDownFilterUnion PushDownFilterAggregate PushDownFilterWindow PushDownFilterWindowTopN PushDownFilterSort PushDownFilterEvalScalar PushDownFilterJoin PushDownFilterProjectSet end subgraph PushLimit["LIMIT/Sort 下推"] MergeLimit PushDownLimit PushDownLimitUnion PushDownSortEvalScalar PushDownLimitEvalScalar PushDownLimitSort PushDownLimitWindow PushDownRankLimitAggregate PushDownLimitOuterJoin PushDownLimitScan end subgraph JoinSimp["Join 简化"] SemiToInnerJoin FoldCountAggregate TryApplyAggIndex end subgraph ScanLayer["Scan 层下推"] PushDownFilterScan PushDownPrewhere PushDownSortScan PushDownSortFilterScan PushDownLimitFilterScan HierarchicalGroupingSetsToUnion GroupingSetsToUnion end Simplify --> PushFilter --> PushLimit --> JoinSimp --> ScanLayer

注意 PushDownPrewhere 必须在所有其他下推之后——这是 ClickHouse-style 的 prewhere 优化，把高选择度谓词放进 scan 阶段第一遍读，第二遍再读 projection 列。

4.3 DPHyp — 多表 join 的动态规划

DPHyp（dynamic programming with hypergraph）适合 ≤ ~16 个表的 inner/outer join。算法核心思路：

flowchart LR S[初始 SExpr 含 N 个 Join 节点] --> QG[query_graph.rs\n构造连接超图] QG --> JR[join_relation.rs\n基础关系（叶子表）] JR --> JN[join_node.rs\nDP 子集状态] JN --> DP[dphyp.rs\nDPHyp 主算法\nemit_csg / emit_cmp / emit_csg_cmp] DP --> Pick[挑选最佳 join 顺序\nbuild new SExpr 树] Pick --> OPTSE[加上 dphyp_optimized=true]

源码：

  • src/query/sql/src/planner/optimizer/optimizers/hyper_dp/dphyp.rs::DPhpyOptimizer (L≈48)
  • query_graph.rs 把 SExpr 中的 Join/Filter 折成超图（边 = 谓词，顶点 = 基础关系）。
  • join_node.rs 缓存子集 → 当前最优 plan 的 hash map，状态空间是 2^N。

DPHyp 不重写非 join 节点；它只调整 join 顺序，调整完用 build_unary / build_binary 把新树拼起来。

源码：

  • src/query/sql/src/planner/optimizer/optimizers/cascades/tasks/：5 个 task 类型 + TaskManager。
  • cascade.rs::L≈173 optimize_internal：根据 enable_cbo 和 dphyp_optimized 切换 RuleSet（StrategyFactory::create_strategy）。
  • cascade.rs::L≈202 root_required_prop：当启用 enforce_distribution 时，根 group 必须达到 Distribution::Serial，从而在内部塞入合适的 Exchange::Merge 算子。

4.5 解相关（Subquery Decorrelator）

flowchart TB IN["IN/EXISTS/标量子查询，含 outer 引用"] --> SD[subquery_decorrelator.rs L≈169] SD -->|EXISTS / NOT EXISTS| SJ[Semi/Anti Join] SD -->|IN / NOT IN| MJ[Mark Join] SD -->|Scalar Subquery| LSJ[LeftSingleJoin\n空时返回 NULL] SD -->|相关投影| EVS[EvalScalar 提到外层] SJ --> OK[已无相关引用] MJ --> OK LSJ --> OK EVS --> OK

这一步保证后续所有规则的 RelOperator 树不含 correlated reference，规则不需要写"如果是相关子查询则跳过"这种特例。

7. 端到端案例

SELECT count(*) FROM t WHERE x > 1，优化器段：

sequenceDiagram autonumber participant Plan as Plan::Query.s_expr participant Opt as optimize_query participant SD as SubqueryDecorrelator participant Stat as CollectStatistics participant RR as RecursiveRuleOptimizer participant DP as DPhpy participant CO as CascadesOptimizer participant PB as PhysicalPlanBuilder Plan->>Opt: SExpr(EvalScalar(Aggregate(Filter(Scan(t))))) Opt->>SD: 没有子查询，no-op Opt->>Stat: 给 Scan/Filter/Aggregate 估行数 Opt->>RR: DEFAULT_REWRITE_RULES RR->>RR: PushDownFilterScan: Filter(Scan(t,x>1))→Scan(t, prewhere=x>1) RR->>RR: FoldCountAggregate: 没遇到无谓词 count(*)，跳过 Opt->>DP: 单表，no-op Opt->>CO: 现在的 SExpr 简单，单 group CO->>CO: ApplyRule: TryApplyAggIndex 检查 t 上是否有 agg index→否 CO->>CO: 物理性质：单节点 Serial→不需要 Exchange CO-->>Opt: SExpr(Aggregate(Scan(t, prewhere=x>1))) Opt-->>PB: 终态 SExpr PB-->>PB: 转 PhysicalPlan: TableScan(t,prewhere)→FinalAggregate(count)

注意细节：

  • WHERE x > 1 被推进 Scan 算子的 push_downs 字段（不是另起 Filter 算子），这就是 06 文档里 do_read_partitions(push_downs) 真正接收到的东西。
  • count(*) 没有 GROUP BY，物理形态是单 worker FinalAggregate，不需要 partial/final 分裂。
  • 因为只有一个表 + 一个聚合，整条流水线绝大多数 stage 都是 no-op；这是 Databend 把"小查询路径"做轻的重要原因。
