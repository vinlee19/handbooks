02 · Meta Service：客户端层 + 外部 OpenRaft 状态机

基于 commit fe693bb677（本仓库）+ databend-meta main（/tmp/databend-meta，浅克隆）。本篇横跨两个仓库：本仓库内只剩 client/types/proto，核心 raft 实现在 v1.2.874 之后迁出到独立的 databend-meta。

1. 解决了什么问题

存算分离后，每个 query 节点都是无状态的临时计算。"哪些表存在、字段是什么、谁有权限、当前指向的 snapshot 在哪里"——这些必须有一个外部强一致 KV 来托管。Databend 选择的是「在 KV 之上分层」：

层 谁来管
传输 gRPC：watch / kv_read_v1 / install_snapshot_v1（兼容老接口）
协议 KvApi（通用 K/V 抽象）+ SchemaApi（数据库/表/索引/...）
类型 Rust 类型 TableMeta / DatabaseMeta / IndexMeta / ...（在 client 端用）
序列化 protobuf + META_CHANGE_LOG 版本表
共识 OpenRaft，写日志 + 状态机 + 快照（外部仓库）
存储 raft_log_v004 (WAL) + sm_v003 (内存层级 KV，定期落 snapshot)

直接用 etcd / Zookeeper 的反例：

反例 后果
直接拿 etcd 当 backend，把所有 schema JSON 塞进一个 key watch 风暴 + 写放大；schema 演进无法版本化
用 ZK，把元数据塞 znode 序列化层不可演进；ZK 的 snapshot 模型不适合大 KV
自己用 Raft+RocksDB 写 重复造轮子；状态机演进缺少版本控制工具链

Databend 的取舍：自研 meta 服务，但底层 raft 用 OpenRaft（同一团队），类型/protobuf/版本管理留在 query 仓库——这样 query / meta 升级解耦：query 端只需读懂 protobuf 版本，server 端只需把字节按 raft 复制。

flowchart LR W[Writer 写出 protobuf bytes] --> ME[bytes 内嵌 ver=VER, min_reader=MIN_READER_VER] R1[Reader v=N\nN >= ver.min_reader] --> OK1[能读] R2[Reader v=N\nN < min_reader] --> FAIL[直接失败 — 上线时强制升级 reader] ME --> R1 ME --> R2

MIN_READER_VER 是滚动升级的安全线：写新格式前，运维必须先把所有 reader 升到 ≥ 24。每加一个版本都必须挂一个 tests/it/vNNN_*.rs 测试，verify 旧字节能在新代码下还原（注释 L≈205-209 在源码里强制提醒开发者）。

3.5 状态机 sm_v003 与日志 raft_log_v004

flowchart TB subgraph SMv3["sm_v003"] LD[LeveledStore\n多级 KV：Level0=可写, Level1+=只读 base] APPLIER[applier/] COMP[immutable_compactor + compactor_acquirer] SNAP[snapshot_loader / snapshot_store_v003] KVAPI[sm_v003_kv_api.rs] end subgraph LOGv4["raft_log_v004"] WAL[WAL 写流：log_store_meta + io_phase + io_desc] CB[callback (append/commit)] UTIL[importer / codec_wrapper] end R[OpenRaft] --> WAL R --> APPLIER APPLIER --> LD COMP --> LD SNAP --> LD KVAPI --> LD

设计要点：

  • LeveledStore 像 LSM 的多层：L0 可写用于接收新 apply 的变更；Lₙ (n≥1) 只读作为基线 KV。新 leader 不需要重放整段日志，只需"L0 + 基线"即代表当前状态。
  • Compactor 把 L0 周期性合并到 Lₙ，再做一次 snapshot 上传。
  • raft_log_v004 是 WAL 文件版日志，不依赖 sled——这是从早期 sled-store 演进的成果（sled-store 仍然在 crates/server/sled-store/ 作为旧版兼容）。
  • SpawnApi 泛型参数 SP：让测试可以注入自己的 task 调度器，方便确定性测试。

4. 关键流程

4.1 Query → Meta：一次读

sequenceDiagram autonumber participant Q as Query node participant Cli as MetaGrpcClient participant Net as gRPC participant Svc as MetaService (Leader) participant RR as RaftLeader participant SM as sm_v003 Q->>Cli: SchemaApi.get_table("default","t") Cli->>Cli: 拼 key 前缀 / 选择 endpoint Cli->>Net: kv_read_v1(GetReq) Net->>Svc: 收请求 Svc->>RR: ensure_leader / read_index（线性化读保障） RR->>SM: read("__fd_table_by_id/...") SM-->>Svc: SeqV<TableMeta bytes> Svc-->>Net: KvReply Net-->>Cli: bytes Cli->>Cli: proto-conv decode → TableMeta（按 ver） Cli-->>Q: TableMeta

注意 read_index/linearizable read 通过 OpenRaft 内部协议实现；客户端不需要知道。

4.2 Query → Meta：一次写（commit table snapshot）

sequenceDiagram autonumber participant Q as Query (CommitSink) participant Cli as MetaGrpcClient participant L as Leader MetaNode participant F1 as Follower participant F2 as Follower participant SM as sm_v003 Q->>Cli: SchemaApi.update_table_meta(prev_seq, new_meta) Cli->>L: TxnRequest { compare prev_seq == X, then put new_meta } L->>L: 包成 raft entry, 写 WAL L->>F1: AppendEntries L->>F2: AppendEntries F1-->>L: ack F2-->>L: ack L->>SM: apply（CAS：seq 一致才成功） alt CAS 成功 SM-->>L: TxnReply { success=true, new_seq } L-->>Cli: ok Cli-->>Q: 成功 else seq 不一致 SM-->>L: TxnReply { success=false } L-->>Cli: TableVersionMismatched Cli-->>Q: 失败 → set_backoff 重试（详见 06 文档） end

整条路径里：

  • CAS 保证强一致：prev_table_seq 是 query 的"乐观锁"。
  • Raft 保证多副本：commit 不返回直到大多数副本确认。
  • 写完 SM 才回包：避免半成功。

4.3 滚动升级 / 版本兼容

flowchart LR subgraph Cluster["query 集群（v1.2.x）"] Q1[Query 节点 1] Q2[Query 节点 2] end subgraph Meta["databend-meta 集群"] M1[Meta 1] M2[Meta 2] M3[Meta 3] end Q1 --(VER=173)-->M1 Q2 --(VER=170)-->M1 M1 --> CHK{字节内嵌的 ver in MIN_READER_VER..=VER ?} CHK -- 是 --> OK[正常读] CHK -- 否 --> FAIL[要求升级 query]
  • 任何一条 protobuf 字节都内嵌 ver 与 min_reader_ver；不同版本的 query 都能从 meta 拿同一份字节，按各自 reader 解码。
  • 真实滚动顺序：先升 meta，再升 query；而当前 commit 的 MIN_READER_VER = 24 意味着升级到 v173 写出的字节，最老的 query 必须 ≥ v24（这是历史断面，老 query 老 meta 早已不兼容，文档不需要管）。
