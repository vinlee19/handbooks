1. 起点：Scanner 如何编译成执行计划

rust/lance/src/dataset/scanner.rs（16,344 行，全仓库最大文件）是查询的"编译器前端"。它是一个 fluent builder，最终 create_plan() 产出一棵 DataFusion ExecutionPlan 树：

图 3-1 · 查询计划树。三分支（ANN / 标量索引 / 顺序扫描）最终都汇成 row address 流进入 TakeExec，或作为纯扫描直接出流。

DataFusion 在这里的角色

Lance 不是"用 DataFusion 做 SQL 解析"那么简单：Scanner::analyze_plan/create_plan 手工构建物理计划节点（不经 volcano 逻辑优化），然后可交给 lance/src/datafusion.rs 的 DataFrame 做进一步关系代数（join/aggregate）。谓词拆分是关键优化：DataFusion 优化器把 WHERE 拆成"索引可回答"与"需要回表验证"两半——前者变 ScalarIndexExec 掩码，后者留在 LanceFilterExec。

2. 文件读取层：structural FileReader

v2.1 起读取器重构为 structural reader（lance-file/src/reader/structural.rs + versions/v2_*/reader.rs）。核心思想：读取器的每一层都通过 trait 组合，文件版本只决定"组装哪套实现"：

// lance-file/src/reader.rs —— 关键抽象
pub struct FileReader  { metadata: CachedFileMetadata, scheduler: Arc<ScanScheduler>, ... }
pub trait ReadProjection     // 把用户 schema 投影成"物理列读取计划"
pub trait ProjectedReader    // 按投影读取：decode_column / decode_pages

// 版本组装（versions/mod.rs）—— 每个版本给出自己的组合根
fn read_projection(version) -> Result<Arc<dyn ReadProjection>> {
    match version {
        V2_0 => v2_0::read_projection(),  V2_1 => v2_1::read_projection(),
        V2_2 => v2_2::read_projection(),  V2_3 => v2_3::read_projection(), ... }}
图 3-2 · 六层调用栈。注意没有任何一层会"等待"：调度器发完请求立刻处理下一个。

3. I/O 调度器：Lance 性能的心脏

rust/lance-io/src/scheduler.rs（约 5000 行含测试）实现了一个带优先级 + 背压的异步 I/O 队列。三个关键机制：

机制一：u128 优先级编码

每个 I/O 请求携带 priority: u128。高位来自解码器赋予的"行号优先级"（page 的首行号，或 ANN 查询的分区优先级），低位由 split_priority 拆出子优先级。队列永远先服务优先级最小的请求，但有一条巧妙的旁路规则（scheduler.rs:156-165）：队头任务若优先级 ≤ 所有在途请求的最小优先级，则直接旁路发出，避免"低优先级任务堵住队列头"的死锁。

机制二：字节背压（io_buffer_size_bytes）

调度器为"已读入但未被消费"的字节设预算（默认 max_bandwidth = 32MiB × io_parallelism）。解码太慢→预算耗尽→I/O 循环暂停发新请求；Response::drop 时退还预算（即使 future 被取消也保证释放）。这是流式系统防止 OOM 的标准做法，但 Lance 把粒度做到了"每个请求"。

机制三：标准 vs Lite 双队列

IoQueueType::{Standard, Lite}：本地盘/低延迟后端用 Lite（省内存、少簿记），S3 等高延迟后端用 Standard（深度流水线）。可通过 LANCE_USE_LITE_SCHEDULER 环境变量或对象存储的 prefers_lite_scheduler() 自动选择。

图 3-3 · 四个执行域：调度决策 → 网络 I/O → CPU 解码 → 缓存。全异步、全流水。

4. Search Cache：随机访问的"页目录"

随机访问前需要知道"第 i 行在哪个 page、page 用什么编码、miniblock 元数据长什么样"。这些统称 search cache（LRU），按列存于 FileReader。初始化阶段（init phase）一次加载：列元数据、miniblock 元数据、字典。全量扫描则刻意绕过它（冷扫描不为一次性读预热缓存）。

缓存条目内容何时加载
列元数据 ColumnInfopage 位置表 + 每页 encoding proto首次投影该列
MiniBlock 元数据每块 2 字节的 (字数, log2 值数)首次随机访问该列
字典（dict 编码）解码后的字典数组init phase
Repetition index行→item 换算表init phase（嵌套列）
索引页/向量缓存IVF 质心、PQ 码本、HNSW 邻接首次 ANN 查询

5. 特殊读法：take / take_blobs / sample

take(indices)
全局行号 → (fragment, offset) 二分（fragment_offsets 预计算）→ 各 fragment 并行随机访问 → 按请求顺序重组。百万级 take 会被分批。
take_blobs
只取 blob 列的单值，不经 batch 流水线，Blob 布局保证 1~2 IOP/值。训练数据加载器的主力 API。
scan().with_row_address()
已知 row address（如来自 ANN 结果）直接定点取行，RowAddrMaskFilterExec 免去索引二次查找。
调优抓手速查：① Scanner::batch_size 控制解码粒度；② Scanner::limit/offset 下推避免读多余 page；③ Session 缓存大小决定冷启动后的重复查询延迟；④ LANCE_USE_LITE_SCHEDULER、io_buffer_size_bytes 调节内存/吞吐权衡；⑤ 物化投影顺序（把大列放最后）可让谓词先跑——DataFusion 的 projection pushdown 会自动重排。
