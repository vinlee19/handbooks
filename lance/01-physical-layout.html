1. Dataset 目录树：一个 .lance 数据集的物理形态

一个 Lance 数据集就是一个目录（或对象存储前缀）。目录常量定义在 rust/lance/src/dataset.rs:173-175 与 rust/lance-table/src/io/commit.rs:29-31：

pub(crate) const INDICES_DIR: &str = "_indices";
pub(crate) const DATA_DIR: &str = "data";
pub(crate) const TRANSACTIONS_DIR: &str = "_transactions";
pub const VERSIONS_DIR: &str = "_versions";   // Manifest 存放处
const VERSION_HINT_FILE: &str = "latest_version_hint.json"; // 最新版本提示
— Manifest（表快照） ├─ 1.manifest · 2.manifest · 3.manifest ├─ 18446744073709551614.manifest (V2 命名:u64::MAX−v) ├─ d7.manifest (detached 分支快照) └─ latest_version_hint.json {"version":N} data/　— 不可变数据文件 ├─ 0.lance · 1.lance … {fragment_id}.lance └─ blob/… 大对象外置文件 _deletions/　— 删除掩码（MVCC） ├─ {frag}-{read_ver}-{id}.arrow (数组型) └─ {frag}-{read_ver}-{id}.bitmap _indices/{uuid}/　— 索引文件 ├─ idx.{page} IVF 分区/PQ 码本/图 └─ auxiliary/… _transactions/　— 事务记录 ├─ 0-{uuid}.txn └─ {read_version}-{uuid}.txn 内容 = proto Transaction，用于审计与冲突消解 关键物理事实（源码依据） ① 数据文件不可变：写操作永远创建新文件， 通过新 Manifest 引用新文件实现版本切换。 ② Manifest 位于 _versions/{N}.manifest， V2 命名法把版本号倒置（u64::MAX−v）并补零 20 位， 使字典序最大者=最新版本 → O(1) 定位。 ③ latest_version_hint.json 让 S3 等不支持 字典序列举的后端用 1 次 HEAD 拿最新版本。 ④ 删除不重写数据：只在 _deletions/ 追加掩码文件， 读时与数据文件做布尔差集（apply deletion mask）。 ⑤ Compaction(optimize) 重写小文件并 Rewrite 事务 同步重映射索引中的行地址（row address）。

1.1 Manifest 命名方案（ManifestNamingScheme）

源码 rust/lance-table/src/io/commit.rs:39-77 定义了两种命名方式，是"如何在对象存储上 O(1) 找到最新版本"这一经典问题的 Lance 答案：

方案路径模式最新版本定位方式
V1_versions/{version}.manifestlist 全部 + 字典序排序（版本小则快，大则慢）
V2_versions/{u64::MAX−version 补零20位}.manifest倒置版本号 → 字典序最大就是最新，list 取第一个或配合 hint 文件 0~1 次 HEAD
detached_versions/d{version}.manifest前缀 d 保证 detached 快照永远排在普通版本之后，不会干扰"取最新"；版本号带 0x8000_0000_0000_0000 掩码（DETACHED_VERSION_MASK）
为什么需要 detached version？分支（branch）在 Lance 中不是独立目录，而是"某些版本号带 detached 掩码 + 指向它们的 manifest 副本"。这样索引文件可以跨分支共享同一物理文件，只有 branch 头部指针不同。

2.1 与 Parquet 的根本差异：为什么没有 RowGroup？

ParquetLance v2.x
组织单位RowGroup（通常 128MB，行组内按列存）无 RowGroup；Column → Pages，page 建议 ≥8MB
元数据footer 集中 + thrift，含每行组统计每列独立 metadata 段 + 40B 极简 footer
读取一列一部分读该列在所有行组中的 chunk（多处 seek）按 page 边界直接 Range GET（page 大且连续）
随机访问单行需解开行组 + page header 层层定位页内 offset → MiniBlock 元数据 2B 即定位（详见 02 篇）
追加写不可追加文件不可变，但表级通过 Fragment 机制廉价追加

v1 格式（versions/v1/）还保留老的"column metadata 内嵌 page 计数表"设计；v2.0 起彻底简化为上面 4 段式。当前主线 v2_1 引入 structural 编码与 CompressiveEncoding proto，v2_2/v2_3 增加 descriptor 布局与 Sparse 布局。

3.1 关键设计点逐条深挖

① Fragment 为什么重要 —— "文件的分组"而非"数据的分组"

Fragment 本身不存数据，它是一组 DataFile 的逻辑编组 + 行区间声明。向 dataset 追加数据 = 新建一个 fragment（新文件）+ 新 manifest，O(1) 完成而无需碰旧文件。这直接导致：写放大极小、但小文件问题需要 optimize（Compaction，见 04 篇）来治理。

② DataFile 的 fields 列表 —— 模式演进的基石

每个 DataFile 只携带自己的 fields: Vec<i32>（field_id）。给表加列 = 写一个只含新列的新 DataFile 挂到已有 fragment 上。读取时 Scanner 按 field_id 从多个文件拼接列——加列和回填（backfill）是纯元数据操作。DataFileFieldInterner（fragment.rs:254）还会在反序列化 manifest 时把 field id 序列去重，节省内存。

③ DeletionFile 的 MVCC 语义

read_version 字段表明"这次删除基于哪个版本"，多个删除文件可以在不同版本上叠加；每个 fragment 最多挂一个当前生效的 deletion file（新删除会合并旧删除再生成新文件）。存储上是 Arrow IPC（Array 型，存 u64 row id 数组）或 RoaringBitmap 序列化（Bitmap 型，超过阈值自动切换）。

④ feature flags 的兼容性契约

reader_feature_flags / writer_feature_flags: u64 位图（table.proto 注释列全了每一位）：bit0=存在删除文件、bit1=稳定 row id、bit3=有 config、bit5=禁写事务文件、bit6=存在数据覆盖层(overlay)、bit7=索引声明 covering 列…读老库遇到不认识的 flag 必须拒绝读取——这是 Lance 跨版本安全演进的防线。

5. 字节对齐与 IOPS 设计哲学

file2.proto 顶部注释里藏着一个重要的工程决策：所有对齐要求都交给写入端用 padding 满足，读取端永远可以按"任意偏移+长度"发 Range 请求。这带来：

对 GPU/矢量友好
64B 对齐使解码后缓冲可直接喂 AVX-512/GPU，无再拷贝。
对 Direct I/O 友好
4KiB 对齐 + io_uring（lance-io/src/uring）跳过 page cache。
对对象存储友好
大 page（≥8MB）+ 连续 buffer = 最少请求数、最大吞吐。
下一篇我们将进入这些 buffer 内部：MiniBlock / FullZip / Sparse 三种结构布局如何与 BitPacking、FSST 等压缩算法正交组合——这是 Lance 随机访问比 Parquet 快两个数量级的根本原因。
