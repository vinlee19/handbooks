三种模式的语义差别

模式Transaction.operation物理动作
Create/OverwriteOverwrite{fragments, schema, …}全新 fragment 集，重置 max_fragment_id 之外的元数据；num_retries=0 时为"严格覆盖"，不自动消解冲突

2. 乐观并发提交：重试循环逐行解读

commit_transaction（rust/lance/src/io/commit.rs:1338）是全仓库最精妙的并发代码。核心循环（简化）：

while backoff.attempt() < num_attempts {
    // ① 悲观预检：无论首发成功率如何，每次都先拉取 read_version 之后的全部事务
    (dataset, other_transactions) = load_and_sort_new_transactions(&dataset).await?;
    ensure_can_write_manifest(&dataset.manifest)?;

    // ② 逐个检查冲突：TransactionRebase 判定"我的变更 vs 他人变更"是否可重放
    let mut rebase = TransactionRebase::try_new(&original_dataset, transaction, affected_rows).await?;
    for (other_version, other_txn) in &other_transactions {
        rebase.check_txn(other_txn, *other_version)?;   // 冲突 → Err(CommitConflict)
    }
    transaction = rebase.finish(&dataset).await?;      // 可自动合并的（如 Append）重定 fragment id

    // ③ 小事务内联进 manifest，大事务写 _transactions/ 文件
    let inline = pb::Transaction::from(&transaction).encoded_len() <= MAX_INLINE_TRANSACTION_BYTES;
    current_transaction_file = write_transaction_file(...).await?;

    // ④ 原子发布 manifest（见 §3）；失败/超时 → 清理事务文件 → backoff 重试
}

4. 删除的完整链路（Delete）

dataset.delete("id > 100") 的执行（dataset/write/delete.rs）：

  1. 谓词分类：能否全靠标量索引回答？能→直接得 row id 集合；否则扫描该谓词涉及的列。
  2. 按 fragment 求掩码：命中的 row address 归组到各 fragment，转成 fragment 内偏移集合。
  3. 写 deletion 文件：小集合→Arrow 数组型（.arrow）；大集合→RoaringBitmap 型（.bitmap）。若该 fragment 已有 deletion 文件，新旧合并后写新文件。
  4. 提交：Operation::Delete{updated_fragments(带新 deletion_file), deleted_fragment_ids(全删的), predicate}。
  5. 读时生效：Scanner 对每个 fragment 加载 deletion 掩码，与扫描结果做差集（apply_deletions_as_nulls 可配置为"显示为 null"而非剔除）。

DeletionFile 结构（fragment.rs:421）：{read_version（基于哪个版本删除——MVCC 语义）, id, file_type: Array|Bitmap, num_deleted_rows, base_id}。删除不重写数据文件 ⇒ 删除是 O(命中数) 而非 O(表大小)。

5. Compaction（optimize）：Rewrite 事务与索引重映射

图 4-4 · Compaction。判据默认：fragment 行数 < 目标行数的指定比例、删除率超阈值、文件太碎等（optimize.rs 可配）。
常见误区：①"overwrite 会立即删除旧文件"——错，旧文件属于旧版本，只有 cleanup（retention 策略）才物理删除；②"append 是原子的"——单事务内原子，跨多个 insert 各自是独立事务；③"delete 后数据立即不可见"——新读者立即不可见（新 manifest），进行中的旧读者继续读旧快照（MVCC 隔离）。
与 Delta Lake / Iceberg 对照：Lance 的事务模型与 Delta 的 JSON commit log、Iceberg 的 metadata.json 指针同构（都是"不可变文件 + 原子指针切换"），差异在：Lance 的数据文件本身为随机访问特化（大 page/结构编码）、事务粒度可以携带行地址映射（Rewrite+索引 remap 是原生能力，Iceberg 需要重写索引表）。
