CHAPTER 01 · WHY MOONCAKE

项目全景与设计哲学

在读任何一行代码之前，先回答三个问题：LLM 推理服务的瓶颈到底是什么？为什么缓存 KVCache（而不是缓存别的）是正确的中心化抽象？Mooncake 用怎样的架构把这件事做成一个平台？

1.1LLM 推理的两个阶段与分离式架构

一次 LLM 推理请求分两个阶段：Prefill（预填充）把整段 prompt 一次性算完，是计算密集型的，GPU 利用率高；Decode（解码）逐 token 生成，每步都要读全部历史 KVCache，是访存密集型的，GPU 算力大量闲置。把两者混布在同一批 GPU 上，prefill 的长请求会阻塞 decode 的逐 token 步进，导致首 token 延迟（TTFT）与每 token 延迟（TPOT）互相拖累。

Mooncake 的第一层答案就是 PD 分离（XpYd）：prefill 跑在 Prefill 集群、decode 跑在 Decode 集群，两者之间传输的唯一"中间产物"就是 KVCache。第二层答案是 KVCache 池化：把集群里 GPU 节点的空闲 CPU DRAM 与 SSD 组织成一个大缓存池，跨请求复用相同前缀的 KVCache——相同 system prompt、多轮对话、few-shot 模板都因此免掉重复计算。

图 1-1从单体推理到 PD 分离 + KVCache 池：KVCache 成为两个集群之间的"通用货币"

1.2KVCache-centric：以缓存为中心调度一切

传统推理服务以"请求"为调度单元；Mooncake 以 KVCache 对象为调度单元。每个请求的前缀被切成若干 token 块（对应源码中的 key 对象，见 mooncake-store 的 Put/Get 接口），全局调度器做三件事：

  • 缓存感知路由：优先把请求派往已有所需前缀的实例，未命中再调度 prefill，并把算好的 KVCache 存入池中供后续复用；
  • Early-Rejection：论文发现过载时大部分请求最终都注定超时，与其排队后超时，不如在入口基于负载预测直接拒绝，把算力留给能完成的请求；
  • 租约与淘汰：缓存对象用租约（lease）保护正在使用的 KV，用软/硬 pin 保护高价值前缀（详见第 06 章）。
图 1-2KVCache 对象生命周期：三段式写 → 复用 → 租约 → 淘汰/offload

1.3四层架构分层

把仓库的十几个模块叠起来看，Mooncake 是一个清晰的四层结构：硬件层提供 GPU/NIC/DRAM/SSD；传输层（Transfer Engine）把异构硬件的搬运方式抽象成统一的 submitTransfer 接口；存储层（Mooncake Store）在传输层之上定义 KV 语义、副本、租约与淘汰；集成层把前两层接到 vLLM/SGLang 等推理引擎。

图 1-3四层架构：集成 → 存储 → 传输 → 硬件，每层只依赖下一层的最小接口

1.4FAST'25 论文核心结论

📈 收益数字

· 合成负载下吞吐最高提升 525%（对比 vLLM 基线）
· 真实流量（Arxiv 轨迹）让 Kimi 多承接 75% 请求
· 过载场景 Early-Rejection 显著降低无效算力消耗

🧩 关键设计

· Global Conductor 全局调度器：缓存感知 + 负载预测
· KVCache 池用空闲 CPU/DRAM/SSD，而非挤占 GPU 显存
· XpYd 弹性比例：按负载动态调整 prefill/decode 实例比

论文与请求轨迹开源在仓库 FAST25-release/（Mooncake-FAST25.pdf 与 jsonl trace），可用 benchmarks/storage_benchmark 回放复现。这篇论文获 FAST'25 最佳论文奖，是理解 Mooncake 设计动机的第一手材料。

一个容易混淆的点：Mooncake 不做推理计算。它不含任何模型权重与 attention kernel；它只是让 KVCache 在正确的时刻出现在正确的节点上。推理引擎（vLLM/SGLang）依旧是计算的执行者。
