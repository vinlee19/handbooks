CHAPTER 04 · TRANSPORT FAMILY & RDMA

Transport 家族与 RDMA 深度剖析

本章是 TE 的发动机舱：先纵览 19 种 transport 的家族图谱，然后以最核心的 RdmaTransport 为标本，拆解对象层级、内存注册（含 GPU dmabuf）、QP 建链状态机、三级流控与一次传输的完整生命周期——这是 Mooncake 87 GB/s 带宽数字背后的全部秘密。

4.2RdmaTransport 对象层级

RdmaTransport 是使用最广的 transport，它的内部是清晰的四层对象：Context（每张网卡一个）→ EndPoint（每条对端链路一对 QP）→ WorkerPool（后台收发线程）→ EndpointStore（连接缓存与驱逐）。源码位于 src/transport/rdma_transport/（约 3200 行）。

图 4-2RdmaTransport 对象层级：Context→EndPoint→QP，配套 WorkerPool / EndpointStore / MR 注册表

4.3内存注册与 lkey/rkey

RDMA 的一切前提是"内存先注册"。客户端调用 registerLocalMemory(addr, len, location) 后，RdmaTransport 会对每张网卡各注册一次，得到 per-HCA 的 lkey（本地读）与 rkey（远端写），并随 SegmentDesc 发布到元数据中心——这就是对端能"直接写我内存"的授权凭据。

GPU 内存注册是隐藏的难点：PyTorch allocator 交给 TE 的可能是大块显存内部的偏移地址。无 nvidia-peermem 时，TE 走 dmabuf 路径：cuMemGetAddressRange 找到所属大块 → cuMemGetHandleForAddressRange 拿 dmabuf fd → ibv_reg_dmabuf_mr 注册，并把范围写入按起始地址排序的 memory_region_map_；lkey/rkey 查询用 findMemoryRegionContaining（upper_bound 查找覆盖区间）。

零拷贝的完整含义：① 应用缓冲区 → RDMA 网卡：不经过内核（MR 直映射）；② 节点 → 节点：不经过任何中间缓冲；③ GPU 显存参与传输时经 GPUDirect，不经过 CPU DRAM 拷贝。三者叠加才是"端到端零拷贝"。

4.4QP 建链状态机

每个 RdmaEndPoint（本机网卡 ↔ 对端网卡路径 server@nic）维护 2 个 QP。建链由"首次传输"惰性触发：worker 线程发现 endpoint 未就绪 → 走 TCP 握手交换 gid/qp_num → 双侧推进状态机。断链后 endpoint 经两阶段销毁（先 ERR 态 flush 所有 WR，再等 wr_depth 归零销毁），避免 use-after-free，随后自动重建。

图 4-3QP 建链与销毁状态机：惰性建链 + 两阶段安全销毁 + 自动重建

4.5三级流控：64KB 切片与滑动窗口

RDMA HCA 的队列深度有限（QP max_wr、CQ max_cqe），要打满 400G 带宽必须把大传输切成小片流水线化。TE 的做法是三级窗口协同：

  1. 切片：每个 TransferRequest 按 kBlockSize = slice_size = 64KB（config.h:64）切片，尾片与 fragment_limit=16KB 合并，减少小片开销；
  2. 提交水印：submitTransferTask 累计未发送切片数，达到 max_wr(256) × num_qp_per_ep(2) = 512（rdma_transport.cpp:822 附近）才批量 submitPostSend 交给 worker；
  3. QP 信用水位：EndPoint 按 qp_avail = max_wr_depth − wr_depth_list_[qp]（rdma_endpoint.cpp:986）检查每个 QP 剩余信用，切片均匀分摊到 2 个 QP；放不下的切片保留在 worker 队列，等 pollCq 回收信用后再重发——这就是"窗口滑动"；
  4. CQ 水位：同时检查 cq_remaining = max_cqe − outstanding，防止完成队列溢出。
图 4-4三级流控：切片 → 批量提交水位 → QP 滑动窗口 + CQ 水位，配合重试与网卡熔断

4.6一次 RDMA WRITE 的完整生命周期

调用链速览 · 从用户 API 到 CQE
// ① 用户侧（多线程安全）
BatchID batch = engine.allocateBatchID(1);
engine.submitTransfer(batch, {req});            // req: WRITE 本地buf → hostB@offset
while (engine.getTransferStatus(batch, 0, status) != COMPLETED) {}

// ② MultiTransport::submitTransfer — 按 SegmentID 查对端 protocol → 选 RdmaTransport
// ③ RdmaTransport::submitTransferTask — 64KB 切片 → 绑定 lkey → 挑本地 HCA(selectDevice)
// ④ RdmaContext::submitPostSend → WorkerPool 8 分片队列
// ⑤ transferWorker 线程: endpoint 未建链 → sendHandshake 建链 → RdmaEndPoint::submitPostSend
//     → ibv_post_send(QP, wr)   // 真正的 RDMA verbs 调用，数据被网卡 DMA 发出
// ⑥ monitorWorker 线程: epoll 就绪 → performPollCq: ibv_poll_cq → slice->markSuccess()
//     → 原子累加 task.transferred_bytes / success_slice_count → 扣减 wr_depth → 窗口滑动
// ⑦ getTransferStatus: success+failed == slice_count ⇒ COMPLETED（event-driven 模式用 cv 唤醒）
为什么轮询而不是回调：RDMA 完成事件本身就是异步的；TE 用"batch 内原子计数 + 轮询/条件变量双模式"（USE_EVENT_DRIVEN_COMPLETION）兼顾了低开销与低延迟。上层 Store 的 TransferSubmitter 把轮询封装成 TransferFuture，对业务暴露同步语义。

4.7拓扑发现与选路

Topology::discover()（src/topology.cpp）构造一张"位置 → 网卡"的优先矩阵：

  • CPU 位置：与 HCA 同 NUMA 的进入 preferred_hca，key 为 cpu:N；
  • GPU 位置：先取同 NUMA 的 HCA 子集，再按 PCI 拓扑距离（比较 /sys/bus/pci realpath 的公共前缀深度）选出离 GPU 最近的一组，key 为 cuda:N；
  • 通配：* 记录所有可用 HCA 兜底；
  • 运行时选卡：selectDevice() 默认随机取 preferred（MC_PATH_ROUNDROBIN 开轮询），传输失败重试时顺序遍历并可带"对端网卡提示"做目的亲和。

这张矩阵最终写入本地 SegmentDesc 对外发布——两端各持有一份自己的矩阵，发起端选自己的出口网卡，对端 QP 由握手时的 peer_nic_path 指定入口网卡，两个选择组合成一条最优物理路径。

调试钩子：transfer_engine_topology_dump（wheel 内 CLI）可导出节点完整拓扑矩阵；MC_CUSTOM_TOPO_JSON 可完全手工指定矩阵绕过自动探测——云上虚拟化环境 PCI 信息不全时的救命稻草。
